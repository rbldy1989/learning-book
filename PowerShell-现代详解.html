1.0 相关经典书籍

如果你从 CMD 或 Bash 转过来，学 PowerShell 最大的障碍从来不是语法，而是一个根深蒂固的习惯：把命令的输出当成「一堆字符」。这一章只讲一件事——在 PowerShell 里，管道传的是结构化的 .NET 对象，不是文本行。这个观念一旦转过来，后面所有章节都会顺理成章；转不过来，你写出来的就是「用 PowerShell 语法写的 Bash 脚本」，又长又脆。

1.1 从一个真实的痛点说起

需求很简单：找出当前内存占用超过 100 MB 的前 5 个进程。先看 CMD 时代怎么做。

:: CMD：先让命令打印出一张「报表」，再从字符里抠数据
tasklist | findstr /i "chrome"

:: 输出（节选）
chrome.exe                    4312 Console                    1    268,432 K
chrome.exe                    9088 Console                    1     51,204 K

问题来了：你怎么比较「268,432 K」和 100 MB？你得先把这一行按空白切开，数出内存在第几列，再去掉千位逗号，再去掉末尾的 K，再转成数字，再乘 1024。而这四步里，每一步都可能崩：

  • 系统语言换成英文，表头文字变了，你按行号跳过表头的逻辑就错位；
  • 进程名变长（比如 MicrosoftEdgeWebView2.exe），列宽被撑开，按字符位置切的方案全废；
  • 千位分隔符在某些区域设置里是点号而不是逗号，你的去逗号逻辑静默失效；
  • 会话名里出现空格，按空白切列直接多切一列。

同一件事，PowerShell 里是这样：

# PowerShell：直接按「属性」筛选和排序，全程不碰一个字符
Get-Process |
    Where-Object WorkingSet -gt 100MB |
    Sort-Object WorkingSet -Descending |
    Select-Object -First 5 Name, Id, @{ Name = 'MB'; Expression = { [math]::Round($_.WorkingSet / 1MB, 1) } }

# 输出
Name     Id     MB
----     --     --
chrome   4312 256.0
Code     7720 412.5
explorer 2288 118.3

注意这里发生了什么：WorkingSet 是一个属性，值是 Int64 类型的字节数；100MB 是 PowerShell 内置的数字字面量，等于 104857600。两个数字直接比大小，没有解析、没有正则、没有列宽、没有语言问题。换个系统语言，这条命令一字不改照样跑。

🟢 这就是全书最重要的一句话

CMD 和 Bash 的命令把「数据」渲染成「给人看的报表」再交给下一个命令，下游只能反向猜；PowerShell 的命令把数据本身交给下一个命令，渲染留到最后一刻才做。你省下的不是几行代码，而是一整类永远修不完的 bug。

1.2 管道里流的是对象，不是文本

把上面那条命令想象成一条流水线。在 Bash 里，每个工位收到的是一张打印好的纸——想知道零件重量，只能拿尺子量纸上第几个字符到第几个字符。在 PowerShell 里，每个工位收到的是贴着标签的零件盒：盒子上写着型号（类型名），里面每个格子有名字（属性名）和真实的值（带类型的数据），甚至还附带一套工具（方法）。

你看到的表格，只是「渲染结果」

初学者最容易被屏幕骗到：Get-Process 打印出来明明是一张表格，怎么说它是对象？因为 PowerShell 在管道末端偷偷加了一步——把没人接手的对象交给格式化子系统（Out-Default → Format-Table），按内置的显示规则渲染成表格。屏幕上的列，只是这个对象几十个属性里被挑出来展示的那几个。

# 屏幕上只有 8 列，真实属性远不止
Get-Process -Name explorer | Get-Member -MemberType Property | Measure-Object

# 直接取一个屏幕上根本没显示的属性
(Get-Process -Name explorer).StartTime
(Get-Process -Name explorer).Path

由此得出一条铁律：Format-* 系列命令只能出现在管道最末尾。因为它们吐出来的不再是原始对象，而是一堆「格式化指令」对象，下游的 Where-Object 根本找不到 WorkingSet 属性。

# 错误：Format-Table 之后管道里已经不是 Process 对象了，结果永远为空
Get-Process | Format-Table Name, WorkingSet | Where-Object WorkingSet -gt 100MB

# 正确：先筛选，再渲染
Get-Process | Where-Object WorkingSet -gt 100MB | Format-Table Name, WorkingSet -AutoSize
🔵 现代提示　Write-Host 不入管道

Write-Host 是「直接往屏幕上刷字」，它不产生对象，下游命令什么也收不到。要往管道里送数据请用 Write-Output（或者干脆什么都不写，表达式的结果会自动进入管道）。从 PowerShell 5.0 起 Write-Host 改走信息流（Information Stream，可被 6> 重定向），但它依然不是数据输出。

设计动机：Windows 的数据本来就是结构化的

Unix 选择文本管道是有历史原因的——那个年代的系统对象就是文件和字节流，纯文本是最小公约数。而 Windows 的管理数据一开始就活在注册表、WMI、COM、.NET 里，本身带类型、带层级。把这些结构化数据硬压成文本表格再让你用正则解析回来，是一次有损压缩：类型没了、嵌套没了、精度没了、还平白引入了本地化问题。PowerShell 的答案很直接——既然源头是对象，那就一路传对象，别压。

1.3 动词-名词：命令名本身就是文档

PowerShell 的命令（正式叫 cmdlet，读作 command-let）一律遵循 动词-名词 的形式：Get-Process、Stop-Service、New-Item、Export-Csv。动词表示「做什么」，名词表示「对什么做」，而且名词永远用单数——是 Get-Service 不是 Get-Services，哪怕它返回一堆服务。

这个约定的价值在于可推测性。你在 Linux 上得记住关服务是 systemctl stop、关进程是 kill、关机是 shutdown——三个毫无关联的词。在 PowerShell 里它们是 Stop-Service、Stop-Process、Stop-Computer。你会了一个动词，就等于会了一整排命令。

# 系统认可的动词清单（约 100 个），分组列出
Get-Verb | Sort-Object Group, Verb | Format-Table Verb, Group, Description

# 反过来用：我不知道命令叫什么，但我知道我要操作「服务」
Get-Command -Noun Service

# 我知道我要「导出」点什么
Get-Command -Verb Export

1.4 5.1 与 7：两个 PowerShell，不是新旧关系

这是新手最常踩的认知坑：你的 Windows 里可能同时装着两个 PowerShell，它们不是「旧版和新版」，而是两条并行产品线，可以共存，互不干扰，甚至配置文件、模块目录都是分开的。

  • Windows PowerShell 5.1：可执行文件是 powershell.exe，跑在 .NET Framework 上，只有 Windows 有，随系统内置，版本永久停在 5.1，微软只发安全补丁，不再加新功能。
  • PowerShell 7.x：可执行文件是 pwsh.exe，跑在跨平台的 .NET 上，Windows / Linux / macOS 都能装，需要单独安装，持续迭代。

#requires -Version 7.0
#requires -RunAsAdministrator
#requires -Modules Microsoft.PowerShell.Archive

param(

)
Get-ChildItem -Path $Path -Recurse -File |
    Measure-Object -Property Length -Sum

🔵 现代提示　$IsWindows 在 5.1 里不存在

$onWindows = $PSVersionTable.PSVersion.Major -lt 6 -or $IsWindows

1.6 执行策略：脚本跑不起来的头号原因

你写好了第一个 hello.ps1，双击、或者在终端里敲下路径，得到的是一片红：

无法加载文件 C:\Scripts\hello.ps1，因为在此系统上禁止运行脚本。
有关详细信息，请参阅 about_Execution_Policies。
    + CategoryInfo          : SecurityError: (:) []，PSSecurityException
    + FullyQualifiedErrorId : UnauthorizedAccess

这不是你的脚本有问题，是执行策略（ExecutionPolicy）拦住了。Windows 客户端版上，默认值是 Restricted——只允许交互式敲命令，不允许运行任何 .ps1 文件。

🟢 先摆正认知：它不是安全边界

执行策略防的是「你不小心双击了一个来路不明的 ps1」，不是「恶意程序想执行 PowerShell 代码」。任何人都可以把脚本内容复制粘贴进控制台、或者用 -Command 参数传进去，执行策略一点都拦不住。微软自己的文档也明确说它是防误操作的护栏，不是安全控制。真正的防线是代码签名、AppLocker / WDAC 和受限语言模式。

六个策略值

# 第一步：先看清每一层现在是什么，别盲目改

Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

Set-ExecutionPolicy -ExecutionPolicy Bypass -Scope Process

# 撤销某一层的设置，回落到上一级
Set-ExecutionPolicy -ExecutionPolicy Undefined -Scope CurrentUser
🔴 禁用　别再这么干

Set-ExecutionPolicy Unrestricted -Scope LocalMachine：给整台机器所有用户永久放行任意脚本，包括从互联网下载的。网上一半的教程都这么教，因为它「一次解决所有问题」。请改用 RemoteSigned -Scope CurrentUser——它同样让你自己写的脚本跑起来，但下载来的脚本仍需签名或手动解锁。

还有一种红字：文件被「标记为来自网络」

在 RemoteSigned 下，从浏览器下载、从邮件附件保存、从网络共享复制过来的 .ps1 会带一个叫 Mark of the Web 的 NTFS 备用数据流，PowerShell 会拒绝执行它。

# 看看这个文件是不是带了网络来源标记
Get-Item .\downloaded.ps1 -Stream Zone.Identifier

# 确认内容安全后再解除标记（务必先读一遍脚本内容！）
Unblock-File -Path .\downloaded.ps1

# 批量解锁某个目录
Get-ChildItem -Path .\scripts\ -Filter *.ps1 -Recurse | Unblock-File
🔵 现代提示　自动化场景怎么办

CI 流水线、计划任务这类无人值守场景，不要去改机器策略，而是在调用时一次性指定：

pwsh -NoProfile -ExecutionPolicy Bypass -File .\build.ps1

-NoProfile 同样重要：它跳过用户配置文件，保证脚本在干净环境里跑，不受某台机器上私人配置的影响。另外注意，在 Linux 和 macOS 上执行策略恒为 Unrestricted，Set-ExecutionPolicy 会直接报「平台不支持」——这是正常的，那些平台靠文件权限位来管。

1.7 三大自省命令：学会它们就能自学一切

PowerShell 有几千个命令，没人能背下来，也不需要背。真正要练的是提问的路径：不知道命令叫什么，问 Get-Command；不知道命令怎么用，问 Get-Help；不知道手里这坨东西是什么，问 Get-Member。这三条命令构成一个闭环，能把你从任何陌生场景里捞出来。

Get-Command：这里有没有一把趁手的锤子

# 通配符搜命令名（最常用）
Get-Command *firewall*

# 按动词或名词精确搜
Get-Command -Verb New -Noun Item
Get-Command -Noun Service

# 某个模块提供了哪些命令
Get-Command -Module Microsoft.PowerShell.Archive

# 一个名字到底指向什么：cmdlet？函数？别名？外部 exe？
Get-Command ping
Get-Command ls | Select-Object CommandType, Name, ResolvedCommand

# 不看帮助，直接列出这个命令支持的所有参数名
(Get-Command Send-MailMessage).Parameters.Keys
参数作用
-Name命令名，支持通配符（位置参数，可省略参数名）
-Verb / -Noun按动词或名词部分筛选
-Module限定在某个模块内
-CommandTypeCmdlet / Function / Alias / Application（外部程序）
-ParameterName反查：哪些命令有 -Credential 这个参数
-Syntax只打印语法行，比完整帮助快得多

Get-Help：先看示例，再看参数

# 首次使用先联网下载帮助文档（5.1 出厂时几乎没有本地帮助）
Update-Help -UICulture zh-CN -ErrorAction SilentlyContinue

# 最高效的读法：直接看例子
Get-Help Get-ChildItem -Examples

# 只想搞清楚某一个参数的含义
Get-Help Get-ChildItem -Parameter Recurse

# 完整帮助 / 打开官方网页
Get-Help Get-ChildItem -Full
Get-Help Get-ChildItem -Online

# 概念性主题：语言本身的规则都在这里，几百篇
Get-Help about_*
Get-Help about_Pipelines
Get-Help about_Operators
参数用途使用建议
-Examples只显示示例首选九成问题看例子最快
-Parameter <名>单个参数的详细说明确认参数是否接受管道输入、是否支持通配符
-Full全部内容需要通读时用
-Detailed介于默认和 Full 之间—
-Online打开浏览器看最新官方文档本地帮助过期时用
-ShowWindow弹出可搜索的帮助窗口已过时仅 5.1 有，PS7 已移除
🟢 读懂语法行里的方括号

Get-Help X -Syntax 输出里：[-Path] <String[]> 表示参数名可省略（位置参数）、值必填、类型是字符串数组；[-Force] 整体加括号表示这是开关参数，写上即为真；[<CommonParameters>] 指所有 cmdlet 都有的通用参数（-Verbose、-ErrorAction、-WhatIf 等）。

Get-Member：把对象拆开看

这是三条里最能体现「对象思维」的一条。凡是屏幕上出现了你不认识的输出，就把它管道给 Get-Member。

# 看流经管道的对象是什么类型、有哪些成员
Get-Service | Get-Member

# 只看属性（属性才是能用来筛选和排序的字段）
Get-Service | Get-Member -MemberType Property

# 只看方法（对象自带的动作）
Get-Service -Name Spooler | Get-Member -MemberType Method

输出的第一行最关键——TypeName: System.ServiceProcess.ServiceController。拿这个类型名去搜索，你能查到该类型的全部官方文档。

🔵 现代提示　数组的陷阱

$files = Get-ChildItem; $files | Get-Member 看到的是 数组里每个元素 的类型（FileInfo），因为管道会把数组拆开逐个传递。如果你想看数组本身有哪些成员（比如 Count、Where()、ForEach()），要用参数而不是管道：

Get-Member -InputObject $files

这个区别在调试「为什么 .Count 取不到值」时会救你一命。

一次完整的自学演练

假设你完全没做过「把某个服务改成手动启动」这件事：

# 1) 有没有相关命令？
Get-Command -Noun Service
#    看到 Get-Service / Set-Service / Start-Service / Restart-Service ...

# 2) Set-Service 怎么用？
Get-Help Set-Service -Examples
#    示例里出现 -StartupType 参数

# 3) 这个参数能填哪些值？
Get-Help Set-Service -Parameter StartupType
#    Automatic / Manual / Disabled / AutomaticDelayedStart

# 4) 我手里的服务对象有什么可判断的字段？
Get-Service -Name Spooler | Get-Member -MemberType Property
#    Status / StartType / DisplayName / DependentServices ...

# 5) 先干跑一遍确认无误
Get-Service -Name Spooler | Set-Service -StartupType Manual -WhatIf

整个过程没有搜索引擎、没有翻书，全在终端里完成。这才是这三条命令真正的价值——它们让 PowerShell 成为一个可以问自己问题的系统。

1.8 拆一条管道：每一段流的到底是什么

把观念落成手感。看下面这条命令，目标是找出系统目录下最大的 5 个 DLL 文件，并以 MB 显示。

Get-ChildItem -Path C:\Windows\System32 -Filter *.dll -File |
    Where-Object Length -gt 5MB |
    Sort-Object Length -Descending |
    Select-Object -First 5 Name, @{ Name = 'SizeMB'; Expression = { [math]::Round($_.Length / 1MB, 2) } }
阶段做了什么出口对象类型数量变化
Get-ChildItem枚举文件，产生对象System.IO.FileInfo0 → 约 2000
Where-Object按 Length 属性过滤，不改变对象System.IO.FileInfo约 2000 → 约 60
Sort-Object按数值排序（不是按字符串！）System.IO.FileInfo60 → 60
Select-Object取前 5 个，并裁剪重组属性PSCustomObject60 → 5
（隐式）Out-Default渲染成表格给人看格式化对象—

三个细节值得停下来看：

  1. 排序是数值排序。因为 Length 是 Int64，不是字符串。如果流的是文本，"9 MB" 会排在 "120 MB" 后面——这是文本管道最经典的暗坑。
  2. 计算属性 @{ Name=...; Expression={...} } 是个哈希表，Name（可简写 n）是新列名，Expression（可简写 e）是脚本块，$_ 代表当前对象。这是把对象重新塑形的标准手法。
  3. Select-Object 会换掉对象类型。裁剪之后你拿到的是 PSCustomObject，原来的 FileInfo 方法（比如 .Delete()）就没了。所以「先筛选、后裁剪」的顺序不能反。

换个输出目标，同一份数据可以变成任何格式，而转文本只发生在最后一步：

# 存成 CSV（PS7 默认 UTF-8；5.1 务必显式指定编码，否则中文乱码）
... | Export-Csv -Path .\big-dlls.csv -NoTypeInformation -Encoding utf8

# 转成 JSON 字符串（不落盘）
... | ConvertTo-Json -Depth 3

# 生成 HTML 片段
... | ConvertTo-Html -Title '大文件报告' | Out-File .\report.html

第 2 章变量、类型与运算

上一章你已经能让 PowerShell 跑起来了。这一章处理的是每天都会碰到、也每天都会踩的东西：一个 $ 开头的名字里到底装了什么，它有没有类型，两个值怎么比大小，为什么单引号和双引号能决定你的脚本是正常工作还是吐出一堆光秃秃的 $ 符号。

PowerShell 在这一层做了大量和 C 系语言不同、也和 Bash 不同的取舍。这些取舍不是随便定的——它同时要当一个交互式 shell（你在命令行里敲一行就要能跑）和一个真正的脚本语言（几千行的自动化要能维护）。这两个身份互相拉扯的结果，就是本章里那些看起来"怪"的规则。把动机弄明白，你就不用靠背诵去躲坑了。

2.1 变量：一个 $ 背后的两套规则

你写下这一行，什么都不用声明，它就工作了：

# 直接赋值即创建，不需要 var / let / Dim
$name = 'Ada'
$count = 42
$name                       # 输出 Ada

然后你写下这一行，它也"工作"了，只是什么都没输出：

$naem                       # 拼错了，PowerShell 不报错，直接返回 $null

机制：变量是一个对象，住在 Variable: 驱动器里

PowerShell 里的变量不是编译期的槽位，而是运行时会话状态中的一条记录——一个 PSVariable 对象，带有名字、值、选项和描述。所以你能像操作文件一样操作它：

Get-Variable name            # 查看变量对象本身
Get-ChildItem Variable:\      # 列出当前作用域可见的全部变量
Remove-Variable name         # 删除
New-Variable -Name PI -Value 3.14159 -Option Constant  # 常量，不可改也不可删

变量名不区分大小写：$Name、$name、$NAME 是同一个。名字里如果要用空格、连字符、冒号这类特殊字符，用花括号包起来：${my var}。

🔵 通俗比方

把变量想成贴了标签的抽屉。PowerShell 允许你随手在任何一个空抽屉上贴新标签；而当你去拉一个从没贴过标签的抽屉，它不会报警，只会给你一手空气（$null）。这对交互式命令行是舒服的，对几百行的脚本是灾难性的——错别字会静悄悄地变成 $null 参与运算。

设计动机与现代解法

"不声明也能用"是 shell 血统带来的：命令行里没人愿意为了临时算一下就先写声明。但脚本需要相反的严格性，所以 PowerShell 提供了一个开关，让你在脚本顶部把宽松模式关掉。

🟢 每个脚本第一行都该有的东西

Set-StrictMode -Version 3.0（或 -Version Latest）会让：引用未初始化的变量报错、访问对象上不存在的属性报错、数组越界索引报错、用函数调用语法 f(1,2) 调用命令报错。它只影响当前作用域及其子作用域，不会污染用户的会话。

2.2 类型：动态但不弱，[int]$x 约束了什么

先看一个每个人都会踩一次的例子：

$n = Read-Host '请输入数量'   # 用户输入 100
$n + 1                        # 得到 1001，不是 101

Read-Host 返回的永远是字符串，而 + 的行为由左操作数决定——左边是字符串，于是 + 变成了拼接。这类问题的根治办法不是每次都记得转换，而是给变量本身装上类型约束。

一次性转换 vs 永久约束

这两行长得很像，语义完全不同：

$a = [int]'42'      # 一次性转换：把 '42' 转成 42 再赋值。$a 之后可以变成任何类型
[int]$b = '42'      # 类型约束：给变量 $b 装上转换器，以后每次赋值都会被转成 int

$a = 'hello'        # 完全合法，$a 现在是字符串
$b = '7'            # $b 变成整数 7（自动转换）
$b = 'hello'        # 报错：无法将值 "hello" 转换为类型 System.Int32
🔵 通俗比方

[int]$b 是给抽屉装了一个只收硬币的投币口——你塞纸币进去，它会当场帮你换成硬币，塞不进去的东西直接弹回来。而 [int]'42' 只是你这一次把手里的纸条折成了硬币形状，抽屉本身照单全收。

类型约束在脚本里价值很高：它把"错误的数据"拦在赋值那一刻，而不是等到几十行之后某个运算得出诡异结果。函数参数上的 [int]$Count 用的正是同一套机制。

🟢 变量上也能挂验证特性

类型不是唯一能贴在变量上的东西。参数验证特性同样适用于普通变量：

[ValidateRange(1,100)][int]$Percent = 50 —— 之后任何把它赋成 0 或 101 的尝试都会当场报错。这在长脚本里比事后检查更早、更准。

2.4 字符串：单引号与双引号的分水岭

这是 PowerShell 里回报率最高的一条规则，也是新手 bug 的最大来源：

$name = 'Ada'
'Hello $name'     # 输出：Hello $name
"Hello $name"     # 输出：Hello Ada

机制：两种字符串是两种语法

单引号是逐字字符串（verbatim string）：里面的每个字符都是它自己，没有变量展开，没有转义。唯一的特例是要表示一个单引号本身时，写两个 ''。

双引号是可展开字符串（expandable string）：解析器会在里面找四类东西——变量引用、$() 子表达式、@() 数组子表达式、以及反引号转义序列。

最常踩的坑：变量后面的点号

解析器在双引号里识别变量名时，只吃"变量名"这么多字符——点号、方括号、括号都不算变量名的一部分。所以：

$f = Get-Item .\report.txt

"文件名是 $f.Name"          # 错：输出完整路径后面跟着字面的 .Name
"文件名是 $($f.Name)"        # 对

$arr = 'a','b','c'
"第一项 $arr[0]"             # 错：输出 a b c[0]
"第一项 $($arr[0])"          # 对
🔵 通俗比方

单引号是复印机——你放进去什么，出来就是什么。双引号是朗读者——它会一边念一边把 $ 开头的部分替换成"当前实际的值"，遇到 $( ) 还会停下来先把里面的活干完再接着念。

速查表：转义与特殊序列（仅双引号内有效）

注意：PowerShell 的转义字符是反引号 `，不是反斜杠。这是个刻意的取舍——Windows 路径里全是反斜杠，如果沿用 C 系的 \，那么 "C:\temp\new" 里的 \t 和 \n 就会变成制表符和换行符。用反引号，路径字符串就能原样书写。

序列含义备注
`n换行 (LF)需要 CRLF 时写 `r`n
`r回车 (CR)
`t制表符
`0空字符 NUL
`a / `b响铃 / 退格
`e 6.0+ESC (0x1B)ANSI 颜色序列；7.2+ 更推荐 $PSStyle
`u{1F600} 6.0+Unicode 码位
`$字面的 $写价格时最常用："总价 `$100"
`" 或 ""字面的双引号两种写法等价
``字面的反引号
''（单引号串内）字面的单引号单引号串内只有这一条规则

数组插值与 $OFS

把数组放进双引号，PowerShell 会用一个分隔符把元素连起来，默认是空格。这个分隔符来自变量 $OFS（output field separator）：

$a = 1,2,3
"值：$a"                 # 值：1 2 3

$OFS = ', '
"值：$a"                 # 值：1, 2, 3
Remove-Variable OFS      # 用完记得清掉，它是全局生效的

# 更可控的写法，不依赖隐式状态
"值：$($a -join ', ')"
🟢 拼接的三种正经方式
$n = 'Ada'; $c = 3
"用户 $n 有 $c 条记录"                        # 插值：最易读，首选
'用户 {0} 有 {1} 条记录' -f $n, $c            # 格式化：适合模板、对齐、数字格式
'{0,-10}{1,8:N2}' -f $n, 1234.5              # 左对齐 10 位 + 右对齐 8 位两位小数

字符串比较默认不区分大小写（'ABC' -eq 'abc' 为真），需要区分时用 -ceq。这与 .NET 的默认相反，是为了迁就 shell 用户的直觉。

2.5 Here-String 与它的三个陷阱

当你要在脚本里嵌一段 JSON、一段 SQL、一段 HTML 或一大块帮助文本，用普通字符串会被引号和换行折磨死。Here-String（此处字符串）就是为这个准备的：

$json = @'
{
  "name": "build",
  "path": "C:\logs",
  "template": "$notAVariable"
}
'@

整块内容原样保留：引号不用转义，反斜杠不用转义，$ 也不会被当成变量。同理，@"…"@ 是可展开版本，里面的 $var 和 $( ) 照常生效。

三个陷阱，一个都躲不掉

陷阱错误现象规则
开始符后面还有字符解析错误，或整行被吞@' / @" 后面必须立刻换行，连一个空格都不能有
结束符有缩进"字符串缺少结束符"，报错位置常常在文件末尾，极难定位'@ / "@ 必须顶格在行首，前面不能有任何空白
在 @"…"@ 里写 JSON/正则${...}、$name 被意外展开或报错内容里含 $ 就用单引号版 @'…'@
🔴 缩进陷阱的真实样子
function New-Report {
    $body = @"
    标题：$title
    "@          # 这里缩进了 → PowerShell 不认为字符串结束了
}

报错信息会指向文件的最后一行，跟真正出问题的地方隔了几十行。记住这条规则的代价远小于一次调试。为什么要这么严格？因为"行首的 "@ 才是结束符"这条规则，正是 here-string 内部可以自由出现 "@、引号、任意语言代码的前提。

两种 here-string 的选择

写法变量展开适合放什么
@'…'@不展开JSON 模板、正则、其他语言的源码、含 $ 的配置片段
@"…"@展开 $var、$( )邮件正文、报告文本、需要填空的模板
 
# 需要填空又含美元符号时：用可展开版 + 反引号转义
$user = 'Ada'
$mail = @"
你好 $user：
本月账单为 `$128.00，请于 $((Get-Date).AddDays(7).ToString('yyyy-MM-dd')) 前支付。
"@
🔵 别用 here-string 拼 JSON

手拼 JSON 意味着你要自己负责转义、逗号和引号。有现成工具就别手拼：

$cfg = [ordered]@{ name = 'build'; retries = 3; tags = @('ci','nightly') }
$cfg | ConvertTo-Json -Depth 5 | Set-Content .\config.json -Encoding utf8

Here-string 更适合那些确实"就是一整块死文本"的场景。另外注意换行符：here-string 里的换行取决于源文件本身是 CRLF 还是 LF，跨平台脚本对此敏感。

2.6 数组：定长的真相与 += 的代价

先看一段几乎人人写过的代码：

$result = @()
foreach ($i in 1..100000) {
    $result += $i * 2
}

一百条数据时它瞬间完成，十万条时它能跑上好几分钟。问题不在循环，在 +=。

机制：PowerShell 的数组是定长的 .NET 数组

@() 和逗号构造出的是 System.Object[]——.NET 的数组，长度在创建时固定，不能增长。那 += 是怎么"加进去"的？它悄悄做了三件事：新建一个长度 +1 的数组、把旧数组的所有元素逐个复制过去、把新元素放在最后。

🔵 通俗比方

数组是一个格数固定的鸡蛋托。每加一个蛋，你就得换一个大一号的托盘，然后把原来的蛋一个一个搬过去。十个蛋无所谓，十万个蛋就完全无法接受。

两种正确写法

# 写法一：让循环整体成为表达式的值（最 PowerShell 的写法）
$result = foreach ($i in 1..100000) { $i * 2 }

# 写法二：需要在多处零散追加时，用可增长集合
$list = [System.Collections.Generic.List[int]]::new()
foreach ($i in 1..100000) { $list.Add($i * 2) }
$list.AddRange(@(1,2,3))
🟡 ArrayList 是上一代的答案

老脚本里常见 $a = New-Object System.Collections.ArrayList 加 [void]$a.Add(...)。它能用，但是非泛型的、需要用 [void] 吞掉返回的索引值。现在一律用 [System.Collections.Generic.List[T]]：类型安全、Add() 无返回值、性能更好。

速查表：数组操作

写法作用备注
$a = 1,2,3逗号构造数组最常用；@(1,2,3) 等价

$a = 1..10范围运算符10..1 是倒序；'a'..'e' 需 6.0+ 6.0+

2.7 哈希表：字典、有序表与 splatting

哈希表是 PowerShell 里出场率仅次于数组的结构，而且它有一个别的语言没有的用法——直接当参数包用。

$user = @{
    Name = 'Ada'
    Age  = 36
    Tags = 'admin','dev'
}

$user.Name           # 属性式访问
$user['Age']         # 索引式访问，键名含空格或存在变量时必须用这种
$user.Email = 'a@example.com'   # 新键直接赋值即可
$user.Remove('Age')
$user.ContainsKey('Name')

哈希表的键默认不区分大小写：$user['name'] 和 $user['NAME'] 拿到的是同一项。这和变量名、字符串比较的默认行为是一致的。

顺序：@{} 不保证，[ordered]@{} 保证

$h = @{ b = 2; a = 1; c = 3 }
$h.Keys                        # 顺序不确定，由哈希算法决定

$o = [ordered]@{ b = 2; a = 1; c = 3 }
$o.Keys                        # b, a, c —— 严格按书写顺序

# 造对象时顺序 = 表格列顺序，所以这里几乎总要用 [ordered]（或直接依赖字面量特例）
$row = [pscustomobject][ordered]@{
    时间 = Get-Date
    主机 = $env:COMPUTERNAME
    状态 = 'OK'
}
🟢 遍历哈希表的正确姿势
# 键值对一起拿
foreach ($kv in $h.GetEnumerator()) {
    "{0} = {1}" -f $kv.Key, $kv.Value
}

# 遍历中需要增删时，先把键快照下来，否则会抛"集合已被修改"
foreach ($k in @($h.Keys)) {
    if ($h[$k] -eq 0) { $h.Remove($k) }
}

另一条要记住的：哈希表送进管道时是一个对象，不会逐项流出。想逐项处理必须显式 .GetEnumerator()。

Splatting：哈希表当参数包用

参数一多，命令行就会长到需要横向滚动，或者靠反引号续行——而行尾反引号后面多一个空格就会静默出错。Splatting 把参数装进哈希表，再用 @ 前缀展开：

$params = @{
    Path        = 'C:\Logs'
    Filter      = '*.log'
    Recurse     = $true        # 开关参数在 splat 里写成 $true
    ErrorAction = 'Stop'
}
Get-ChildItem @params           # 注意是 @params，不是 $params

# 条件性追加参数，比写两条几乎相同的命令干净得多
if ($IncludeHidden) { $params['Force'] = $true }
Get-ChildItem @params
反引号续行 已过时
# 脆弱：反引号后面只要有一个不可见的空格，整条命令就断了
Get-ChildItem -Path C:\Logs `
              -Filter *.log `
              -Recurse

用 splatting 代替它。真需要换行时，让行尾停在管道符 |、逗号或左括号上，这些位置解析器知道语句还没结束。

2.8 比较运算符：为什么不是 ==

从别的语言过来的人第一天就会写出这个，然后困惑地看着报错：

if ($a == $b) { ... }     # 报错：意外的标记 '=='
if ($a -eq $b) { ... }    # 正确

设计动机：> 已经被重定向占用了

PowerShell 首先是个 shell。在 shell 里，> 和 < 天然属于重定向：Get-Process > out.txt 必须能工作，而且必须是把输出写进文件，不能是"比较 Get-Process 和 out.txt 谁大"。这个坑位被占了，就没法再拿来做比较。

接下来是一致性问题：如果 >、< 用单词形式而 == 用符号形式，那记忆负担反而更大。于是 PowerShell 干脆全部统一成 -单词 的形式——这也和 -Path、-Recurse 这种参数写法在视觉上保持一致。

== 在 PowerShell 中不存在 禁用

它不是"不推荐"，是根本没有这个运算符。同样地：!= 不存在（用 -ne）、&& 和 || 在 7.0 之前不存在（逻辑运算用 -and / -or）。7.0 起引入的 && / || 是管道链运算符，作用是"上一条命令成功/失败才执行下一条"，不是逻辑与或，别混用。

2.9 数组在左边：比较会变成过滤器

这是 PowerShell 最独特、也最容易造成静默 bug 的一条规则。看下面这段，猜猜输出：

$codes = @(0)
if ($codes -eq 0) {
    '找到了 0'
} else {
    '没找到'
}
# 输出：没找到

数组里明明就是 0，比较也确实匹配上了，但 if 走了 else。

机制：集合在左时，比较运算符返回的是"匹配的元素"

当左操作数是集合，比较运算符不返回布尔值，而是逐个元素比较，把所有匹配的元素组成新集合返回：

$a = 1,2,3,2

$a -eq 2              # 返回 2, 2（两个元素的数组）
$a -ne 2              # 返回 1, 3
$a -gt 1              # 返回 2, 3, 2
($a -eq 2).Count      # 2
($a -eq 9).Count      # 0，空数组

然后 if 把这个返回值转成布尔：空数组是 $false，多元素数组是 $true，而单元素数组取该元素自身的真值。于是 @(0) -eq 0 返回 @(0)，而 [bool]@(0) 就是 $false。

把它当特性用

这个语义不是 bug，它让"从集合里挑东西"变得极短：

$procs = Get-Process
$procs.Name -like 'pwsh*'           # 直接得到匹配的名字数组

$files = Get-ChildItem
$files.Length -gt 1MB               # 得到符合条件的长度值数组
$null 必须放在比较的左边 已过时的写法
# 危险：如果 $x 是 @($null, 1)，这个比较返回 @($null)，真值为 $false
if ($x -eq $null) { ... }

# 安全：$null 是标量，比较必然返回布尔
if ($null -eq $x) { ... }

PSScriptAnalyzer 有专门的规则 PSPossibleIncorrectComparisonWithNull 检查这一点。把它接进 CI，比靠人眼审查可靠。

🟡 附带的一个坑：集合在左时 $Matches 不填充
$lines = 'ID-1','ID-2'
$lines -match 'ID-(\d)'     # 返回两行，但 $Matches 保持不变（甚至是上一次的残留）

# 需要捕获组就逐项处理
foreach ($l in $lines) {
    if ($l -match 'ID-(\d)') { $Matches[1] }
}

第 3 章管道与对象处理

如果你只学 PowerShell 的一件事，那就学管道。它不是「把上一条命令的屏幕输出喂给下一条命令」——那是 cmd 和 bash 的玩法。PowerShell 的管道传的是活的对象：带类型、带属性、带方法。这一章讲清楚管道里到底流着什么，以及沿途那七八个负责筛、变、排、算、导出的命令各自把数据改成了什么形状。

3.1 管道里流的不是文本，是对象

先看一个你多半遇到过的场景：找出占 CPU 最高的几个进程。在 cmd 里，你得先把 tasklist 的输出打出来，再用 findstr 去匹配某一列——而那「一列」其实只是一串空格分隔的字符，列宽一变、进程名一长，脚本就崩了。

# cmd.exe 的思路：先得到一屏文本，再想办法切开它
tasklist | findstr chrome

# PowerShell 的思路：直接对对象的属性提问
Get-Process | Where-Object CPU -gt 10 | Select-Object Name, CPU

差别在于：Get-Process 吐出来的不是字符串，而是一个个 System.Diagnostics.Process 对象。屏幕上那张表只是 PowerShell 在最后一刻替你排版的结果，不是数据本身。想看清对象真正的样子，用 Get-Member——这是本书里你会用得最多的排错命令之一。

Get-Process -Name pwsh | Get-Member

#    TypeName: System.Diagnostics.Process
# Name        MemberType     Definition
# ----        ----------     ----------
# Kill        Method         void Kill()
# Id          Property       int Id {get;}
# CPU         ScriptProperty System.Object CPU {get=...}

打个比方：bash 的管道像是把打印好的报表递给下一个人，对方要拿尺子量、拿剪刀裁，报表格式一改就前功尽弃；PowerShell 的管道像是把整个零件盒直接递过去，每个零件上都贴着标签，下一道工序想拿哪个拿哪个。

管道还有一个容易被忽略的性质：一次一个，边产边耗。上游不会等全部结果攒齐再传，而是每产出一个对象就立刻交给下游。你可以亲眼看见这一点：

1..3 | ForEach-Object { Write-Host "上游产出 $_"; $_ } |
       ForEach-Object { Write-Host "    下游收到 $_" }

# 上游产出 1
#     下游收到 1
# 上游产出 2
#     下游收到 2
# 上游产出 3
#     下游收到 3

这就是为什么 Get-ChildItem -Recurse | Select-Object -First 1 能在几秒内返回，而不必先遍历完整块硬盘——从 PowerShell 3.0 起，Select-Object -First 拿够数量后会向上游发出停止信号。

下游命令怎么知道该拿上游对象的哪一部分？靠参数上的两种管道绑定声明。这是管道能「自动接上」的全部秘密：

绑定方式含义典型例子怎么确认
ByValue把整个上游对象作为该参数的值Get-Process pwsh | Stop-Process（Process 对象整体交给 -InputObject）Get-Help Stop-Process -Parameter InputObject
ByPropertyName拿上游对象里同名属性的值填进参数[pscustomobject]@{ Path = 'C:\Windows\notepad.exe' } | Get-ItemGet-Help Get-Item -Parameter Path
都不支持该命令不接受管道输入，必须写参数Get-Process | Get-Random -Count 1 可以，而多数 New-* 不行帮助里显示 Accept pipeline input? False
🔵 现代提示

PowerShell 7 引入的 && 和 || 叫「管道链操作符」，它们按上一条命令的成功/失败决定要不要执行下一条，不传递对象，和 | 不是一回事。例如 dotnet build && dotnet test。

ETS:每个对象都被 PSObject 包了一层,所以你能给任何东西加属性

管道里流的其实不是裸 .NET 对象,而是包着一层 PSObject 的对象:这层「外套」可以携带额外的成员——这就是扩展类型系统(ETS)。Get-Member 列出的成员里,MemberType 为 NoteProperty/ScriptProperty/AliasProperty 的都是外套上的,C# 里的原类型根本没有:

NoteProperty存死的值拼报表对象、打标记
ScriptProperty每次访问现算(一个 scriptblock)派生值:全名=姓+名
AliasProperty转发到另一属性给生态惯用名搭桥(Name→ProcessName)
🟢 看穿两件日常怪事

①$obj.PSObject 能进这层外套(.PSObject.Properties 枚举全部成员——写通用导出/对比工具靠它);裸值要看真身用 $obj.GetType()。②对象经过远程/作业回来变成 Deserialized.* 类型、方法全没了(5.9 讲过)——那正是「只有外套被序列化传回来」:属性值还在,方法(活代码)留在了对面。ETS 解释了 PowerShell 一半的「魔法」。

3.2 Where-Object：管道上的筛子

Where-Object 只做一件事：对流过的每个对象求一次条件，为真就放行，为假就丢弃。它有两种写法，你都得认识，因为别人的脚本两种都会出现。

# 写法一：脚本块（万能，$_ 代表当前对象）
Get-Service | Where-Object { $_.Status -eq 'Running' -and $_.StartType -eq 'Automatic' }

# 写法二：比较语句简化写法（PowerShell 3.0+，只能写一个条件）
Get-Service | Where-Object Status -eq Running

# $PSItem 是 $_ 的全名，两者完全等价，脚本里用哪个都行
Get-Service | Where-Object { $PSItem.Name -like 'Win*' }
对比项脚本块写法简化写法
条件个数任意多个，可用 -and / -or / 括号只能一个
能否调用方法能，如 $_.Name.StartsWith('a')不能
可读性复杂条件更清楚单条件更清爽
建议仍适用 脚本中的默认选择仍适用 单条件时优先

筛选条件靠比较运算符表达，这张表建议贴在手边：

运算符含义示例
-eq / -ne等于 / 不等于$_.Status -eq 'Running'
-gt -ge -lt -le大于 / 不小于 / 小于 / 不大于$_.Length -gt 10MB
-like / -notlike通配符匹配（* ?）$_.Name -like 'chrome*'
-match / -notmatch正则匹配，结果存入 $Matches$_.Name -match '^svc\d+'
-contains / -notcontains左边的集合里是否含右边的元素$allow -contains $_.Name
-in / -notin左边的元素是否在右边集合里$_.Name -in $allow
-is / -isnot类型判断$_ -is [string]
前缀 c / i强制区分 / 不区分大小写-ceq、-clike、-imatch
🟡 易错：-contains 不是「包含子串」

'PowerShell' -contains 'Power' 得到 $False——-contains 问的是「集合里有没有这个元素」。判断子串请用 -like '*Power*'、-match 'Power' 或 .Contains('Power')。另外，条件里写 = 是赋值不是比较，PowerShell 不会报错，只会让你困惑一下午。

🟢 性能原则：筛选靠左

Where-Object 是在本地逐个过滤，数据已经被取回来了。只要上游命令自带筛选参数，就优先用它，让服务端或文件系统先把量降下来：Get-ChildItem -Filter '*.log'、Get-WinEvent -FilterHashtable @{LogName='System'; Level=2}、Get-ADUser -Filter "Department -eq 'IT'"。管道越靠左筛掉的数据越多，整条链就越快。

3.3 ForEach-Object：对每个对象动手

Where-Object 决定「留不留」，ForEach-Object 决定「做什么」。它对流过的每个对象执行一段脚本块，脚本块里 $_ 就是当前对象；脚本块的输出会继续流向下游。

# 完整形态：-Begin 跑一次，-Process 每个对象跑一次，-End 结尾跑一次
Get-ChildItem *.log | ForEach-Object `
    -Begin   { $total = 0 } `
    -Process { $total += $_.Length; $_.Name } `
    -End     { "共 $([math]::Round($total/1MB,2)) MB" }

# 日常形态：只写 -Process，参数名省略
Get-Process | ForEach-Object { "$($_.Name) 用了 $($_.WS/1MB) MB" }

# 极简形态：-MemberName（PowerShell 3.0+），取属性或调方法
Get-Process | ForEach-Object Name
Get-Process notepad | ForEach-Object Kill

这里要分清两个同名但不同的东西：foreach 语句和 ForEach-Object 命令。

对比项foreach ($x in $c) { } 语句... | ForEach-Object { } 命令
数据来源先把整个集合放进内存，再循环从管道流式接收，来一个处理一个
内存占用大集合会吃满内存恒定，适合超大数据
速度快（无管道开销）慢一些
当前项变量你自己命名的 $x固定是 $_ / $PSItem
break / continue正常工作行为怪异，应改用 return 跳过当前项
选择建议集合已在变量里、要循环控制正在管道中间、数据量大或来源是流
🔵 现代提示：并行处理

PowerShell 7.0 起支持 ForEach-Object -Parallel，每个对象在独立 runspace 中跑：
1..50 | ForEach-Object -Parallel { Test-Connection $using:target -Count 1 } -ThrottleLimit 10
注意三点：脚本块里访问外部变量必须加 $using: 前缀；各线程不共享变量，累加计数器会出错；输出顺序不保证。任务本身很轻时，并行的开销反而更大。

3.4 Select-Object：裁剪、取样与计算列

对象自带几十个属性，但报表里你只想要三列；结果有八百条，但你只想看前十条。Select-Object 同时负责这两件事——它是管道上的裁缝。

# 挑属性（列裁剪）
Get-Process | Select-Object Name, Id, WS

# 取前 N 条（行裁剪），会向上游发停止信号，很省时间
Get-ChildItem C:\Windows -Recurse -File -ErrorAction SilentlyContinue |
    Select-Object -First 5

# 计算列：n= 是 Name 的简写，e= 是 Expression 的简写
Get-Process | Select-Object Name,
    @{ n = 'MemMB'; e = { [math]::Round($_.WS / 1MB, 1) } },
    @{ n = 'RunFor'; e = { (Get-Date) - $_.StartTime } }
参数作用备注
-Property保留哪些属性，支持通配符和计算列位置参数，通常省略参数名
-ExcludeProperty排除某些属性需与 -Property 同用
-First N / -Last N取开头 / 结尾 N 条-Last 必须等上游全部结束
-Skip N / -SkipLast N跳过开头 / 结尾 N 条常与 -First 配合做分页
-Index 0,3,7按下标取从 0 开始
-Unique去重比较的是整个对象；只对单一属性去重更常用 Sort-Object -Unique
-ExpandProperty拆包，只留属性值本身见下一节
🟡 类型会变

只要用了 -Property 或计算列，Select-Object 就造了一批新的 PSCustomObject，原类型和它的方法全部丢失。所以 Get-Process | Select-Object Name | Stop-Process 会失败——下游要的是 Process 对象，你给的是一个只有 Name 属性的自定义对象。需要保留原对象时，别过早 Select，把它留到管道末尾。

3.5 取属性的四种写法与 -ExpandProperty

这是新手最常踩的坑。你想要一个纯粹的名字列表，于是写了 Select-Object Name，结果拼接出来是这样：

$names = Get-Service | Select-Object -First 3 Name
$names -join ', '
# @{Name=AJRouter}, @{Name=ALG}, @{Name=AppIDSvc}     ← 不是你要的

$names = Get-Service | Select-Object -First 3 -ExpandProperty Name
$names -join ', '
# AJRouter, ALG, AppIDSvc                              ← 这才对

原因很简单：Select-Object Name 给你的是一个装着 Name 的盒子（PSCustomObject），把盒子转成字符串自然得到 @{Name=...}；-ExpandProperty 才是把盒子拆开，只把里面那颗糖递出来。比方说，前者是「一份只填了姓名栏的表格」，后者是「姓名本身」。

# 四种写法，同一个目的：拿到服务名
Get-Service | Select-Object Name                    # 对象（含 Name 属性）
Get-Service | Select-Object -ExpandProperty Name    # 裸字符串，流式
Get-Service | ForEach-Object Name                    # 裸字符串，流式
(Get-Service).Name                                    # 裸字符串数组，一次性
写法结果类型是否流式集合为空时什么时候用
Select-Object NamePSCustomObject是无输出要做成表格、要导出 CSV
Select-Object -ExpandProperty Name属性原本的类型是无输出要把值喂给下游参数、要 -join
ForEach-Object Name属性原本的类型是无输出同上，写起来更短
(...).Name（成员访问枚举，3.0+）数组否，先全部取回内存返回空数组小集合、交互式速查
🟢 -ExpandProperty 还能带上下文

-ExpandProperty 可以和 -Property 同时用：展开的对象上会被附加所选的其他属性。例如把每个进程的模块展开、同时保留进程名：
Get-Process pwsh | Select-Object -Property Name -ExpandProperty Modules
另外，被展开的属性若为空或不存在，该对象会被静默跳过，别把这当成筛选手段。

3.6 排序与统计三件套：Sort / Group / Measure

筛完、裁完，接下来通常是排序和汇总。这三个命令组合起来，能顶掉大半个 Excel 数据透视表。

Sort-Object

Get-Process | Sort-Object CPU -Descending | Select-Object -First 5

# 多字段，且每字段单独指定升降序
Get-ChildItem | Sort-Object @{ Expression = 'Extension' },
                              @{ Expression = 'Length'; Descending = $true }

# 按属性去重（比 Select-Object -Unique 常用得多）
Get-Process | Sort-Object Name -Unique

Sort-Object 是阻断性命令：它必须收齐上游所有对象才能开始输出。所以 Sort-Object | Select-Object -First 5 的提前终止优化在这里失效，整条链仍会把数据全取回来——这是意料之中的代价，排序本来就需要看到全部。

Group-Object

# 按扩展名分组，-NoElement 表示不保留每组的成员，只要计数
Get-ChildItem C:\Windows\System32 -File |
    Group-Object Extension -NoElement |
    Sort-Object Count -Descending |
    Select-Object -First 5

# 分组结果当查找表用：-AsHashTable -AsString
$byStatus = Get-Service | Group-Object Status -AsHashTable -AsString
$byStatus['Running'].Count

Measure-Object

Get-ChildItem C:\Windows\System32 -File |
    Measure-Object Length -Sum -Average -Maximum

# 对文本计数：行/词/字符
Get-Content .\README.md | Measure-Object -Line -Word -Character
命令关键参数输出
Sort-Object-Property -Descending -Unique -CaseSensitive -Top N / -Bottom N（PS 6+）-Stable（PS 6.2+）原对象，顺序改变
Group-Object-Property -NoElement -AsHashTable -AsString -CaseSensitiveGroupInfo 对象：Name / Count / Group
Measure-Object-Sum -Average -Maximum -Minimum -Line -Word -Character；-StandardDeviation / -AllStats（PS 6+）一个统计对象：Count / Sum / Average…

把三件套串起来，就是一个「按扩展名统计磁盘占用 Top 5」的完整报表：

Get-ChildItem $HOME -Recurse -File -ErrorAction SilentlyContinue |
    Group-Object Extension |
    ForEach-Object {
        [pscustomobject]@{
            Extension = if ($_.Name) { $_.Name } else { '(none)' }
            Files     = $_.Count
            SizeMB    = [math]::Round((($_.Group | Measure-Object Length -Sum).Sum) / 1MB, 2)
        }
    } |
    Sort-Object SizeMB -Descending |
    Select-Object -First 5
🟢 排序稳定性

历史上 Sort-Object 不保证「值相同的元素保持原有相对顺序」。PowerShell 6.2 起提供 -Stable 开关；需要可复现结果时（例如先按时间排、再按名字排的两段式排序）记得加上它，或干脆在一次调用里写多个排序字段。

算完了总要交付：写文件、发接口、给别的脚本读。这里有一对容易混淆的前缀——ConvertTo-* 把对象变成文本继续留在管道里；Export-* 直接落盘。反方向的 ConvertFrom-* 吃文本，Import-* 吃文件。

🟡 四个必踩的坑
  • Export-Csv 只会平铺一层。属性若是集合或复杂对象，落到 CSV 里就是 System.Object[] 这样的类型名——先用计算列把它压成字符串。
  • Import-Csv 出来的全是字符串。Import-Csv .\sales.csv | Where-Object Amount -gt 1000 做的是字符串比较，而 '99' -gt '1000' 为真，你会筛出一堆错的。正确写法：Where-Object { [double]$_.Amount -gt 1000 }。
  • ConvertTo-Json 默认 -Depth 2。PowerShell 7 会给出截断警告，Windows PowerShell 5.1 默默截断。习惯性写上 -Depth。
  • 编码。Windows PowerShell 5.1 的默认编码不是 UTF-8，中文很容易变问号；PowerShell 6+ 默认 UTF-8 无 BOM。跨版本脚本一律显式写 -Encoding utf8。
🔵 现代提示

# Deserialized.System.Diagnostics.Process   ← 只是数据快照，Kill() 已不存在
🔴 禁用：把凭据明文写进导出文件

禁用 不要把包含密码的对象随手 Export-Csv / ConvertTo-Json——那是明文落盘。Export-Clixml 保存 PSCredential 时用 DPAPI 加密，但只能在同一台机器的同一个用户下解回，不能当作跨机分发的方案。凭据管理见第 9 章。

3.8 格式化命令为什么必须放在管道最后

这是 PowerShell 最著名的陷阱，几乎每个人都会中一次招：

# 看起来天经地义，实际上什么都筛不出来
Get-Process | Format-Table Name, CPU | Where-Object CPU -gt 10

# 导出的 CSV 里全是 ClassId2e4f51ef21dd47e99d3c952918aff9cd 之类的鬼东西
Get-Process | Format-Table Name, CPU | Export-Csv .\out.csv

原因在前面那张「一条数据在管道各环节的形态变化」的最后一格已经画出来了：Format-* 系列命令输出的不是数据对象，而是一串格式化指令对象（FormatStartData、GroupStartData、FormatEntryData……）。它们描述的是「这里画一条表头线、这一列宽 12 个字符」，里面根本没有名叫 CPU 的属性。

打个比方：Format-Table 是印刷车间。零件送进车间，出来的是印好的宣传册。你再把宣传册送去质检工位，质检员当然量不出零件尺寸——它已经不是零件了。

设计动机：PowerShell 把「数据」和「呈现」彻底分开。任何命令在管道末尾结束时，PowerShell 都会隐式调用 Out-Default，由它交给格式化子系统决定怎么画。你显式写 Format-Table，只不过是把这一步提前手动做了——既然做了，后面就没有「数据」可言了。这份分离正是同一批对象既能上屏幕、又能转 JSON、又能进 CSV 的原因。

命令别名适合场景常用参数
Format-Tableft列少、行多，横向对比-AutoSize -Wrap -GroupBy -HideTableHeaders -RepeatHeader（PS 6+）
Format-Listfl属性多，逐条细看；fl * 看全部属性-Property * -GroupBy
Format-Widefw只看一个属性，多列铺满屏幕-Column N -AutoSize
Format-Custom—调试嵌套结构，树状展开-Depth N
🟢 一条冷知识，解释了很多「为什么突然变竖排」

当对象没有内置格式定义时，PowerShell 的默认规则是：要显示的属性不超过 4 个就排成表格，超过 4 个就自动改用列表。所以 Select-Object 多挑一个属性，输出形态可能突变——这不是 bug，显式加 | Format-Table -AutoSize 即可。

🔵 现代提示：三条替代路线

想继续处理数据 → 用 Select-Object，不要用 Format-*。
想要一段可保存的纯文本 → 用 Out-String（配 -Width；加 -Stream 可按行拆开继续流）。
想交互式挑选 → Windows 上的 Out-GridView，或 PowerShell 7 的 Out-ConsoleGridView（来自 Microsoft.PowerShell.ConsoleGuiTools 模块）。
另外 PowerShell 7.2+ 的 $PSStyle 可以统一控制输出配色，不必再往数据里塞转义序列。

第 4 章流程控制、函数与脚本

前三章你一直在敲单行命令。从这一章开始，你要把这些命令攒成能重复运行、能被别人调用、能带参数的东西。流程控制是骨架，函数是关节，脚本和模块是外壳。PowerShell 在这三件事上有一批和 C#、Python、Bash 都不一样的规则——尤其是「函数返回什么」这一条，几乎每个新手都要在上面栽一次。这一章会把它讲透。

4.1 条件判断：if / elseif / else 与真值规则

先看一段看起来完全正常的代码：

# 想判断"有没有找到日志文件"
$logs = Get-ChildItem C:\Logs -Filter *.log
if ($logs) { "找到 $($logs.Count) 个" } else { "一个都没有" }

这段是对的。但把同样的写法搬到别处就会翻车：if ($count) 在 $count 为 0 时走了 else；if ($userInput) 在用户输入字符串 "0" 时却走了 if。原因是 PowerShell 会把条件里的任何东西强制转成 [bool]，而它的转换规则和你的直觉不完全一致。

语法本身很简单

if (条件) {
    ...
} elseif (另一个条件) {
    ...
} else {
    ...
}

三条硬规则：条件必须用圆括号包住；花括号不能省（PowerShell 没有单行 if 的无括号写法）；elseif 是一个词，中间没有空格。

真值转换速查表

表达式转成 [bool]说明
$false / $nullFalse—
0、0.0、0x0、[decimal]0False任何数值类型的零
""、[string]::EmptyFalse只有空串为假
"0"、"False"、" "True非空字符串一律为真，这是最常见的坑
@()False空集合
@(0)、@($null)、@("")False单元素集合取「那一个元素」的真假
@(0, 0)True元素数 ≥ 2 一律为真，不看内容
@{}True空哈希表是真——它是一个对象，不是集合
任意非 null 对象引用True包括 [pscustomobject]@{}

打个比方：PowerShell 的 if 像海关，不管你带的是数字、字符串还是一箱子对象，都要先盖一个 [bool] 章。盖章规则只有一句话——「空的、零的、没有的」是假，其余都是真。字符串 "0" 不空，所以它是真；空哈希表虽然「看着空」，但它是一个实实在在的对象，所以是真。

🔵 现代提示

不确定的时候别猜，直接问它：[bool]$x 会当场给你答案。写脚本时把这行塞进调试输出，比读文档快。

条件里最常用的比较运算符

运算符含义大小写敏感版备注
-eq / -ne等于 / 不等于-ceq / -cne字符串比较默认不区分大小写
-gt -ge -lt -le大于/不小于/小于/不大于加 c 前缀因为 > < 被重定向占用了
-like / -notlike通配符匹配-clike* ? [abc]
-match / -notmatch正则匹配-cmatch成功后填充 $matches
-contains / -in集合包含某元素-ccontains$arr -contains 3 ≡ 3 -in $arr

-and -or -not（!）逻辑运算—-and/-or 会短路求值

三个必须记住的坑

坑一：$null 一定放左边。当左操作数是集合时，比较运算符会变成「过滤器」，返回的是匹配的元素而不是布尔值。

$a = @(1, $null, 3)
$a -eq $null          # 返回 $null 这个元素 → if 判成假，看起来"没有 null"
$null -eq $a          # 返回 False，这才是你要的判断

@(1,2,3) -gt 1        # 返回 2, 3 —— 这是过滤，不是比较

规则很简单：判断相等永远写 $null -eq $x，把常量放左边。

坑二：赋值可以当条件用，而且不报错。

if ($count = 5) { "进来了" }   # 合法！把 5 赋给 $count，然后判成真

PowerShell 不像某些语言会拦你。写比较时多看一眼是 -eq 还是 =。

坑三：字符串比数字。比较时以左操作数的类型为准，右边会被强制转换。

"10" -gt 9        # True  —— "10" 是字符串？不，左边是字符串，右边 9 转成 "9"，字符串比较 "10" < "9"
🟡 上面这行的真实结果是 False

左边是字符串 "10"，于是右边的 9 被转成字符串 "9"，按字典序 "10" 排在 "9" 前面，所以是 False。凡是可能收到字符串的地方，先显式转换：[int]$x -gt 9。

设计动机与现代替代

为什么要设计成「空即假」？因为 PowerShell 首先是个 shell。你在管道里拿到的东西经常是命令的输出，而命令「什么都没找到」时返回的就是空集合。让 if ($result) 自然地表示「有结果吗」，比逼你写 if ($result.Count -gt 0) 顺手得多——而且 .Count 在 $null 上会出问题。

# PowerShell 7+：三元运算符与空合并，短判断不必再写 if 块
$level = $isProd ? 'Error' : 'Verbose'          # 三元 ?:
$name  = $env:APP_NAME ?? 'default-app'          # 为 null 时取右边
$cache ??= @{}                                     # 仅当 $cache 是 null 才赋值
现代提示 现代提示

? :、??、??= 都是 PowerShell 7.0 起才有的语法，在 Windows PowerShell 5.1 上会直接语法报错。写跨版本脚本时，用 #Requires -Version 7.0 声明清楚（见本章最后两节）。注意 ?? 只看 $null，不看「空字符串」。

4.2 switch：多分支、正则、通配与脚本块条件

当 elseif 堆到第四层，代码就开始难读了。switch 是 PowerShell 里被严重低估的一个关键字——它远不止「按值分支」这么简单。

switch ($code) {
    200     { "OK" }
    404     { "没找到" }
    default { "其它：$code" }
}

第一个反直觉：它不会自动停

C 系语言的 switch 是「匹配后一路往下执行语句，直到 break」。PowerShell 的 switch 不一样：它把每一条条件都重新求值一遍，所有命中的分支全都执行。

$file = "report-2026-Q1.final.CSV"
switch -Regex ($file) {
    '\.csv$'  { "标签：表格" }
    'final'   { "标签：定稿" }
    '^report' { "标签：报表" }
    default   { "标签：未分类" }
}
# 输出三行：表格、定稿、报表。default 一行都不出。

注意 default 的语义：它只在一个分支都没命中时才执行，不是「最后兜底跑一次」。想要「命中一条就收工」，自己加 break：

function Get-HttpHint {
    param([int]$Code)
    switch ($Code) {
        200               { "一切正常"; break }
        { $_ -ge 500 }    { "服务端炸了"; break }
        { $_ -ge 400 }    { "请求有问题"; break }
        default           { "未知状态码 $_" }
    }
}

这个「全部求值」的行为不是 bug，是刻意设计。日常运维里「给一个输入贴多个标签」比「二选一」更常见——一个文件既是 CSV、又是定稿、又是报表，三个标签都要。C 式 switch 做不到这件事，PowerShell 让它变成默认行为。你要单选，只需多打五个字母。

条件可以是脚本块

上面 { $_ -ge 500 } 就是脚本块条件：花括号里写任意表达式，返回真就算命中，$_（或写全名 $PSItem）是当前输入值。这一条让 switch 直接取代了 if/elseif 长链。

输入是集合时，它自动逐项处理

switch (1, 2, 3, 4) {
    { $_ % 2 -eq 0 } { "$_ 是偶数" }
    default          { "$_ 是奇数" }
}

这时 break 和 continue 的区别才显出来：continue 是「这一项不比了，换下一项」，break 是「整个 switch 就到这儿，剩下的项也不看了」。输入是单个值时两者效果相同。

switch 参数速查

参数作用示例
-Exact精确匹配（默认行为，通常不用写）switch -Exact ($s) { ... }
-CaseSensitive区分大小写；默认不区分switch -CaseSensitive ($s)
-Wildcard条件按通配符解释（* ? []）'*.log' { ... }
-Regex条件按正则解释，命中后填充 $matches'^ERR-(\d+)' { $matches[1] }
-File <路径>直接逐行读文件当输入，不用先 Get-Content见下

-File 是处理大日志的隐藏利器——它是流式读取，不会把整个文件吞进内存：

$errors = 0; $warns = 0
switch -Regex -File .\app.log {
    '\bERROR\b' { $errors++ }
    '\bWARN\b'  { $warns++ }
}
"错误 $errors 条，警告 $warns 条"
组合是允许的 仍适用

-Regex、-CaseSensitive、-File 可以叠加使用，例如 switch -Regex -CaseSensitive -File .\a.log。但 -Regex、-Wildcard、-Exact 三者互斥，只能选一个。

别再找 switch -Parallel 禁用

switch -Parallel 只存在于 PowerShell Workflow 里，而 Workflow 在 PowerShell 6 之后已被整体移除，不可能回来。要并行处理，用 ForEach-Object -Parallel（下一节）或线程作业 Start-ThreadJob。

4.3 循环家族：for、foreach、while、do

PowerShell 有六种「重复做一件事」的写法。选错了不会报错，只会让脚本慢十倍或者莫名其妙吃光内存。先看全景，再讲怎么挑。

循环结构速查表

写法语法骨架集合何时求值当前项能否 break典型场景
forfor ($i=0; $i -lt $n; $i++) {}不涉及集合自己维护索引能要索引、要计数、要倒着走
foreach 语句foreach ($x in $col) {}先全部求值再开始循环你命名的变量能集合已在内存里，追求速度

foreach 语句 vs ForEach-Object：搬货 vs 传送带

这两个名字太像了，但机制完全不同。

foreach ($x in Get-ChildItem C:\) 会先把 Get-ChildItem 的全部结果装进内存，然后才开始跑循环体。像是先把整仓库的货搬进屋，再一件件拆。快，因为没有管道开销；但如果货有一千万件，你的内存就没了。

Get-ChildItem C:\ | ForEach-Object { ... } 是传送带：上游吐一个，你处理一个，处理完就可以扔掉。内存恒定，第一个结果几乎立刻出现；代价是每一项都要过一遍管道机制，循环体简单时会比 foreach 慢好几倍。

# 大文件统计：这样写内存恒定
Get-Content .\huge.log -ReadCount 1000 | ForEach-Object { $_.Count } |
    Measure-Object -Sum

# 小集合密集计算：这样写更快
$sum = 0
foreach ($n in 1..100000) { $sum += $n }

四个必须避开的性能与语义陷阱

陷阱一：用 += 累加数组。PowerShell 的数组是定长的，$arr += $x 实际是「新建一个大一号的数组、把老的全部复制过去、再放进新元素」。循环一万次就是一万次全量复制，复杂度 O(n²)。

# 慢得离谱 —— 别这么写
$result = @()
foreach ($f in $files) { $result += $f.Name }

# 写法 A：用 List，Add 是 O(1)
$result = [System.Collections.Generic.List[string]]::new()
foreach ($f in $files) { $result.Add($f.Name) }

# 写法 B：更 PowerShell —— 让循环本身作为表达式产出结果
$result = foreach ($f in $files) { $f.Name }

写法 B 值得记住：foreach、for、while 的循环体输出会被自动收集成数组。这是下一小节「函数返回值」那套机制的同一个规则。

陷阱二：1..10000000 会真的生成一千万个元素的数组。范围运算符不是惰性的。计数很大时改用 for。

陷阱三：一边枚举一边改集合。对 List、Hashtable 这类对象，在 foreach 里增删元素会抛 InvalidOperationException。要删就先把待删项收集起来，循环结束后再删；或者对副本枚举：foreach ($k in @($hash.Keys))。

陷阱四：$null 的两副面孔。

foreach ($x in $null) { "跑了" }        # 什么都不输出（PowerShell 3.0 起）
$null | ForEach-Object { "跑了" }        # 输出"跑了" —— $null 是一个合法的管道项

这个不对称经常制造幽灵 bug。管道里如果可能出现 $null，在循环体第一行加 if ($null -eq $_) { return }，或者上游加 Where-Object { $null -ne $_ }。

现代提示：并行循环 现代提示

PowerShell 7.0 起，ForEach-Object -Parallel { } -ThrottleLimit 8 会把每项丢到独立 runspace 里跑（默认并发 5）。注意两点：外部变量必须写成 $using:varName 才能被看见；每个 runspace 是全新会话，模块要重新导入，所以只有当单项耗时明显（网络请求、外部进程）时才划算——CPU 轻活并行反而更慢。

4.4 break、continue 与标签：跳出的边界

break 跳出整个循环，continue 跳到下一轮。这句话在 for/foreach/while 里成立，但一进管道就变味了——而且变味的方式很危险。

switch（集合输入）结束 switch，剩余项不处理跳到下一个输入项结束整个函数

那个会出问题的组合

# 想在找到第一个匹配后停下 —— 这么写会出事
Get-ChildItem C:\Logs | ForEach-Object {
    if ($_.Length -gt 1MB) { "太大：$($_.Name)"; break }
}

break 会沿着调用栈往上找「最近的一个循环」。ForEach-Object 是 cmdlet，不是循环结构，所以它找不到——于是往上继续找，找到调用方的循环就跳出那个，一个循环都没有就直接终止整个脚本。这类 bug 表现为「脚本跑一半悄无声息地结束了，没有报错」，极难排查。

正确的三种写法：

# 写法 1：改用 foreach 语句，break 有明确归属
foreach ($f in Get-ChildItem C:\Logs) {
    if ($f.Length -gt 1MB) { "太大：$($f.Name)"; break }
}

# 写法 2：让管道自己停 —— Select-Object -First 会向上游发停止信号
Get-ChildItem C:\Logs |
    Where-Object Length -gt 1MB |
    Select-Object -First 1

# 写法 3：PowerShell 4.0+ 的 .Where() 方法，'First' 模式
(Get-ChildItem C:\Logs).Where({ $_.Length -gt 1MB }, 'First', 1)
Select-Object -First 是真的会停 仍适用

很多人以为 Select-Object -First 5 只是「把后面的丢掉」。其实它取够数后会向上游抛出一个内部停止异常，让 Get-ChildItem 之类的命令立刻停止枚举。所以在超大目录或长日志上，它既省时间也省内存，是管道里最正统的「提前退出」手段。

标签：跳出嵌套循环

:outer foreach ($server in $servers) {
    foreach ($disk in $server.Disks) {
        if ($disk.FreePercent -lt 5) {
            "$($server.Name) 磁盘告急，停止全部扫描"
            break outer          # 一次跳出两层
        }
    }
}

标签定义时带冒号（:outer），引用时不带冒号（break outer）。continue outer 同理，表示「回到外层循环的下一轮」。标签只能贴在循环关键字前面，不能贴在任意语句上。

4.5 函数：定义、调用与 param() 块

函数是把一段逻辑封起来、起个名字、以后当命令用。PowerShell 的函数有一个特点：它和内置 cmdlet 在使用上完全一样——同样的参数语法、同样能进管道、同样能被 Get-Help 查。这不是巧合，是设计目标。

两种等价写法

# 写法 A：参数写在函数名后面（简洁，适合小函数）
function Get-Square($n) { $n * $n }

# 写法 B：param 块（推荐，能加属性、能加默认值、能写多行）
function Get-Square {
    param($n)
    $n * $n
}

两者语义相同，但 param() 块是唯一能挂参数属性的地方，所以除了随手写的三行函数，一律用写法 B。

param() 的位置不能挪 禁用

param() 必须是函数体里的第一条可执行语句。它前面只能有注释、<# ... #> 注释帮助块，以及 [CmdletBinding()] 之类的属性声明。你先写一行 $ErrorActionPreference = 'Stop' 再写 param()，会直接语法报错。

调用语法：这里最容易暴露「别的语言口音」

# 正确：像调用命令一样，空格分隔，参数名带单横杠
Get-Square -n 5
Get-Square 5                    # 位置参数也行

# 错误但不报错的写法 —— 最阴险的一类 bug
Get-Square(5)                   # 碰巧能跑：(5) 就是 5
Set-Thing(1, 2)                 # 把数组 @(1,2) 整个塞给第一个参数，第二个参数为空

从 C#、Java、Python 转过来的人几乎都会踩这一脚。记住：PowerShell 里的圆括号只表示「先算这一坨」，它不是函数调用语法。参数之间用空格分隔，不用逗号；逗号在 PowerShell 里是「构造数组」的运算符。

升级成高级函数：[CmdletBinding()]

function Get-BigFile {
    [CmdletBinding()]
    param(
        [string]$Path = '.',
        [int]$MinMB = 100
    )
    Write-Verbose "扫描 $Path，阈值 ${MinMB}MB"
    Get-ChildItem $Path -File -Recurse -ErrorAction SilentlyContinue |
        Where-Object Length -gt ($MinMB * 1MB)
}

4.6 参数属性：强制、类型、默认值与验证

参数属性是 PowerShell 里性价比最高的一块——多写十几个字符，就能换来参数校验、Tab 补全、交互提示和自动生成的帮助文档，而且这些校验发生在函数体执行之前，你的代码里一行 if 都不用写。

function New-Backup {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory, Position = 0, ValueFromPipeline)]
        [ValidateNotNullOrEmpty()]
        [string]$Path,

        [Parameter()]
        [ValidateSet('Zip', 'Copy', 'Mirror')]
        [string]$Mode = 'Zip',

        [ValidateRange(1, 30)]
        [int]$KeepDays = 7,

        [switch]$Force
    )
    Write-Verbose "$Mode 备份 $Path，保留 $KeepDays 天"
}

这个签名做完的事：-Path 不给就交互式追问；-Mode 敲 -Mode 后按 Tab 会循环补出三个候选值，传第四个值直接报错；-KeepDays 传 0 或 99 会被拦下；-Force 是开关，写了就是真。

4.7 返回值的坑：没被吞掉的输出全都还给你

这一节是整章最重要的部分。PowerShell 的返回值模型和你熟悉的任何一门语言都不一样，不理解它，你的函数迟早会在生产环境里返回一堆莫名其妙的东西。

一条规则

函数体内每一个没有被赋值、没有被抑制的表达式，它的结果都会成为函数输出的一部分。

return 不是「指定返回值」的语法，它只是「把这个值输出，然后立即退出函数」的简写。return $x 完全等价于 $x; return。

验证一下

function Add-Fruit {
    $bag = [System.Collections.ArrayList]::new()
    $bag.Add("apple")                       # 返回新元素的索引 0 → 漏进输出
    Write-Host "已加入"                     # 走信息流，不漏
    "调试：现在有 $($bag.Count) 项"          # 裸字符串 → 漏进输出
    return $bag.Count                       # 你想要的那个
}

$r = Add-Fruit
$r.Count        # 3   ——  不是 1
$r -join ' | '  # 0 | 调试：现在有 1 项 | 1

修好它：

function Add-Fruit {
    [CmdletBinding()]
    param()
    $bag = [System.Collections.Generic.List[string]]::new()
    $bag.Add("apple")              # List<T>.Add 返回 void，天然安全
    Write-Verbose "已加入"          # 调试信息走 Verbose 流
    return $bag.Count
}

$null = $bag.Add('x')赋值给自动变量 $null，写入即丢弃最快首选可读性最好，任何表达式都能用
[void]$bag.Add('x')把结果强制转换为 void很快推荐方法调用时最自然；复杂表达式记得加括号 [void](...)
$bag.Add('x') > $null把成功流重定向到空设备快可用但和文件重定向长得太像，容易读错
$bag.Add('x') | Out-Null真的建一条管道，逐项送进去丢弃最慢已过时老代码里遍地都是；循环里用会明显拖慢（新版有优化但仍垫底）

集合会被「拆包」

还有一个反直觉：函数输出集合时，PowerShell 会把集合展开成一个个元素送进管道。单元素集合于是就退化成标量。

function Get-Names { return @('alice') }
(Get-Names).GetType().Name      # String —— 不是 Object[]！

# 解法 1（在接收端）：用 @() 强制包成数组，最稳
$names = @(Get-Names)
$names.Count                    # 1

# 解法 2（在输出端）：一元逗号，把数组整个当作"一个对象"输出
function Get-Names2 { return ,@('alice') }

# 解法 3：Write-Output -NoEnumerate
function Get-Names3 { Write-Output @('alice') -NoEnumerate }

为什么要拆包？因为这是管道的基本契约：上游产出的是「对象流」，不是「一个装着对象的容器」。Get-Process | Where-Object ... 之所以能工作，正是因为 Get-Process 的结果被逐个送进管道。函数只是遵守了同一套规则。

写函数时的三条自检 仍适用

1）函数写完后，从上往下扫一遍，问每一行「这行会不会产生输出」；2）调试信息一律用 Write-Verbose／Write-Debug，绝不用裸字符串；3）调用方接收可能为空或单元素的结果时，一律写 @(...) 包一层。

[OutputType()] 不做任何强制 已过时的期待

[OutputType([int])] 只是写给 Get-Command、IntelliSense 和文档看的元数据，运行时不会检查、不会转换、更不会拦截。它有价值（补全和帮助会更准），但别指望它当类型守卫。真要强类型返回，自己在 return 前显式转换。

return 和 exit 不是一回事 禁用混用

return 结束的是当前函数或脚本块；exit 结束的是整个脚本，并设置退出码。在函数里写 exit 1，会把调用它的整个脚本一起干掉；如果这个脚本是被点源运行的（见下文），exit 会直接关掉你的 PowerShell 会话。函数里要报错就用 throw 或 Write-Error。

4.8 管道函数：begin / process / end / clean

你已经会写 Get-Thing -Name x 了。要让它能写成 $names | Get-Thing，还差一步。

先看一个几乎所有人都写错过的版本

function Get-Upper {
    [CmdletBinding()]
    param([Parameter(ValueFromPipeline)][string]$Text)
    $Text.ToUpper()
}

'a', 'b', 'c' | Get-Upper      # 只输出 C

参数属性写对了，管道也确实传进来了，却只剩最后一项。原因是：函数体没有显式分块时，所有代码都属于 end 块——它在整条管道跑完之后只执行一次，此时 $Text 里躺着的自然是最后一个值。

function Get-Upper {
    [CmdletBinding()]
    param([Parameter(ValueFromPipeline)][string]$Text)
    process { $Text.ToUpper() }        # 每来一项执行一次
}
'a', 'b', 'c' | Get-Upper      # A B C

四个块的分工

块执行次数干什么注意
begin { }1（管道开始前）建连接、初始化计数器、准备缓冲区此时管道参数还没有值
process { }每个输入项 1 次真正干活的地方没有管道输入时也会跑 1 次
end { }1（全部处理完）汇总、输出统计不写任何块时，代码默认属于这里
clean { } 7.3+1（无论如何）释放连接、删临时文件语义类似 finally；不能向输出流写东西
分块是全有全无 禁用

一旦你写了 process { }，函数体里就不允许再有块外的裸语句了。下面这种写法会直接语法报错：

function F { param($x); $count = 0; process { ... } } —— 把 $count = 0 挪进 begin { } 就对了。

一个完整例子

function Measure-LogSize {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory, ValueFromPipeline, ValueFromPipelineByPropertyName)]
        [Alias('FullName')]
        [string]$Path
    )
    begin {
        $total = 0L
        $n = 0
        Write-Verbose '开始统计'
    }
    process {
        if (-not (Test-Path -LiteralPath $Path)) {
            Write-Warning "跳过不存在的路径：$Path"
            return                      # 在 process 里 = 处理下一项
        }
        $size = (Get-Item -LiteralPath $Path).Length
        $total += $size
        $n++
        [pscustomobject]@{ Path = $Path; SizeMB = [math]::Round($size / 1MB, 2) }
    }
    end {
        Write-Verbose "共 $n 个文件，合计 $([math]::Round($total/1MB,2)) MB"
    }
}

Get-ChildItem C:\Logs -Filter *.log | Measure-LogSize -Verbose

注意两个细节。第一，ValueFromPipelineByPropertyName 加上 [Alias('FullName')]，让 Get-ChildItem 的输出能自动把 FullName 属性绑到 $Path 上——这是 PowerShell 命令之间能「无缝拼接」的秘密。第二，process 块里的 return 只是「跳过这一项」，不会结束整个函数，语义上等同于循环里的 continue。

$input：end 块里的所有项

function Get-Count {
    end { @($input).Count }        # $input 是个枚举器，含全部管道输入
}
1..5 | Get-Count                    # 5

$input 只是个一次性枚举器——遍历过一次就空了。它在需要「看到全部数据才能算」的场景（排序、去重、求中位数）有用，但代价是必须把所有数据装进内存，失去流式优势。能用 process 就别用 $input。

filter 关键字 已过时

filter Get-Upper { $_.ToUpper() } 是「只有 process 块的函数」的老式简写。它能跑，但不支持 param()、不支持 [CmdletBinding()]、不支持参数验证，帮助系统也认不全。现代替代：写成普通函数加 process { } 块，多打几个字换来全套能力。

参数绑定的完整次序:对象到底怎么「管」进参数

一个对象从管道流进命令时,绑定器按固定次序找它的落点——「为什么管不进去/绑到了错的参数」全部可以按这张次序表推演:

轮尝试说明
①命名参数命令行上显式写了 -Name x 的先占坑
②位置参数没写名字的实参按 Position 落座
③ByValue,精确类型管道对象的类型与某个 ValueFromPipeline 参数完全一致
④ByValue,可转换类型不同但能转(比如任何对象转 [string])——很多「怎么绑到它上面去了」的意外发生在这一轮
⑤ByPropertyName,精确名对象的属性名与某个 ValueFromPipelineByPropertyName 参数同名,取该属性值来绑
⑥ByPropertyName,经别名参数的 [Alias(...)] 也参与对名——Stop-Process 能接 Get-Process 的输出,靠的是 Id 属性对上参数
 
# 诊断利器:让绑定器把决策过程一步步吐出来Trace-Command -Name ParameterBinding -PSHost -Expression {    Get-Process pwsh | Stop-Process -WhatIf}# 输出里能看到每一轮 BIND 尝试、成功/失败与最终落点 —— 别猜,看判决书
🟢 写自己的管道函数,怎么选 ByValue 还是 ByPropertyName

规则很简单:「本命参数」(命令主要操作的那个对象)用 ByValue;「从对象上取一个字段」的参数用 ByPropertyName 并起与生态一致的名字(Name、Id、Path、ComputerName)。两者可以同时标在一个参数上(先试 ByValue 再试 ByPropertyName)。名字与生态对齐,你的函数就自动接得住 Get-* 家族的输出——这是 PowerShell「命令之间天然咬合」的全部秘密。

4.9 脚本参数、.ps1 调用、点源与作用域

把函数存成 .ps1 文件，它就成了脚本。脚本和函数长得像，规则却有几处关键差异——尤其是作用域。

脚本也有 param()

# ---- backup.ps1 ----
#Requires -Version 7.0
[CmdletBinding()]
param(
    [Parameter(Mandatory)][string]$Source,
    [string]$Dest = "$env:TEMP\backup",
    [switch]$Force
)

Write-Verbose "从 $Source 备份到 $Dest"
# ... 实际逻辑 ...

脚本里的 param() 必须是第一条可执行语句，前面只能有注释、#Requires 和属性声明。调用方式和 cmdlet 完全一样：

.\backup.ps1 -Source C:\Data -Verbose

调用方式对照表

写法作用域用在什么时候
.\run.ps1 -Name x新建子作用域，结束即销毁常规执行。注意当前目录不在 PATH 里，.\ 不能省
& 'C:\我的 脚本\run.ps1'新建子作用域路径含空格，或路径存在变量里：& $scriptPath
. .\lib.ps1当前作用域，不新建加载函数库、加载配置——脚本里定义的函数和变量会留下

脚本里能用的内置变量

变量内容典型用途

脚本运行时的「当前目录」是调用者的目录，不是脚本自己的目录。Get-Content .\config.json 在别人从桌面运行你的脚本时会找不到文件。写 Get-Content (Join-Path $PSScriptRoot 'config.json') 才稳。

#Requires：把前提写成硬约束

#Requires -Version 7.4
#Requires -Modules Az.Accounts, Az.Storage
#Requires -PSEdition Core
#Requires -RunAsAdministrator

条件不满足时，脚本一行都不会执行就报错退出。这比在代码里写 if ($PSVersionTable.PSVersion.Major -lt 7) { throw ... } 更早、更可靠——后者已经太晚了，语法层面的不兼容在解析阶段就会炸。#Requires 可以写在脚本的任何一行，但必须是那一行的第一个内容。

执行策略：先解释再动手

# 查看当前各作用域的策略
Get-ExecutionPolicy -List

# 推荐设置：本地写的脚本随便跑，从网上下载的必须有签名
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned

# 下载来的单个脚本确认可信后，去掉"来自网络"标记
Unblock-File .\downloaded.ps1
执行策略不是安全边界 别当防线用

这是微软官方的说法：执行策略防的是「用户不小心双击运行了脚本」，防不住有意为之的攻击者。所以一方面别指望它保护你，另一方面也别为了图省事把机器级策略设成 Bypass——那等于关掉了唯一的误操作提醒。需要临时放宽时，用 -Scope Process，只影响当前这个窗口，关掉就恢复。

作用域：读会向上找，写只写本层

这个「读向上、写向下」的不对称是新手最大的困惑来源：

$counter = 0

function Add-One {
    $counter          # 读得到，输出 0 —— 向上找到了
    $counter++        # 这一句在本地新建了一个 $counter，值为 1
}
Add-One
$counter              # 还是 0 —— 外层根本没变

function Add-One2 {
    $script:counter++ # 显式指定作用域，这才真的改到了
}

打个比方：作用域像一栋楼里的储物柜。你在自己房间找不到某样东西，可以下楼去公共柜里拿来看；但你要放东西，默认只会放进自己房间的柜子——哪怕公共柜里有个同名的。想改公共柜，得写明地址。

这个设计是为了安全：一个函数不应该因为随手用了个常见变量名（$i、$result、$path）就把调用者的状态搞乱。

作用域修饰符速查

修饰符含义备注
$global:x整个会话可见脚本里慎用，容易污染用户环境
$script:x当前脚本文件 / 当前模块内可见模块里维护内部状态的标准做法
$local:x当前作用域（默认行为，通常不写）—
$private:x当前作用域，且子作用域看不到比 local 更严，防止被内层意外读取
$using:x把当前会话的变量值复制到另一个执行上下文Invoke-Command、Start-Job、ForEach-Object -Parallel 里必须用
Get-Variable -Scope 1按层数访问（0 = 本层，1 = 父层）调试有用，业务代码里别写，太脆

点源的正确用法与危险

# ---- functions.ps1 ----
function Get-Foo { 'foo' }
function Get-Bar { 'bar' }

# ---- main.ps1 ----
. (Join-Path $PSScriptRoot 'functions.ps1')   # 点源，把函数装进当前作用域
Get-Foo                                        # 现在能调了

点源的两条铁律：第一，被点源的文件里不要有裸露的执行语句，它们会立刻跑起来；第二，被点源的文件里绝不能出现 exit，因为它会结束整个宿主。函数库文件应该只包含 function 定义，别的什么都别放。

现代提示：写完就打开 StrictMode 现代提示

在脚本第一行加 Set-StrictMode -Version Latest，PowerShell 会把三类静默失败变成明确错误：引用未初始化的变量、访问对象不存在的属性、用函数式语法调用函数（Get-Thing(1,2)）。这是把本章前面讲的所有「不报错但结果不对」的坑，一次性变成会报错的坑。代价是老代码可能要改几处——值得。

scriptblock 与闭包:大括号里装的是什么

{ ... } 在 PowerShell 里是一等公民 scriptblock:一段未求值的代码,可以存进变量、传给参数(Where-Object/ForEach-Object 收的就是它)、用 & 调用、用 . 点源到当前作用域执行。它有参数和返回值,本质是匿名函数:

$area = { param($w, $h) $w * $h }& $area 3 4          # 12 —— & 在新作用域执行. { $x = 42 }; $x    # 42 —— . 在当前作用域执行,内部赋值会留下来

变量捕获是 PowerShell 与多数语言分岔的地方:scriptblock 默认不捕获定义处的变量,执行时按「动态作用域」现场查找——谁调用它,就用谁当时的变量环境。要「定义时的值锁进去」,必须显式 GetNewClosure():

$n = 1$sb  = { $n }$cls = { $n }.GetNewClosure()   # 闭包:拷走此刻的 $n$n = 2& $sb    # 2 —— 动态查找,看到的是现在的 $n& $cls   # 1 —— 锁住了定义那一刻
🔴 两个高频事故:循环变量与跨 runspace

①循环里造一批 scriptblock 回调(比如注册事件),不 GetNewClosure 的话,它们最后全看到循环结束时的变量值——各语言闭包坑的 PS 版,解法就是每次迭代 .GetNewClosure()。②scriptblock 传进另一个 runspace(Start-ThreadJob、ForEach-Object -Parallel)时,外面的变量一概不可见——那边是全新会话;要带数据进去用 $using:varName 语法显式打包(远程 Invoke-Command 同理,见 5.9)。

4.10 模块基础：从 .psm1 到 .psd1

点源能凑合，但一旦你的函数库要给别人用、要有版本号、要能被 Get-Command 发现、要按需自动加载，就该做成模块了。

最小可用模块

模块就是一个目录，目录名和主文件名必须一致：

MyTools\
├─ MyTools.psd1        # 清单（元数据），可选但强烈建议
├─ MyTools.psm1        # 主模块文件，就是改了扩展名的 .ps1
└─ Public\
   ├─ Get-DiskFree.ps1
   └─ New-Backup.ps1

MyTools.psm1 的内容——把每个函数拆成独立文件，然后自动加载：

$publicFiles = Get-ChildItem -Path (Join-Path $PSScriptRoot 'Public') -Filter *.ps1

foreach ($f in $publicFiles) {
    . $f.FullName          # 点源：函数进入模块作用域
}

Export-ModuleMember -Function $publicFiles.BaseName

生成清单（用 splatting 而不是反引号续行）：

$manifest = @{
    Path              = '.\MyTools\MyTools.psd1'
    RootModule        = 'MyTools.psm1'
    ModuleVersion     = '1.0.0'
    Author            = '你的名字'
    Description       = '日常运维小工具集'
    PowerShellVersion = '7.0'
    FunctionsToExport = @('Get-DiskFree', 'New-Backup')
    CmdletsToExport   = @()
    VariablesToExport = @()
    AliasesToExport   = @()
}
New-ModuleManifest @manifest

Test-ModuleManifest .\MyTools\MyTools.psd1     # 校验一下

自动加载靠的是这两样

把 MyTools 目录放进 $env:PSModulePath 列出的任一路径下，你就能直接敲 Get-DiskFree——PowerShell 会自动帮你 Import-Module。

$env:PSModulePath -split [System.IO.Path]::PathSeparator
FunctionsToExport = '*' 会拖垮你的会话 禁用

清单里写通配符，意味着 PowerShell 无法从清单直接知道模块导出了什么，只能把整个模块加载起来再看——每次启动、每次 Tab 补全都要付这个代价。系统里模块一多，控制台启动就会明显变慢。永远显式列出函数名。同理，CmdletsToExport、AliasesToExport、VariablesToExport 用不到就写 @()，不要留空、也不要写 '*'。

模块作用域：一个额外的好处

模块有自己独立的作用域。这意味着 .psm1 里的 $script: 变量是模块私有的：模块内的所有函数都能读写它，模块外的人完全看不见、也改不了。这是维护模块内部状态（缓存、连接句柄、配置）的标准做法。

# MyTools.psm1 内部
$script:cache = @{}

function Get-Cached {
    param([string]$Key)
    if ($script:cache.ContainsKey($Key)) { return $script:cache[$Key] }
    $v = Invoke-ExpensiveThing $Key
    $script:cache[$Key] = $v
    return $v
}

命令 / 概念用途

什么时候用点源，什么时候做模块 选型建议

只有你自己用、就一个文件、改起来天天变 —— 点源。要给同事用、要有版本号、要写帮助文档、要发到内部库、函数超过五六个 —— 做模块。中间态：先按模块的目录结构组织代码（Public/ 一个函数一个文件），哪怕暂时只是点源加载，将来升级成模块只需补一个 .psm1 和 .psd1。

本章要带走的五句话 现代提示

一、条件里「空的、零的、没有的」是假，"0" 和 @{} 是真，$null 永远放比较符左边。
二、switch 会把每条条件都试一遍，要单选就写 break。
三、break 别写在 ForEach-Object 里；要提前停用 Select-Object -First。
四、函数返回的是「所有没被吞掉的输出」，写完函数逐行检查一遍，调试信息一律 Write-Verbose。
五、脚本开头三件套：#Requires、[CmdletBinding()] + param()、Set-StrictMode -Version Latest。

第 5 章文件、注册表与系统管理

前四章你学的是语言本身：管道、对象、参数、函数。这一章开始，PowerShell 要去干它真正被发明出来要干的活——管住一台 Windows 机器。你会发现，一旦把「文件系统、注册表、环境变量、证书」这些八竿子打不着的东西统统塞进同一个路径模型，你要记的命令量会突然塌缩到一个很小的集合。这是 PowerShell 最漂亮的一个设计决定，我们从它讲起。

5.1 一切皆路径：PSProvider 与统一路径模型

先看三个很常见的需求：统计一个目录下有多少个 .log 文件；看看某个注册表项底下挂了哪些子项；列出当前会话里所有环境变量。在 cmd 里这是三套完全不同的工具（dir、reg query、set），三种输出格式，三套参数记法，三次查手册。在 PowerShell 里，它们是同一条命令：

# 三种完全不同的数据源，一条命令
Get-ChildItem C:\Windows\Logs
Get-ChildItem HKCU:\Software\Microsoft\Windows\CurrentVersion
Get-ChildItem Env:

让这件事成立的东西叫 PSProvider（提供程序）。它是一个适配器：把某种层次化的数据源，翻译成 PowerShell 认得的三个概念——驱动器（drive）、容器（container，能装东西的，像目录）、叶子（leaf，装不了东西的，像文件）。翻译完之后，所有以 -Item 结尾的命令就都能作用在它身上了。

打个比方。你家里的 U 盘、移动硬盘、SD 卡，内部构造天差地别，但插到电脑上都是「一个盘符 + 文件夹 + 文件」。USB 协议做的事，就是 PSProvider 做的事——把内部差异藏在适配层后面，对外只暴露一套统一接口。如果你用过 Linux 的 /proc，那更贴切：/proc 把内核状态伪装成文件，好让 cat 和 grep 能读它。PowerShell 把这个思路推广到了极致——不是只有内核状态，而是所有层次化数据都伪装成文件系统。

设计动机很直白：命令数量从「数据源 × 操作」降成了「数据源 + 操作」。假设有 8 种数据源、12 种操作，传统做法要造 96 个工具，PowerShell 只要 8 个 provider 加 12 个命令。对你来说更实惠的是：学会一次 Item 命令族，以后遇到任何新 provider（IIS 的 IIS:、SQL Server 的 SQLSERVER:、Active Directory 的 AD:），你已经会用了。

5.2 路径与项：Test-Path、New-Item 和 Item 命令族

路径这东西看着简单，脚本翻车却经常翻在这儿。先说三个必须现在就纠正的直觉。

第一，别用字符串拼路径。$dir + '\' + $name 在 $dir 末尾已经有反斜杠时会拼出 D:\a\\b，在跨平台脚本里更是直接错。用 Join-Path，它知道该补几个分隔符：

Join-Path 'D:\work' 'logs'                # D:\work\logs
Join-Path 'D:\work\' '\logs'              # D:\work\logs（自动收拾多余的斜杠）
Join-Path 'D:\work' 'logs' '2026' 'a.txt' # 多段拼接，PowerShell 6+ 支持

第二，-Path 会解释通配符，-LiteralPath 不会。文件名里带 [ ] 的情况比你想的常见（下载下来的 report[1].pdf），这时 -Path 会把方括号当成字符集匹配，结果「文件明明在，命令说找不到」。凡是路径来自变量、来自用户输入、来自另一条命令的输出，一律用 -LiteralPath。

第三，PowerShell 的当前目录和 .NET 的当前目录不是一回事。你 cd 到 D:\work，然后调用 [System.IO.File]::ReadAllText('a.txt')——它读的是进程启动时的目录，多半是 C:\Windows\System32。调 .NET 静态方法前先把路径转绝对：

$full = Convert-Path '.\a.txt'        # 必须已存在，返回真实绝对路径
$full = $ExecutionContext.SessionState.Path.GetUnresolvedProviderPathFromPSPath('.\new.txt')  # 不要求存在
[System.IO.File]::ReadAllText($full)

🟡 陷阱：Test-Path 返回 $false 不等于「不存在」

没有读取权限、路径超长、网络共享断开，都会让 Test-Path 老老实实返回 $false。它把「不存在」和「看不见」混为一谈了。关键脚本里，与其信 Test-Path，不如直接 Get-Item -ErrorAction Stop 然后 try/catch，这样你能拿到真实的错误原因。另外，注册表里 Test-Path 只能测「项」，测不了「值」——测值要用 Get-ItemPropertyValue ... -ErrorAction SilentlyContinue。

New-Item：一个参数两种脾气

New-Item -Path 'D:\a\b\c' -ItemType Directory -Force   # -Force 会把中间目录一起建出来
New-Item -Path 'D:\a\b\c\log.txt' -ItemType File -Value 'header'
New-Item -ItemType SymbolicLink -Path 'D:\link' -Target 'D:\real\folder'
危险：New-Item -Force 对已存在的文件是清空重建

-Force 在目录上的意思是「顺手把父目录建出来」，很温和；但在文件上的意思是「已经有了也照建不误」——结果就是原文件内容被清空。想「不存在才建」，请显式判断：if (-not (Test-Path $p)) { New-Item $p -ItemType File }；想追加内容，用 Add-Content。

复制、移动、删除

Copy-Item 'D:\src' -Destination 'E:\backup\src' -Recurse
Move-Item 'D:\a.txt' -Destination 'D:\archive\' 
Rename-Item 'D:\a.txt' -NewName 'b.txt'          # -NewName 只能是名字，不能带路径

# 删除之前，先让它「说说打算删什么」
Remove-Item 'D:\temp\*' -Recurse -WhatIf
Remove-Item 'D:\temp\*' -Recurse -Force -Confirm:$false
🟢 仍适用：-WhatIf 是你的安全带

凡是支持 ShouldProcess 的命令（Remove-Item、Stop-Process、Set-ItemProperty、Restart-Service…）都认 -WhatIf 和 -Confirm。写破坏性脚本的标准动作：先带 -WhatIf 跑一遍看输出，再去掉它。整段脚本要空跑，可以设 $WhatIfPreference = $true。自己写函数时，加上 [CmdletBinding(SupportsShouldProcess)] 和 if ($PSCmdlet.ShouldProcess($target)) {...}，你的函数也就自动有了这条安全带。

🟡 陷阱：-Include / -Exclude 在 Remove-Item 上经常「不生效」

Remove-Item 'D:\temp' -Include '*.log' 什么也删不掉。因为 -Include 是作用在被枚举出来的子项上的，而这条命令的目标只有 D:\temp 这一个项。正确写法是让路径本身带通配符，或者加上递归：Remove-Item 'D:\temp\*' -Include '*.log'，或 Remove-Item 'D:\temp' -Include '*.log' -Recurse。更稳妥的习惯是先 Get-ChildItem 选出来，确认列表没问题，再管道给 Remove-Item。

三个和编码无关、但同样常踩的坑

坑一：Get-Content 返回的是数组，不是字符串。它按行切开，并且吃掉换行符。所以 (Get-Content a.txt) -replace 'foo\r?\nbar', 'x' 永远匹配不上——跨行的正则要先用 -Raw 把整个文件读成一个字符串。

$lines = Get-Content .\app.log            # String[]，每行一个元素
$text  = Get-Content .\app.log -Raw       # 一整个 String，换行符保留
$text -replace "`r`n", "`n" | Set-Content .\app.log -NoNewline

Get-Content .\app.log -Tail 20            # 只看最后 20 行，大文件必备
Get-Content .\app.log -Tail 5 -Wait       # 相当于 tail -f
Get-Content .\app.log -TotalCount 100     # 只读前 100 行就停

坑二：读进来再写回去，换行符会被统一。Set-Content 每写一个元素就补一个换行（Windows 上是 CRLF）。所以「读一个 LF 结尾的文件、原样写回」的结果是全文变成 CRLF，Git 会告诉你整个文件都改了。要精确控制，用 -Raw 读、-NoNewline 写，或者直接调 .NET 的 [IO.File]::WriteAllText()。

坑三：Set-Content 和 Out-File 不是一回事。Set-Content 对每个对象调 ToString()；Out-File 走的是格式化引擎——也就是把你在屏幕上看到的那个表格原样存进去，包括表头、对齐空格，以及超出宽度就截断成 …。

🔴 禁用：用 Out-File 保存对象数据

Get-Process | Out-File p.txt 存下来的是一张给人看的表，列会被截断，数据不可再解析。要保存数据请用 Export-Csv（表格型）、ConvertTo-Json（层次型）或 Export-Clixml（要完整还原 PowerShell 对象时）。Out-File 只适合保存「本来就是文本」的内容，或者存一份人肉查看的快照。

5.4 遍历与筛选：-Recurse、-Filter 和三种过滤法

需求：在一个有二十万个文件的目录树里，找出最近 7 天修改过、体积最大的 10 个 .log。这件事有好几种写法，运行时间能差十倍。差别在于——过滤动作发生在哪一层。

过滤方式在哪里执行速度能力坑
-Filter交给 provider（即 Windows 文件系统 API）在枚举时过滤最快只能一个模式，只认 * ?沿用 Win32 通配符怪癖（见下）；只有 FileSystem 支持
-Include / -ExcludePowerShell 枚举出来之后再过滤中可给多个模式，支持 [a-z] 等 PowerShell 通配符必须配合 -Recurse，或路径以 \* 结尾，否则静默失效
Where-Object管道下游，对象已完全构造好最慢任意属性、任意表达式大目录下内存和时间都吃紧

实战原则：先用 -Filter 把量级砍下来，再用 Where-Object 做精细判断。

Get-ChildItem D:\logs -Filter '*.log' -Recurse -File -ErrorAction SilentlyContinue |
    Where-Object LastWriteTime -gt (Get-Date).AddDays(-7) |
    Sort-Object Length -Descending |
    Select-Object -First 10 FullName,
        @{ Name = 'MB'; Expression = { [math]::Round($_.Length / 1MB, 2) } }
🟡 陷阱：-Filter '*.doc' 会连 .docx 一起捞出来

这不是 PowerShell 的锅，是 Windows 文件系统通配符的历史包袱：匹配时会同时拿长文件名和 8.3 短名去比。report.docx 的短名是 REPORT~1.DOC，于是 *.doc 命中了它。同理 *.htm 会命中 .html，*.xls 会命中 .xlsx。三字符扩展名尤其容易中招。

修法二选一：用 -Include '*.doc'（PowerShell 自己的通配符引擎，没有这个怪癖），或者过滤完再补一刀 Where-Object { $_.Extension -eq '.doc' }。

5.5 注册表读写：项是文件夹，值是属性

注册表让很多人发怵，一半原因是概念对不上号。用 PowerShell 看它，其实只要记住一组映射：

注册表术语对应文件系统用什么命令
项 / 键（Key）目录Get-Item、Get-ChildItem、New-Item、Remove-Item
值（Value）目录上挂的一条属性Get-ItemProperty、Set-ItemProperty、New-ItemProperty、Remove-ItemProperty
默认值（Default）—属性名写成 '(default)'
配置单元 HKLM / HKCU盘符HKLM:、HKCU: 两个驱动器默认就有

关键点：注册表里没有「文件」。值不是子项，而是挂在项上的属性——就像文件的「只读」「创建时间」是属性一样。所以 Get-ChildItem HKCU:\Software\MyApp 只会列出子项，看不到任何值，这不是命令坏了，是你找错了命令。

🟡 陷阱一：Get-ItemProperty 返回的对象里混着五个噪声属性

PSPath、PSParentPath、PSChildName、PSDrive、PSProvider 是 provider 自动附加的，不是注册表里真实存在的值。你要遍历「这个项下所有值」时它们会捣乱。干净的做法：(Get-Item $key).GetValueNames() 拿到真实的值名列表，或者用 Get-ItemPropertyValue（PowerShell 5.0 起）直接取单个值。

🟡 陷阱二：读 REG_EXPAND_SZ 时会被自动展开

Get-ItemPropertyValue HKCU:\Environment Path 读到的是 %USERPROFILE% 已经被替换成实际路径之后的结果。如果你打算「读出来、改一改、再写回去」，这一步会把变量永久固化成当前值——换台机器就废了。要拿原始字符串，得下沉到 .NET：

$k = [Microsoft.Win32.Registry]::CurrentUser.OpenSubKey('Environment')

$k.Close()
🔴 危险：32 位视图重定向，以及 HKLM 的不可逆操作

在 32 位 PowerShell 里访问 HKLM:\SOFTWARE\X，系统会悄悄把你重定向到 HKLM:\SOFTWARE\WOW6432Node\X。同一段脚本在 powershell.exe（64 位）和 SysWOW64\powershell.exe（32 位）下读到的是两个不同的地方。计划任务里尤其容易踩，因为你不一定知道它启的是哪个。

5.7 计划任务：让脚本自己跑起来

脚本写好了，下一个问题必然是：怎么让它每天凌晨两点自己跑？答案是注册一个计划任务。Windows 8 / Server 2012 起自带 ScheduledTasks 模块，全套用 PowerShell 即可完成。

一个任务由四块拼成，像给操作系统贴一张便利贴：什么时候（Trigger）、用谁的身份（Principal）、干什么（Action）、出状况怎么办（Settings）。

$argLine = '-NoProfile -NonInteractive -ExecutionPolicy Bypass -File "D:\ops\backup.ps1"'

$action = New-ScheduledTaskAction -Execute 'pwsh.exe' -Argument $argLine -WorkingDirectory 'D:\ops'
$trigger = New-ScheduledTaskTrigger -Daily -At '02:00'
$principal = New-ScheduledTaskPrincipal -UserId 'SYSTEM' -LogonType ServiceAccount -RunLevel Highest
$settings = New-ScheduledTaskSettingsSet -StartWhenAvailable `
                -ExecutionTimeLimit (New-TimeSpan -Hours 2) -MultipleInstances IgnoreNew

Register-ScheduledTask -TaskName 'NightlyBackup' -TaskPath '\Ops\' `
    -Action $action -Trigger $trigger -Principal $principal -Settings $settings -Force
# 查看、试跑、删除
Get-ScheduledTask -TaskPath '\Ops\' | Get-ScheduledTaskInfo |
    Select-Object TaskName, LastRunTime, LastTaskResult, NextRunTime
Start-ScheduledTask -TaskName 'NightlyBackup' -TaskPath '\Ops\'   # 不等触发时间，立刻跑一次
Disable-ScheduledTask -TaskName 'NightlyBackup' -TaskPath '\Ops\'
Unregister-ScheduledTask -TaskName 'NightlyBackup' -TaskPath '\Ops\' -Confirm:$false

-AtLogOn -User 'DOMAIN\alice'指定用户登录时
-Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Minutes 15)每 15 分钟一次

5.8 WMI/CIM：系统信息的万能查询口

「这台机器插了几条内存、单条多大」「系统上次装机是什么时候」「每块磁盘还剩多少空间」——这类信息没有专门的 cmdlet，或者有但不够细。它们都躺在 WMI 里。

把 WMI 想成一个只读为主的系统信息数据库：Win32_Process、Win32_Service 这些「类」是表，类的属性是列，WQL 是简化版的 SQL。CIM 则是这个数据库遵循的行业标准模型；PowerShell 里的 CIM 命令，就是这个数据库的客户端。

# 各分区剩余空间（DriveType=3 表示本地固定磁盘）
Get-CimInstance -ClassName Win32_LogicalDisk -Filter 'DriveType=3' |
    Select-Object DeviceID,
        @{ N = 'FreeGB'; E = { [math]::Round($_.FreeSpace / 1GB, 1) } },
        @{ N = 'SizeGB'; E = { [math]::Round($_.Size / 1GB, 1) } },
        @{ N = 'Used%';  E = { [math]::Round(100 * (1 - $_.FreeSpace / $_.Size)) } }

# 上次开机时间（CIM 会自动转成 DateTime，不用再手工解析）
(Get-CimInstance Win32_OperatingSystem).LastBootUpTime

# 调用方法：不是 $obj.Method()，而是 Invoke-CimMethod
Get-CimInstance Win32_Process -Filter "Name='notepad.exe'" |
    Invoke-CimMethod -MethodName Terminate

5.9 远程执行一瞥：Invoke-Command 与序列化边界

上面所有命令都还只作用在本机。当你要管的是 100 台机器时，Invoke-Command 是那把总钥匙。

# 一次性执行：命令在每台机器上并行跑（默认最多 32 个并发）
Invoke-Command -ComputerName srv01, srv02, srv03 -ScriptBlock {
    Get-Service 'Spooler' | Select-Object Name, Status
}

# 复用连接：多次操作同一批机器时省下反复握手的开销
$s = New-PSSession -ComputerName srv01, srv02
Invoke-Command -Session $s -ScriptBlock { $env:COMPUTERNAME }
Copy-Item 'D:\ops\backup.ps1' -Destination 'C:\ops\' -ToSession $s[0]
Remove-PSSession $s

# 把本地变量带过去：$using: 前缀
$threshold = 90
Invoke-Command -ComputerName srv01 -ScriptBlock {
    Get-CimInstance Win32_LogicalDisk -Filter 'DriveType=3' |
        Where-Object { (1 - $_.FreeSpace / $_.Size) * 100 -gt $using:threshold }
}

这里有一个你必须建立的直觉：脚本块是在对面那台机器的另一个 PowerShell 进程里跑的。它有自己的变量、自己的当前目录、自己加载的模块。你本地定义的函数、变量，对面统统不知道——除非你用 $using: 显式带过去，或者用 -ArgumentList 配合 param() 传参。

看懂这张图，你就能提前躲开新手最常撞的那堵墙：

# 错的：远程返回的是「标本」，Kill() 方法在序列化时就没了
(Invoke-Command srv01 { Get-Process notepad }).Kill()

# 对的：让方法调用发生在对面
Invoke-Command srv01 { Get-Process notepad | Stop-Process -Force }

原则：把「动作」整个丢到对面去做，只把「结果数据」带回来。回来的对象只适合筛选、排序、导出、报表——所有需要调方法的事，都留在脚本块里面。

-Session $s复用已有会话多步操作、需要保持状态时用
-FilePath .\a.ps1把本地脚本文件送过去执行对面不需要有这个文件
-AsJob后台作业配合 Receive-Job 收结果
-ThrottleLimit 16并发上限默认 32
$using:x带本地变量过去只读；改了不会传回来
-ArgumentList + param()传参数另一种传值方式，兼容性更好
Enter-PSSession交互式进入远程相当于 ssh 到对面的 PowerShell
Copy-Item -ToSession / -FromSession通过会话传文件不需要额外开共享
🔵 现代提示：PowerShell 7 支持基于 SSH 的远程

WinRM 是 Windows 专属、配置繁琐。PowerShell 7 起可以直接走 SSH，同一套命令还能连 Linux：

Invoke-Command -HostName 'alice@srv01.example.com' -SSHTransport -ScriptBlock { Get-Date }

🔴 禁用：TrustedHosts 设成 *

非域环境里配远程时，网上大量教程会让你执行 Set-Item WSMan:\localhost\Client\TrustedHosts -Value '*'。这等于宣布「任何主机都可信」，中间人可以冒充目标机器骗走你的凭据。正确做法是只列出你真正要连的主机名（-Value 'srv01,srv02' -Concatenate），生产环境则应配置 HTTPS 监听器（5986）并使用证书。同理，CredSSP 不要随手打开——它会把你的明文凭据交给远程机器，一旦对方被攻陷，凭据直接失守。解决「双跳」问题应优先考虑基于资源的约束委派。

第 6 章错误处理、调试与实用技巧

前五章你已经能把命令、管道、函数串成像样的脚本了。但真正把脚本交出去跑，你会遇到另一类问题：某台机器连不上、某个文件被占用、某个字段是空的。脚本崩了不可怕，可怕的是它不崩、也不干活，还给你一路绿灯。这一章讲的就是：错误从哪来、怎么接住、怎么定位、以及怎么写得又稳又快。

本章所有实测数据都来自 Windows PowerShell 5.1（Windows 11，10.0.26200），代码在 PowerShell 5.1 与 7.x 上都能跑，版本差异会单独标注。

6.1 两类错误：非终止型与终止型

先看一个让无数人栽跟头的现象。你写了段脚本批量处理 500 台机器，跑完一看"成功"，结果一查发现中间 30 台根本没处理；换个脚本，开头一个小毛病就整个崩掉。同样是"出错"，为什么表现天差地别？

因为 PowerShell 里的错误分两类：

  • 非终止型错误（Non-terminating error）：命令说"这一条我干不了，但我手上还有别的活"。它把错误写进错误流，然后继续处理下一个输入对象。
  • 终止型错误（Terminating error）：当场停机。当前管道立刻停止，异常沿调用栈向上抛，直到有人接住，或者整个脚本中止。

打个比方：非终止型错误像流水线上的质检员，在次品上贴张红条就放行，生产线一秒不停；终止型错误则是有人拉了紧急停机绳，整条线立刻定住。

为什么要这么设计？ 因为 PowerShell 天生是面向"一批对象"的。Get-ChildItem C:\ -Recurse | Remove-Item 要处理上万个文件，其中三个因为权限失败，你显然不希望剩下的九千九百多个也不做了。所以默认策略是"记下来，接着干"。这个默认值救了很多批处理场景，也坑了很多以为 try/catch 万能的人。

下面这段代码把差别摆在一起，你自己跑一遍印象最深：

# A：非终止型 —— Get-Item 找不到路径，但脚本继续
Get-Item 'C:\不存在的目录\a.txt'
'这一行照样执行'

# B：终止型 —— .NET 方法抛异常，当场停止
[int]::Parse('abc')
'这一行不会执行'

更严重的是，try/catch 对第一种完全无效。这是实测输出，一个字没改：

try {
    Get-Item 'C:\no\such\file_xyz.txt'
    'after'
} catch { 'CAUGHT-1' }
# 实际输出：一大段红字报错，然后打印 after —— catch 块根本没进去

try {
    Get-Item 'C:\no\such\file_xyz.txt' -ErrorAction Stop
    'after'
} catch { 'CAUGHT-2: ' + $_.Exception.GetType().Name }
# 实际输出：CAUGHT-2: ItemNotFoundException

记住这条铁律：想让 try/catch 接住 cmdlet 的错误，就必须写 -ErrorAction Stop。这是全章最值钱的一句话。

6.2 错误开关面板：$ErrorActionPreference 与 -ErrorAction

既然默认是"记下来接着干"，那怎么改？PowerShell 给了你两个旋钮：一个全局的偏好变量 $ErrorActionPreference，一个逐条命令的通用参数 -ErrorAction。后者优先级更高，覆盖前者。

# 旋钮 1：影响之后的所有命令（按作用域生效）
$ErrorActionPreference = 'Stop'

# 旋钮 2：只影响这一条命令，优先级更高
Get-Content $path -ErrorAction Stop

ActionPreference 取值速查表

取值显示错误继续执行记入 $Error说明
Continue是是是默认值。看得见、拦不住
SilentlyContinue否是是只是不显示，错误照样被记录，事后可翻 $Error
Stop是否是把非终止型升级为终止型，try/catch 才能接住
Inquire是问你是弹出"继续/挂起/中止"提示，仅适合手工交互
Ignore否是否彻底当没发生。只能用于 -ErrorAction，见下方警告
Break是进调试器是PowerShell 7.0+ 才有，出错即断点，调试神器
Suspend———禁用仅用于已废弃的 Workflow，普通脚本别碰
Ignore 不能赋给偏好变量 禁用

$ErrorActionPreference = 'Ignore' 这行赋值本身不报错，所以很多人以为生效了。实测下一条 cmdlet 执行时会抛出：The value Ignore is not supported for an ActionPreference variable ... and has been replaced by the default value. —— 不但没静音，反而白白多出一条错误。Ignore 只能作为 -ErrorAction 的参数值逐条使用。

脚本顶部一刀切 SilentlyContinue 禁用

$ErrorActionPreference = 'SilentlyContinue' 放在脚本第一行，等于把仪表盘上所有的灯泡都拧下来 —— 车照开，故障你一个都看不见。真要吞掉某条命令的噪声，就在那一条命令上写 -ErrorAction SilentlyContinue，并配 -ErrorVariable 把它捞出来核对。

还有个更阴险的副作用（实测）：脚本里设了 SilentlyContinue 之后，连 throw 'boom' 都会被无声吞掉，后面的代码继续执行，脚本退出码还是 0。这是历史遗留的怪异行为，绝对不要依赖，更不要在这种状态下写业务逻辑。

作用域：偏好变量是"会往下传"的

偏好变量遵循 PowerShell 的作用域规则：在函数里赋值，只影响这个函数和它调用的东西，函数一返回就恢复。这让你可以放心地做局部收紧：

function Import-Config {
    [CmdletBinding()]
    param([string]$Path)

    $ErrorActionPreference = 'Stop'   # 只在本函数内部生效，出了函数自动还原

    try {
        Get-Content $Path -Raw | ConvertFrom-Json   # 不用逐条写 -ErrorAction 了
    }
    catch {
        throw "配置读取失败：$Path -- $($_.Exception.Message)"
    }
}
🟡 一个例外：模块

写在模块（.psm1）里的函数不会继承调用方作用域的偏好变量 —— 模块有自己的会话状态。所以你在控制台里设 $ErrorActionPreference='Stop'，模块内部的命令未必听你的。模块作者应当显式写 -ErrorAction Stop，而不是指望调用者的环境。

6.3 try / catch / finally：把错误接住

结构化异常处理的语法和 C#、Java 几乎一样，会一种就会全部：

try {
    # 可能出事的代码
}
catch [System.IO.FileNotFoundException] {
    # 只接这一类异常（也接它的派生类）
}
catch {
    # 兜底：接住上面没匹配到的一切
}
finally {
    # 无论成功、失败、还是被上层接走，都一定执行
}

三条规则要记牢：

  1. catch 从上往下匹配，先具体后宽泛。 把无类型的兜底 catch 写在最后，否则后面的类型化 catch 永远轮不到。
  2. $_（也写作 $PSItem）在 catch 里是一个 ErrorRecord，不是 Exception。 真正的异常对象在 $_.Exception 里。这是新手最容易搞混的一层包装。
  3. finally 一定跑。 哪怕 try 里 return 了、哪怕异常正在往上抛，它都会先执行完。释放文件句柄、删临时文件、恢复现场全靠它。

catch 里的 $_ 字段速查表

表达式拿到什么典型用途
$_.Exception.Message人话错误消息写日志、拼提示
$_.Exception.GetType().FullName异常类型全名照抄进 catch [类型] 里
$_.Exception.InnerException内层的真正原因调 .NET/REST 时外层消息常常没营养
$_.FullyQualifiedErrorId形如 PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand最稳定的判定依据，比匹配消息文本靠谱（消息会随系统语言变！）
$_.CategoryInfo.Category大类，如 ObjectNotFound / PermissionDenied粗粒度分支
$_.TargetObject出错时正在处理的那个对象知道是"哪一条"失败了
$_.InvocationInfo.ScriptLineNumber出错行号定位
$_.InvocationInfo.Line出错那一行的原文日志里还原现场
$_.ScriptStackTracePowerShell 层面的调用栈多层函数嵌套时救命

一个完整的实用例子 —— 读配置文件，分门别类地处理三种失败：

function Get-AppConfig {
    [CmdletBinding()]
    param([Parameter(Mandatory)][string]$Path)

    try {
        $raw = Get-Content -LiteralPath $Path -Raw -ErrorAction Stop
        return $raw | ConvertFrom-Json -ErrorAction Stop
    }
    catch [System.Management.Automation.ItemNotFoundException] {
        Write-Warning "配置不存在，改用默认值：$Path"
        return [pscustomobject]@{ Retry = 3; TimeoutSec = 30 }
    }
    catch [System.ArgumentException] {
        # JSON 语法错误。注意：不同 PowerShell 版本 ConvertFrom-Json 抛的类型不同，
        # 拿不准就先在自己机器上跑一次 $Error[0].Exception.GetType().FullName 确认
        throw "配置文件不是合法 JSON：$Path"
    }
    catch {
        throw    # 裸 throw：原样重新抛出当前错误，保留原始类型和调用栈
    }
    finally {
        Write-Verbose "配置加载流程结束：$Path"
    }
}
裸 throw 是个好习惯 仍适用

在 catch 块里单独写一个 throw（不带任何参数），表示"我记录一下，但这个错我处理不了，原样交给上层"。它保留原始异常类型和调用栈；而 throw $_.Exception.Message 会把一切降级成一条字符串，上层就再也没法按类型判断了。

trap：来自 PowerShell 1.0 的老写法 已过时

trap { ... } 是 try/catch 出现之前的错误捕获语法，作用域级别生效、跳转行为难以预测、和现代代码风格格格不入。除非维护十几年前的老脚本，一律用 try/catch/finally。

PowerShell 没有 using 语句块 现代提示

C# 里的 using (var r = new StreamReader(...)) 在 PowerShell 里没有对应语法（using namespace／using module 是完全不同的东西）。凡是拿到实现了 IDisposable 的 .NET 对象（StreamReader、SqlConnection、HttpClient），都要自己在 finally 里调 .Dispose()。

6.4 $Error、$? 与错误记录解剖

错误发生过、又被静音了，去哪找？PowerShell 会把每一条错误记录塞进自动变量 $Error，最新的在最前面，也就是 $Error[0]。

Get-Item 'C:\no\such\file.txt' -ErrorAction SilentlyContinue   # 屏幕上什么都没有

$e = $Error[0]                        # 但它就在这儿
$e.FullyQualifiedErrorId              # PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand
$e.CategoryInfo.Category              # ObjectNotFound
$e.TargetObject                       # C:\no\such\file.txt
$e.Exception.GetType().FullName       # System.Management.Automation.ItemNotFoundException

$Error.Count                          # 本次会话累计错误数
$Error.Clear()                        # 排查前先清零，免得被历史错误干扰

（以上注释里的输出是真机实测结果，不是示意。）

$Error 是个有上限的环形缓冲，默认保留最近 $MaximumErrorCount（256）条，老的自动挤掉。被 SilentlyContinue 静音的错误照样进 $Error，只有 Ignore 的不进 —— 这正是 SilentlyContinue 比 Ignore 更值得用的原因：至少还有据可查。

$ErrorArrayList会话内的错误记录，新在前事后回溯、交互式排查

🟡 $? 很脆

$? 只反映紧挨着的上一条命令，而且你一旦在中间插入任何一条命令（哪怕是 Write-Host），它就被刷新了。要判断就立刻判断，或者干脆改用 try/catch + -ErrorAction Stop。另外，对非终止型错误 $? 也会是 False，别把它当"脚本整体成功"的标志。

Get-Error：把最近一条错误的全部字段（含 InnerException 层层展开）漂亮地打印出来，排查复杂错误时比手动点属性快十倍，还能 Get-Error -Newest 5。

6.5 主动报错：throw 与自定义错误记录

前面都在讲怎么接别人的错。轮到你写函数时，问题反过来了：出问题该怎么通知调用者？

最简单的是 throw，它产生一个终止型错误：

throw "库存不足，还差 $shortage 件"                    # 字符串，包成 RuntimeException
throw [System.ArgumentException]::new('端口号必须在 1-65535 之间')   # 指定异常类型，PS 5.0+
throw $errorRecord                                    # 抛一个现成的 ErrorRecord
throw                                                 # 只能写在 catch 里：原样重抛

throw 还是 Write-Error？

场景该用理由
批量处理中，单条失败不该拖累其他条目Write-Error产生非终止型错误，把"停不停"的决定权交给调用者的 -ErrorAction
前提条件不满足，继续跑毫无意义（配置缺失、连不上库）throw 或 $PSCmdlet.ThrowTerminatingError()硬停，避免带病运行造成更大破坏
参数不合法[Validate*] 特性让 PowerShell 在参数绑定阶段就拦下，错误信息标准、还能被 Tab 补全
只是"有点不对劲"，不影响结果Write-Warning3 号流，不污染错误流
希望调用者能精确判断错因带 -ErrorId / 自造 ErrorRecord给出稳定的 FullyQualifiedErrorId，比让人家匹配消息文本文明得多

在高级函数里（加了 [CmdletBinding()] 的函数），更专业的做法是用 $PSCmdlet 的两个方法。它们的好处是：错误位置指向调用你的那一行，而不是你函数内部的实现细节，用起来跟内置 cmdlet 一模一样。

function Import-UserList {
    [CmdletBinding()]
    param([Parameter(Mandatory)][string]$Path)

    if (-not (Test-Path -LiteralPath $Path)) {
        $ex  = [System.IO.FileNotFoundException]::new('找不到用户名单文件', $Path)
        $rec = [System.Management.Automation.ErrorRecord]::new(
                    $ex,
                    'UserListNotFound',                                        # errorId，会出现在 FullyQualifiedErrorId 里
                    [System.Management.Automation.ErrorCategory]::ObjectNotFound,
                    $Path)                                                     # targetObject
        $PSCmdlet.ThrowTerminatingError($rec)     # 致命：调用者必须处理
    }

    foreach ($line in Get-Content -LiteralPath $Path) {
        if ($line -notmatch '^\w+@\w+') {
            # 单行格式不对，报一条非终止错误，接着处理下一行
            Write-Error -Message "跳过非法行：$line" -Category InvalidData -TargetObject $line
            continue
        }
        [pscustomobject]@{ Email = $line.Trim() }
    }
}
让调用者说了算 仍适用

这个函数的设计体现了 PowerShell 的一贯哲学：能继续的用非终止型，让上层用 -ErrorAction 决定要不要停；只有真的没法继续时才终止。你的函数因此可以既用在"宁缺毋滥"的脚本里（-ErrorAction Stop），也用在"能捞多少算多少"的采集脚本里（-ErrorAction SilentlyContinue -ErrorVariable bad），一份代码两种用法。

Write-Host 到底做错了什么

Write-Host 大概是 PowerShell 世界里被骂得最多的一个命令，连 PowerShell 之父都公开表示过它几乎总是错的选择。为什么？

在 PowerShell 5.0 之前，Write-Host 直接把字符画到宿主屏幕上，不经过任何一条流。后果是：不能重定向、不能捕获、不能静音、不能进管道。一个函数只要用 Write-Host 输出结果，它就永远只能"给人看"，别的脚本没法复用 —— 你把数据变成了像素。

function Get-Total {
    Write-Host "开始计算..."     # 屏幕上有，但拿不回来
    42                           # 这才是真正的返回值（1 号流）
}

$sum = Get-Total                 # $sum 得到 42；"开始计算..." 照样打在屏幕上，还静音不了
$log = Get-Total 6>&1            # PS 5.0 起可以这样捞：$log 里是 InformationRecord + 42

PowerShell 5.0 做了一次补救：Write-Host 改为写入 6 号信息流，因此可以被 6> 重定向、被 -InformationVariable 收集（实测捕获到的对象类型是 System.Management.Automation.InformationRecord）。罪减一等，但它仍然强制把 InformationAction 设为 Continue，所以照样静音不掉，也依然不进管道。

用 Write-Host 返回数据 禁用

函数里的"结果"绝不能靠 Write-Host 输出。它不进管道、不能赋值、不能 ConvertTo-Json、不能 Export-Csv，等于把可复用的对象砸成了一句话。

Write-Host 唯一站得住脚的用途 仍适用

写给人看、且明确不打算被复用的交互式脚本界面：菜单、彩色横幅、安装向导的进度提示。这种场景下 Write-Host -ForegroundColor 是正当的、也是最方便的。判断标准很简单：这行字如果被静音了，脚本功能会不会受影响？不会 —— 那用它没问题。

实测：Windows PowerShell 5.1 中加 -Debug 会把 $DebugPreference 设为 Inquire，于是每一条 Write-Debug 都会停下来弹"继续/挂起/中止"，很多人因此以为 -Debug 坏了。（对照：-Verbose 设的是 Continue，直接打印。）想要"只打印不追问"，在函数体第一行加上：

6.8 性能要点：别再用 += 拼数组

脚本慢，十有八九不是 PowerShell 慢，是写法慢。而所有写法里，最贵的一个是 $array += $item。

下面是本机实测（Windows PowerShell 5.1，循环 20 000 次，累积同样的 20 000 个元素）：

写法耗时相对倍数
$a = @(); for (...) { $a += $i }5 819 ms364×
$l = [List[int]]::new(); $l.Add($i)22.6 ms1.4×
$c = foreach ($i in 0..19999) { $i }16.0 ms1×

差了三百多倍。而且这个差距随规模平方增长：元素翻倍，+= 的耗时翻四倍。

为什么？ PowerShell 的数组是 .NET 的定长数组，长度一旦确定就改不了。所以 $a += $i 根本不是"追加"，而是：申请一个长度 n+1 的新数组 → 把旧的 n 个元素逐个复制过去 → 把新元素放最后 → 丢弃旧数组等垃圾回收。追加 n 个元素，总复制次数约为 n²/2 —— 两万个就是两亿次复制，外加两万个待回收的废弃数组。

打个比方：这就像你每买一本新书，就换一个刚好大一格的新书架，然后把原来的书一本本搬过去，旧书架扔掉。搬到第两万本时，你光搬书就搬了两亿次。

三种正确写法

# 写法一（首选）：直接捕获整个循环／管道的输出
$result = foreach ($item in $items) {
    if ($item.Size -gt 1MB) { $item }        # 每个"落地"的对象自动汇集
}

# 写法二：需要边加边删改时，用泛型 List
$list = [System.Collections.Generic.List[object]]::new()
foreach ($item in $items) { $list.Add($item) }
$list.Remove($x)                                  # 定长数组做不到的事

# 写法三：流式处理，边算边往下游送，内存占用恒定
Get-ChildItem D:\logs -Recurse -File |
    Where-Object Length -gt 10MB |
    Export-Csv D:\big.csv -NoTypeInformation

字符串拼接：同一个坑

字符串在 .NET 里是不可变的，$s += "..." 每次都新建一个更长的字符串再复制。实测拼 20 000 行：

写法耗时
$s += "line$i`n"1 113 ms
[System.Text.StringBuilder] + .AppendLine()24.9 ms
少量拼接：$lines -join "`n"几乎瞬间，且代码最短

过滤：管道 vs 语句

实测 20 万个整数取 7 的倍数：

写法耗时什么时候用它
$data | Where-Object { $_ % 7 -eq 0 }721 ms可读性最好、支持流式与远程管道；数据量不大时首选
$data.Where({ $_ % 7 -eq 0 })195 ms数据已在内存中，想快又想保持函数式风格（PS 4.0+）
foreach ($x in $data) { if (...) { $x } }66 ms百万级循环、性能敏感的内层
🟢 别为了快牺牲可读性

上面三者差 11 倍，听起来吓人，但绝对值是 0.7 秒 vs 0.07 秒 —— 处理几百条数据时你根本感觉不到。只在真正的热点循环里换写法。而 += 不一样：它是算法复杂度问题，任何规模下都应该避免，这不叫过早优化，叫别写错。

$ProgressPreference = 'SilentlyContinue'：在 Windows PowerShell 里，Invoke-WebRequest / Invoke-RestMethod 下载大文件时的进度条渲染会拖慢好几倍，关掉它是最著名的一行提速。

1. 带指数退避的重试

网络、数据库、云 API 都会偶发抖动。盲目重试不如退避重试。

function Invoke-WithRetry {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory)][scriptblock]$Action,
        [int]$MaxAttempts = 4,
        [int]$BaseDelayMs = 500
    )

    for ($attempt = 1; $attempt -le $MaxAttempts; $attempt++) {
        try {
            return & $Action                      # 成功就直接返回，不再重试
        }
        catch {
            if ($attempt -eq $MaxAttempts) { throw }   # 最后一次失败：原样上抛
            $delay = $BaseDelayMs * [math]::Pow(2, $attempt - 1)
            Write-Warning "第 $attempt 次失败（$($_.Exception.Message)），$delay ms 后重试"
            Start-Sleep -Milliseconds $delay
        }
    }
}

Invoke-WithRetry { Invoke-RestMethod 'https://api.example.com/v1/status' -ErrorAction Stop }

2. 统一日志函数

function Write-Log {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory)][string]$Message,
        [ValidateSet('INFO','WARN','ERROR')][string]$Level = 'INFO',
        [string]$Path = "$PSScriptRoot\run.log"
    )

    $line = '{0:yyyy-MM-dd HH:mm:ss} [{1,-5}] {2}' -f (Get-Date), $Level, $Message
    Add-Content -LiteralPath $Path -Value $line -Encoding utf8

    # 同时按级别送到对应的流，让调用者能用 -WarningAction 之类统一控制
    switch ($Level) {
        'ERROR'   { Write-Error   $Message }
        'WARN'    { Write-Warning $Message }
        default { Write-Verbose $line }
    }
}

function Invoke-Native {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory)][string]$FilePath,
        [string[]]$ArgumentList = @(),
        [int[]]$SuccessExitCodes = @(0)          # robocopy 之类可以传 @(0,1,2,3)

    $output
}

8. 一个正式脚本的骨架

#requires -Version 5.1
[CmdletBinding()]
param(
    [Parameter(Mandatory)][string]$InputPath,
    [string]$LogPath = "$PSScriptRoot\run.log"
)

Set-StrictMode -Version Latest        # 拼错的变量名立刻报错，而不是悄悄变 $null
$ErrorActionPreference = 'Stop'       # 入口脚本：宁可停，也不要带病跑完

try {
    Write-Verbose "开始处理 $InputPath"

    # ...... 你的业务逻辑 ......

    Write-Verbose '全部完成'
    exit 0                            # 明确的成功退出码，方便被计划任务/CI 判断
}
catch {
    "[$(Get-Date -Format s)] FATAL $($_.Exception.Message)" |
        Add-Content -LiteralPath $LogPath -Encoding utf8
    Write-Error $_
    exit 1                            # 非零退出码 = 失败，上游才知道要报警
}
finally {
    Write-Verbose '清理完成'          # 即使上面 exit 了，这里也会先执行
}
🟢 注意 $ErrorActionPreference 的两副面孔

本章前面把"脚本顶部一刀切"标成了禁用，这里却在骨架里写 $ErrorActionPreference = 'Stop' —— 不矛盾。被禁的是 SilentlyContinue（把错误藏起来），而 Stop 是把错误放大：宁可当场停在第一个问题上，也不要带着半截错误状态跑完全程、留下一个更难收拾的现场。入口脚本用 Stop，可复用的函数库则老老实实逐条写 -ErrorAction Stop，别去改调用者的环境。

凡是写在 try 里的 cmdlet，都加了 -ErrorAction Stop（或函数内设了 $ErrorActionPreference='Stop'）否则非终止型错误会从 try/catch 底下溜走
没有裸奔的 $ErrorActionPreference = 'SilentlyContinue'它会连 throw 一起吞掉，是最难查的一类 bug
用了 -ErrorVariable 收集批量失败项，跑完统一汇报比"跑到一半停住"和"啥也不说"都有用
判断错误类型时用 FullyQualifiedErrorId 或异常类型，而不是匹配消息文本消息会随系统语言变化，中文系统上你的 -match 'not found' 会失效
调外部 exe 之后检查了 $LASTEXITCODEPowerShell 不会替它报错
数据走 1 号流，说明文字走 Verbose／Warning／Information函数才能既给人看又给脚本用
全文搜一遍 Write-Host，确认每一处都是"纯给人看的界面"其余的都该换流
没有 += 拼数组或拼字符串O(n²)，数据一多就卡死
