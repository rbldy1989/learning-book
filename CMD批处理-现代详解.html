第 1 章认识 CMD：它是什么，不是什么

先看三个真实的麻烦

你几乎不会主动选择 CMD。你是被推到它面前的：

第一，你写好了 deploy.ps1，交给同事，同事双击一下——记事本弹出来了。你告诉他右键"使用 PowerShell 运行"，他照做，屏幕上闪过一行红字：此系统上禁止运行脚本。

第二，服务器上的任务计划里躺着一个 D:\ops\nightly.bat，最近三天"上次运行结果"是 0x1。没人知道这个 1 是谁返回的，也没人知道它是不是真的失败了。

第三，你接手的项目里有个 build.bat，第一行写着 @echo off，第二十行写着 for %%i in (*.obj) do ...。你把这行原样粘到命令行窗口里想调试，得到一句"此时不应有 %%i"。

这三件事的答案都在本章。它们看起来是三个孤立的怪癖，其实指向同一件事：CMD 是一个有四十年历史包袱的命令解释器，它的每一处别扭都有来历。搞清楚来历，你就不用死记硬背了。

现代提示：本书的立场

今天写新的自动化逻辑，默认选 PowerShell。CMD 的主要价值在于维护存量脚本、当"到处都能跑"的启动器，以及在没有 PowerShell 的环境里救急。这一章先把边界划清楚，后面各章再教你把存量脚本改对、改稳。

从 COMMAND.COM 到 cmd.exe

1981 年，MS-DOS 随 IBM PC 出货，它的命令解释器叫 COMMAND.COM。它做三件事：显示提示符、执行内部命令（DIR、COPY、SET）、执行外部程序。为了让用户不用反复敲同一串命令，它顺手支持了一种"把命令按行写进文件里一次跑完"的机制——批处理，文件扩展名 .BAT。%1、GOTO、IF ERRORLEVEL 这些语法就是那时候定下的。

1993 年 Windows NT 3.1 发布。NT 是完全重写的 32 位操作系统，跟 DOS 没有代码上的血缘关系。它需要一个命令解释器，微软给了它 cmd.exe——一个标准的 Win32 控制台程序（这个名字更早出现在 OS/2 上，NT 与 OS/2 有一段共同的开发史）。

cmd.exe 的设计目标写在脸上：让 DOS 时代的 .bat 文件继续能跑。所以它照抄了 COMMAND.COM 的全部语法怪癖，然后在上面加了一层增强，即"命令扩展"（Command Extensions，默认开启）：setlocal/endlocal、call :标签、for /f、%~dp0 这类参数修饰符、延迟展开——都是 NT 时代的新东西。

时间事件今天还留下的痕迹
1981MS-DOS 的 COMMAND.COM，批处理与 .BAT 诞生%1 参数、GOTO、IF ERRORLEVEL N 的"大于等于"语义
1987OS/2 上出现 CMD.EXE名字与部分设计思路
1993Windows NT 3.1 内置 cmd.exe（32 位 Win32 程序）今天你用的就是它的直系后代
1995—2000Windows 9x 仍以 COMMAND.COM 为主壳；NT 两者并存.bat 与 .cmd 分家的根源
2000 前后NT 加入命令扩展、延迟展开setlocal、for /f、%~dp0、!VAR!
2006PowerShell 1.0 发布，微软的战略重心转移CMD 从此基本只修 bug，不加新特性
2016 起WSL、Windows Terminal、PowerShell 7 陆续到位CMD 退居"兼容层"

顺带说一句：64 位 Windows 上已经没有 16 位子系统（NTVDM），真正的 command.com 在你的机器上根本不存在了。你今天见到的一切"DOS 命令"，跑的都是 cmd.exe。

设计动机：兼容性压倒一切

批处理语法里所有让你恼火的地方——百分号要翻倍、if errorlevel 2 其实是"大于等于 2"、变量在括号里不按你想的展开——都不是设计者笨，而是他们不能推翻已经在几百万台机器上跑着的旧脚本。CMD 是一件被兼容性焊死的工具，这既是它的原罪，也是它三十年不变、你今天还能依赖它的原因。

它不是什么：三个常见误解

误解一：cmd 就是 DOS。不是。cmd.exe 是一个普通的 Win32 程序，它能用长文件名、能访问超过 2GB 的文件、能读 NTFS 权限、能走 UNC 路径（\\server\share）。DOS 是一个 1981 年的操作系统，它在你的机器上已经不存在了。把 CMD 叫作"DOS 窗口"，就像把电动车叫"马车"。

误解二：cmd 就是那个黑窗口。不是。黑窗口是终端（conhost.exe 或 Windows Terminal），负责把字符画到屏幕上、把你的按键送进去。cmd.exe 是跑在窗口里的壳，负责理解你敲的那行字。同一个窗口里可以换成 PowerShell 或 bash，窗口没变，壳变了。

误解三：批处理是一门编程语言。它更像一门宏语言。它没有数据类型（一切都是字符串）、没有函数返回值（只有退出码）、没有异常（只有 if errorlevel）、没有数组（只有变量名拼接的土办法）。它被设计出来的目的是把一串外部程序按顺序串起来，不是写业务逻辑。你越把它当编程语言用，它越会用离奇的方式惩罚你。

打个比方：CMD 是老楼里的配电箱。外壳掉漆、标签是手写的、接线方式不合今天的规范。但整栋楼的电闸都还接在上面，你不能把它拆了，只能学会看懂它。

你常听到的说法实际指的是准确叫法
DOS 窗口 / DOS 命令cmd.exe 及其内部命令命令提示符、CMD
黑窗口终端程序conhost.exe / Windows Terminal
控制台视语境，通常指终端说清是"终端"还是"壳"
批处理语言cmd.exe 解析的脚本语法批处理（batch）
PowerShell 窗口跑着 powershell.exe 的终端PowerShell 会话

今天仍然非 CMD 不可的场景

如果 PowerShell 各方面都更好，为什么 CMD 还没死？因为下面这些位置，它有别人替代不了的位置。

场景为什么绕不开 CMD你该怎么做
存量构建脚本工具链自己发的就是批处理：vcvarsall.bat、gradlew.bat、npm.cmd、activate.bat就地维护，别顺手重写；它们改一行就可能连累整条流水线
注册表启动项、服务、安装程序自定义动作这些位置只接受"一条命令行"，没有解释器可选用一个 .cmd 当入口，内部再转发

双击即跑的小工具.ps1 双击默认打开记事本，还受执行策略约束；.bat 双击就执行写成 .cmd 启动器，逻辑放别处
最小化环境WinPE、恢复环境、Nano Server 容器里可能根本没有 PowerShell救急脚本只用 CMD 内部命令

第四条值得多说一句。.bat/.cmd "双击就跑、不受执行策略限制"是它的最大优势，也正好是它最大的安全风险——PowerShell 的执行策略本来就是为了拦住"用户被骗着双击了一个脚本"，而批处理没有这道门。

禁用：双击来路不明的 .bat / .cmd

双击一个批处理文件，等于同意它以你当前的用户权限做任何事——删文件、改注册表、下载并运行别的程序，全都不会有二次确认。收到的、下载的、别人发的批处理文件，先用记事本（或 type 文件名）看完内容再决定。这条对你自己适用，也请写进给同事的说明里。

.bat 与 .cmd：一个扩展名的实际差别

先说结论：对 cmd.exe 来说，两者的语法完全一样，同一份内容存成哪个名字都能跑。差别只有一处有文档记载，但足够坑人。

受"命令扩展"影响的一组命令——ASSOC、DPATH、FTYPE、PATH、PROMPT、SET、APPEND——在 .cmd 文件里执行成功时会把 ERRORLEVEL 清成 0；在 .bat 文件里则不动 ERRORLEVEL。自己验证一下：

@echo off
:: errlevel-test —— 分别存成 .bat 和 .cmd 各跑一次
cmd /c exit 7
set MARK=1
echo ERRORLEVEL = %ERRORLEVEL%
存成的文件名输出原因
errlevel-test.batERRORLEVEL = 7set 成功执行，但不碰 ERRORLEVEL
errlevel-test.cmdERRORLEVEL = 0set 成功执行，顺手把 ERRORLEVEL 清零

这意味着：如果你在一个 .cmd 脚本里"先跑命令、再赋个变量、然后判断错误码"，错误码可能已经被那句 set 抹掉了。这是老脚本里非常隐蔽的一类 bug。

维度.bat.cmd
语法完全相同（在 cmd.exe 下）
出身1981 年，DOS1993 年，Windows NT
谁能执行DOS / Win9x 的 COMMAND.COM，以及 NT 的 cmd.exe只有 NT 系的 cmd.exe
上述命令成功后ERRORLEVEL 保持不变ERRORLEVEL 被清 0
PATHEXT 默认优先级更高（.BAT 排在 .CMD 前）更低

PATHEXT 那一行的现实后果：如果同一个目录下同时有 tool.bat 和 tool.cmd，你敲 tool 跑的是 .bat。默认顺序是：

PATHEXT=.COM;.EXE;.BAT;.CMD;.VBS;.VBE;.JS;.JSE;.WSF;.WSH;.MSC
已过时：靠扩展名差异写逻辑

见过有人利用".cmd 会清零"来"重置错误状态"。别这么写——换个扩展名行为就变，读代码的人看不出来。要重置状态就显式写 cmd /c exit 0；要传递结果就显式写 exit /b N。现代提示 新写的脚本统一用 .cmd（它是 NT 时代的原生格式），只有当外部工具或文档明确要求 .bat 时才用 .bat。同一个目录里永远不要放同名的两份。

第一个脚本：@echo off、echo、pause

用记事本或任何编辑器新建 hello.cmd：

@echo off
:: hello.cmd —— 第一个批处理脚本
echo 你好，批处理。
echo 当前工作目录：%CD%
echo 脚本自己所在：%~dp0
pause

双击它，会弹出一个窗口，打印三行，然后停在"请按任意键继续. . ."。下面逐个拆开。

echo 的三重身份

echo 在批处理里身兼三职，这是初学者最容易懵的地方：

写法作用说明
echo 文本输出文本行尾的空格也会被输出，别在行尾留空格
echo（单独一个词）显示当前回显状态输出 ECHO 处于打开状态。——不是空行
echo off / echo on关闭 / 打开命令回显这是个开关，不是输出
echo.输出一个空行点号必须紧贴，中间不能有空格
echo(输出一个空行最稳妥的写法，对特殊字符最不挑剔

echo 文本 >nul丢弃输出只想要副作用或退出码时用

@ 和 @echo off 到底关掉了什么

批处理的默认行为是"回显"：执行每一行之前，先把这一行原样打印到屏幕上。这是 DOS 时代的设计——批处理本质上是"替你敲键盘"，把敲的内容显示出来，你才看得懂它在做什么。

但这对成品脚本是噪音。echo off 关掉它。问题是，echo off 这一行自己还是会先被回显出来。所以要在前面加 @——@ 是行前缀，作用是"抑制这一行自身的回显"，只对当前这一行有效。

@echo off = 关掉后续所有行的回显 + 连我这一行也别显示。看看不加是什么样：

:: noisy.cmd —— 什么都不关
echo 开始
echo 结束

在窗口里运行它，你看到的是：

D:\lab>echo 开始
开始

D:\lab>echo 结束
结束
仍适用：调试时把它关掉

脚本出问题时，把第一行的 @echo off 临时注释掉（前面加 rem），你就能逐行看到 cmd 实际执行的是什么——尤其是变量展开之后的样子。这是批处理最有效的调试手段，比加一堆 echo 打印管用。

注释：rem 与 ::

rem 是正式的注释命令（remark 的缩写，DOS 时代就有）。:: 其实是一个"永远不会被跳转到的畸形标签"，被大家当注释用，因为它比 rem 快一点也短一点。

写法能用的位置注意
rem 说明文字任何位置，包括 ( ) 块内最安全 仍适用
:: 说明文字只能独占一行，且行首写在 ( ) 块里会报错 已过时
命令 :: 注释不存在这种写法:: 会被当成命令参数的一部分

pause：给"双击场景"用的

pause 打印一行提示并等待按键。它存在的唯一理由是：双击运行时，脚本一结束窗口就关闭，你根本来不及看输出。

禁用：无人值守脚本里留 pause

任务计划、CI、服务里跑的脚本绝对不能有 pause——没人按键，它会永远挂在那里，任务状态一直显示"正在运行"，还可能挡住下一次调度。同样的道理也适用于任何会弹窗、要交互的命令。写脚本时想清楚：它是给人双击的，还是给机器调度的。

运行方式与它们的区别

运行方式写法结束之后
资源管理器双击—窗口立刻关闭（所以才需要 pause）
在已有窗口里跑hello.cmd留在当前窗口；脚本改的环境变量会残留（除非用了 setlocal）
新进程，跑完退出cmd /c hello.cmd窗口关闭，退出码传给调用者
新进程，跑完保留cmd /k hello.cmd窗口留着，方便看报错
在父脚本里调用并返回call hello.cmd子脚本结束后继续执行父脚本剩余的行
在父脚本里直接写文件名hello.cmd控制权一去不回，父脚本剩下的行不会执行

最后那两行的差别是批处理的经典陷阱：在脚本里调用另一个脚本，忘了写 call，后面的代码就被静默跳过了，没有任何报错。

仍适用：两个必踩的坑，提前躲开

工作目录不等于脚本目录。双击时两者通常一致，但通过快捷方式、任务计划、或者"以管理员身份运行"启动时，工作目录可能是 C:\Windows\System32。脚本要访问自己旁边的文件，就用 %~dp0（脚本所在目录，带反斜杠结尾），或在开头写一句 cd /d "%~dp0"。
文件编码。批处理文件存成"UTF-8 带 BOM"时，那三个 BOM 字节会被当成第一行命令的一部分，你会看到 '∩╗┐@echo' 不是内部或外部命令。中文内容存成 ANSI（GBK）最省事；一定要用 UTF-8 就存成无 BOM，并在脚本开头加 chcp 65001 >nul。

命令行与批处理不是同一套规则

回到开头的第三个麻烦：同一行字，在提示符下敲和写进 .bat 里，行为不一样。这不是玄学，是解析层次的差别。

关键机制：批处理文件的每一行在执行前，会先经过一遍百分号展开。这一遍会把 %% 折叠成单个 %，把 %VAR% 换成变量值。所以你写 %%i，展开之后 for 命令真正收到的是 %i——正合它的胃口。而在命令行上没有这一层预处理，你直接写 %i 就行。

记忆法：写进文件里，百分号翻倍。

命令行上这样写：

D:\lab>for %i in (*.log) do @echo 找到 %i

写进文件里就得这样：

@echo off
for %%i in (*.log) do echo 找到 %%i

退出码与 ERRORLEVEL

每个进程结束时都会返回一个整数给操作系统。0 表示成功，非 0 表示某种失败——这个约定 DOS 和 Unix 是一致的，也是所有自动化系统（任务计划、CI、监控）判断"这次跑得怎么样"的唯一依据。

cmd 把上一个命令的退出码放进伪变量 ERRORLEVEL。说它是"伪变量"，是因为它并不真的存在于环境块里：只要没有同名的真实变量，cmd 就在你读 %ERRORLEVEL% 时动态给出当前值。

第 2 章变量、参数与展开机制

上一章你已经能让脚本跑起来了。这一章要解决的是另一件事：怎么让脚本记住东西、接收东西、算点东西。听上去平淡无奇，但 CMD 在这里埋了它最著名的一颗雷——变量到底在什么时候被替换。九成以上的「我的批处理明明写对了却输出 0」都出自这一点。我们会先把 set 讲扎实，再一路推进到延迟展开，并且用图把展开时机彻底钉死。

set：批处理里唯一的变量声明

先看一段让无数人抓狂的代码。你想给变量赋值，于是很自然地写成这样：

@echo off
set name = 张三
echo [%name%]

运行结果是 []——空的。为什么？因为 set 不像其他语言那样「智能地忽略空格」。它把等号左边的一切当作变量名，把等号右边的一切当作值。所以你实际定义的变量叫 name （末尾带一个空格），值是 张三（开头带一个空格）。而 %name% 找的是没有空格的 name，当然找不到。

正确的写法有两种，第二种是你以后应该一直用的：

@echo off
set name=张三
echo [%name%]          rem 输出 [张三]

set "name=张三"
echo [%name%]          rem 同样输出 [张三]，但这种写法更安全

set "name=值" 里的引号只起定界作用，不会进入变量的值。它带来两个好处：一是把值的边界写死，末尾多打的空格不会混进去；二是值里出现 & | > < ^ 这些特殊字符时，引号能把它们保护住，不至于被当成命令分隔符或重定向。

经典事故：赋值后面接了别的命令

set VAR=abc & echo done 会把 VAR 赋成 abc （注意尾随空格），后面拿它拼路径就会变成 abc \file.txt，找不到文件还查不出原因。写成 set "VAR=abc" & echo done 就没事了。

几条需要记住的性质：变量名不区分大小写（%path% 和 %PATH% 是同一个）；变量没有类型，一切都是字符串，set "n=5" 存的是字符 5 而不是数字；单个变量的长度上限约 8191 字符，整个环境块也有上限，别拿变量当数组塞几万行文本。

现代提示

PowerShell 里 $name = '张三' 有真正的类型系统，空格随便打，还有数组、哈希表和对象。如果你的脚本已经开始用变量拼 JSON、算浮点、存列表，那说明它早就该是 PowerShell 脚本了。CMD 变量的定位是「给命令行拼参数的临时便签」，不是数据结构。

%VAR% 展开：一次性文本替换

这一节是全章的地基。请先接受一个反直觉的事实：%VAR% 不是「读取变量」，而是「在执行之前，把这一整行里的 %VAR% 用文本替换掉」。

它更像 C 语言的 #define 宏，或者你在编辑器里按下的「全部替换」，而不是 Python 里的读变量。证据很直白：

@echo off
set "cmd=echo Hello"
%cmd% world
rem 屏幕输出 Hello world
rem 因为替换之后，这一行真正变成了：echo Hello world

「替换为空」正是老式批处理最常见的崩溃来源：

@echo off

既然 % 是定界符，要输出一个字面百分号就得转义。规则很简单但有个不对称之处：

这个不对称是 CMD 的历史包袱：批处理文件多了一层「先把 %% 折叠成 %」的处理，所以同一段代码从命令行复制进 .bat 往往需要把 % 全部加倍。调试 for 循环时被这个坑到的人不计其数。

set /a：整数算术与它的边界

CMD 只有一个计算器，就是 set /a。而且它只会算32 位有符号整数——没有浮点，没有大数，除法直接截断。

@echo off
set /a a=7/2
set /a b=7%%2
set /a c=(1+2)*3
set /a "d=1<<10"
echo %a% %b% %c% %d%
rem 输出：3 1 9 1024

三个要点藏在这四行里。第一，7/2 得 3 而不是 3.5，除法向零截断。第二，取模运算符 % 在批处理文件里必须写成 %%，否则会被当成变量定界符。第三，1<<10 里的 < 是重定向符，必须用引号把整个表达式包起来，否则 CMD 会试图从一个叫 < 的文件读输入。

养成习惯

永远写 set /a "表达式"，把表达式整体加引号。凡是含 & | ^ < > 的算式，不加引号必错；加了引号则一律安全，没有副作用。

三个必须知道的行为

表达式里的变量不用写百分号。 set /a "total=total+price" 是合法的，set /a 会自己去查变量。未定义的变量在算式里当 0 处理，所以累加器不初始化也能跑——但这也意味着变量名打错时它会静默算成 0，不报错。

数字有进制约定，而且是个大坑。 0x 开头是十六进制，以 0 开头是八进制。这意味着从时间字符串里切出来的 08 和 09 会直接报错，因为八进制没有数字 8 和 9：

set "h=08"
set /a n=%h%
rem 报错：无效数字。数字常量应为十进制 (17)、十六进制 (0x11) 或八进制 (021)。

set /a n=1%h%-100
rem 得到 8 —— 先拼成 108 再减 100，是处理前导零的惯用手法

在批处理文件里 set /a 不回显结果，在命令行窗口里则会直接把结果打印出来。所以 set /a 2+2 在窗口里是个顺手的计算器，写进脚本里则悄无声息。

不要用 set /a 算钱和平均值

没有浮点意味着 set /a "avg=sum/n" 会丢掉小数部分，金额、百分比、耗时统计全都会失真。要保留两位小数只能靠「先乘 100 再除」的定点小技巧，可读性极差。真要算数，把这一步交出去：for /f %%v in ('powershell -NoProfile -Command "[math]::Round(7/2,2)"') do set "avg=%%v"。

set /p：读一行输入，也能读文件

set /p 是 CMD 里唯一的交互输入手段。它的语法和 set 一致，只是等号右边的内容变成了提示语，用户敲下的一整行才是变量的值：

@echo off
set "ans="
set /p "ans=确认部署到生产环境? (y/N) "
if /i "%ans%"=="y" (
    echo 开始部署...
) else (
    echo 已取消
)

注意第三行那个看似多余的 set "ans="。它是必须的，因为 set /p 在用户直接敲回车时不会清空变量，而是保持原值不变。如果变量之前有值，用户什么都不输入就等于默认接受了旧值——这在循环里询问会造成非常隐蔽的错误。先清空，等于把「直接回车」定义为「留空」。

它还是个读文件的工具

set /p 的输入源可以重定向，于是它顺便成了「读取文件第一行」的最短写法：

@echo off
set "ver="
set /p "ver=" < version.txt
echo 当前版本：%ver%

反过来，把 set /p 的输入接到空设备上，它就变成了唯一的「不换行输出」手段——因为提示语已经打印出去了，而输入立刻遇到 EOF 结束：

<nul set /p "=正在处理"
for /l %%i in (1,1,3) do <nul set /p "=."
echo  完成
rem 屏幕上是一行：正在处理... 完成

安全警告：不要把输入直接拼进命令

set /p "f=文件名: " 之后写 del %f%，用户输入 a.txt & del *.* 就会真的执行两条命令。这是货真价实的命令注入。最低限度要写成 del "%f%"，更稳妥的做法是先校验：if not exist "%f%" (echo 文件不存在 & exit /b 1)。任何来自外部的字符串，进命令行之前都要加引号。

现代提示

需要真正的交互（默认值、密码遮蔽、菜单选择、输入校验）时，PowerShell 的 Read-Host、Read-Host -AsSecureString 和 $Host.UI.PromptForChoice 才是正路。set /p 的定位是「一个 y/N 确认」，超出这个范围就该换工具了。

setlocal / endlocal：作用域与生命周期

默认情况下，批处理里 set 的变量会污染当前 cmd 会话。双击运行时窗口一关就没了，你感觉不到；但当你在一个已经开着的命令行窗口里连续跑几个脚本，前一个脚本留下的 PATH、TEMP、count 就会莫名其妙地影响后一个。setlocal 就是为此存在的。

@echo off
setlocal
set "PATH=%~dp0bin;%PATH%"
set "BUILD_MODE=release"
call build.exe
endlocal
rem 出了这一行，PATH 和 BUILD_MODE 都恢复成进入脚本前的样子

打个比方：setlocal 相当于给整个环境拍了一张快照压进栈里，之后你怎么折腾都行；endlocal 把快照弹出来盖回去。脚本正常结束时 CMD 会自动补上所有未配对的 endlocal，所以「开头写 setlocal，结尾不写也行」——但显式写出来更清楚。

命令作用
setlocal保存当前环境变量、当前驱动器与目录，进入局部作用域
setlocal EnableDelayedExpansion同时开启延迟展开（见 2.8）
setlocal DisableDelayedExpansion同时关闭延迟展开，常用于临时处理含 ! 的文本
setlocal EnableExtensions确保命令扩展开启（for /f、%~dp0 等都依赖它）
endlocal丢弃本层所有改动，还原快照
冷知识：当前目录也在快照里

setlocal 保存的不只是环境变量，还包括当前驱动器和目录。也就是说脚本里 cd 到别处，一执行 endlocal 就自动跳回来了。这既是便利也是陷阱——如果你指望 cd 的效果延续到 endlocal 之后，那会落空。嵌套层数上限约 32 层，正常脚本远远用不到。

怎么让一个值「活着穿过」endlocal

这是 CMD 里最漂亮的一个惯用法，而且它正好复习了 2.2 的展开时机。endlocal 会抹掉局部变量，那子程序算出来的结果怎么传回去？答案是把两条命令写在同一行：

@echo off
setlocal
call :get_version result
echo 版本是 %result%
exit /b

:get_version
setlocal
set "v=1.2.3"
endlocal & set "%~1=%v%"
rem 整行先被替换成：endlocal & set "result=1.2.3"
rem 然后才逐条执行 —— 所以 endlocal 抹掉 v 已经无所谓了
exit /b

看懂了吗？%v% 和 %~1 在第 ② 步就被换成了字面文本，endlocal 在第 ④ 步才执行。等它执行的时候，值早就以文本形式写死在这一行里了。这个「先替换后执行」的特性在别处是坑，在这里成了救命稻草。

持久化环境变量

脚本里的 set 只影响当前进程及其子进程，父进程和其他窗口一无所知。要写进系统里长期生效，得用 setx：

命令范围当前窗口可见？提醒
set "V=1"当前 cmd 进程及子进程是窗口关闭即消失
setx V 1当前用户（写注册表）否，需新开窗口值长度截断到 1024 字符
setx V 1 /m整台机器否需管理员权限
绝对不要用 setx 改 PATH

setx PATH "%PATH%;C:\新目录" 有两重毁灭性问题：一是 setx 在 1024 字符处截断，会把你的 PATH 拦腰砍断；二是 %PATH% 展开的是「用户 PATH + 系统 PATH」拼接后的结果，写回去会把系统 PATH 复制进用户 PATH，从此两份重复且无法同步。修 PATH 请用「系统属性 → 环境变量」对话框，或者 PowerShell 的 [Environment]::SetEnvironmentVariable('Path', $v, 'User')。

命令行参数 %0~%9 与 shift

脚本要接收外部输入，最常见的方式不是 set /p，而是命令行参数。CMD 用 %0 到 %9 这十个位置来接收它们。

记号含义
%0脚本自身——注意是按调用时书写的形式，不一定是绝对路径
%1 ~ %9第 1 至第 9 个参数，引号会被一并带进来
%*全部参数的原始文本（不含 %0），不受 shift 影响
%~1去掉首尾引号的第 1 个参数，见 2.7
shift整体左移：%0←%1，%1←%2…
shift /2从第 2 位开始左移，%0 和 %1 保持不动

没有 %10。 你写 %10，CMD 读成「%1 后面跟一个字符 0」。想拿到第 10 个及以后的参数，只能用 shift 把它们挪进 %1 的位置。

参数是怎么被切开的

这里有个几乎没人预料到的坑：CMD 分割参数用的不只是空格。

分隔符示例调用切分结果
空格run.bat a b%1=a　%2=b
制表符run.bat a b%1=a　%2=b
逗号run.bat a,b%1=a　%2=b
分号run.bat a;b%1=a　%2=b
等号run.bat mode=fast%1=mode　%2=fast
引号包裹run.bat "a,b c"%1="a,b c"（含引号）

所以 myscript.bat name=张三 并不会给你一个 name=张三 的参数，而是两个参数。想传含这些字符的值，调用方必须加引号，脚本内部则用 %~1 把引号剥掉。

用 shift 遍历任意个参数

@echo off
setlocal
set "VERBOSE=0"
set "OUT="

:parse
if "%~1"=="" goto :run
if /i "%~1"=="-v"  (set "VERBOSE=1" & shift & goto :parse)
if /i "%~1"=="-o"  (set "OUT=%~2"  & shift & shift & goto :parse)
echo 未知参数：%~1
exit /b 1

:run
echo VERBOSE=%VERBOSE%  OUT=%OUT%

为什么这里非要用 goto 绕圈，而不是写个 for 循环？因为 shift 的效果在同一个括号块内看不到。整个块在进入时就已经把 %1 %2 全部替换成文本了，块里执行 shift 也改不了这些死文本。goto 会让 CMD 重新读取并重新解析，这才是 shift 生效的前提。这是本章展开时机主题的又一次现身。

子程序里的参数

call :sub 参数1 参数2 会给子程序一套全新的 %1 %2，主程序的参数在子程序里看不到。此时 %0 是标签名（如 :sub）而不是脚本名。子程序用 goto :eof 或 exit /b 返回，返回后主程序的 %1 自动恢复。要在子程序里用脚本路径，请在脚本开头就把 %~dp0 存进变量。

参数修饰符完整速查表

如果这一章只让你记住一节，就是这一节。参数修饰符是 CMD 里性价比最高的语法：一个 %~dp0 顶得上十行路径拼接代码。

它的形式是在百分号和数字之间插入 ~ 和若干字母，让 CMD 把参数当成路径来拆解。假设脚本位于 D:\tools\build\deploy.bat，那么 %0 可以这样被切开：

修饰符的适用范围

修饰符只能用在 %0~%9 和 for 循环变量（写作 %%~nxi）上，不能用于普通环境变量——%~dpMYVAR% 是无效语法。想对一个变量用修饰符，绕一圈即可：
for %%a in ("%MYVAR%") do echo %%~nxa

%~dp0 的正确用法

@echo off
setlocal
rem 开头就把脚本目录固化下来，后面怎么 cd 都不怕
set "HERE=%~dp0"

echo 脚本全路径：%~f0
echo 脚本目录　：%HERE%
echo 配置文件　："%HERE%config.ini"

rem 需要把工作目录切到脚本所在处时，用 pushd/popd 成对操作
pushd "%~dp0"
call tools\build.exe
popd

三个必须注意的细节。第一，%~dp0 末尾自带反斜杠，所以是 "%~dp0config.ini" 而不是 "%~dp0\config.ini"（后者会产生 D:\tools\\config.ini，多数情况能用但不干净）。第二，双击运行脚本时工作目录不一定是脚本目录，从计划任务或右键菜单启动时更是如此，所以任何相对路径都应该改写成 %~dp0 打头。第三，想得到不带尾反斜杠的目录，用这个小技巧：

for %%a in ("%~dp0.") do set "ROOT=%%~fa"
rem ROOT = D:\tools\build   （末尾的 . 被 ~f 规范化掉了）
UNC 路径的老限制

脚本放在网络共享 \\server\share\tools\ 上时，cd 命令不支持 UNC 路径，会报「CMD 不支持将 UNC 路径作为当前目录」。pushd "%~dp0" 可以救场——它会自动映射一个临时盘符，popd 时再解除。这也是应该优先用 pushd 而不是 cd 的现实理由。

现代提示

PowerShell 里 %~dp0 的对应物是 $PSScriptRoot（不带尾反斜杠），路径拆解则交给 Split-Path 和 [System.IO.Path]。但必须承认，%~dp0 这个记号的简洁程度至今没有对手——它是 CMD 少数几个设计得非常好的地方。

延迟展开 !VAR!：CMD 最大的坑

现在来到本章的高潮。下面这段代码几乎每个人都写过，也几乎每个人都被它坑过：

@echo off
set "count=0"
for %%f in (*.txt) do (
    set /a count+=1
    echo 已处理 %count% 个
)
echo 合计 %count% 个

假设目录下有 3 个 txt 文件，你期望看到 1、2、3、合计 3。实际输出是：

已处理 0 个
已处理 0 个
已处理 0 个
合计 3 个

循环里永远是 0，循环外反而是对的。这不是 bug，而是 2.2 那条规则的必然结果——只不过这次，「一条语句」指的是整个括号块。

打个比方：%VAR% 像是剧本印刷——开演前台词就印死在纸上了，演员照本宣科，中途导演改主意也没用；!VAR! 像是提词器——纸上只写着「看提词器」，念到那一句才抬头看当前显示的内容。

开启延迟展开

@echo off
setlocal enabledelayedexpansion
set "count=0"
for %%f in (*.txt) do (
    set /a count+=1
    echo 已处理 !count! 个：%%~nxf
)
echo 合计 %count% 个

注意最后一行仍然写的是 %count%——因为它是独立的一条语句，解析它的时候循环早就结束了，值已经正确。只有在「同一条语句 / 同一个括号块内既赋值又读取」时，才必须用 !VAR!。 除此之外 %VAR% 一切正常，不必到处改。

开启方式作用范围说明
setlocal enabledelayedexpansion到对应的 endlocal 或脚本结束脚本内的标准做法
setlocal disabledelayedexpansion同上临时关掉，用于处理含 ! 的文本
cmd /v:on /c "..."该 cmd 实例命令行窗口默认是关闭的

代价：感叹号从此变成保留字

延迟展开不是白送的。一旦开启，! 就成了定界符，普通文本里的感叹号会被静默吃掉：

@echo off
setlocal enabledelayedexpansion
set "msg=部署成功!"
echo !msg!
rem 输出：部署成功   ← 感叹号不见了

set "msg=部署成功^^!"
echo !msg!
rem 输出：部署成功!   ← 用 ^^! 写出字面感叹号
场景症状解法
字符串里有字面 !感叹号消失写成 ^^!
for /f 读到含 ! 的文件行内容被破坏，无法转义循环内 setlocal enabledelayedexpansion / endlocal 成对切换
set /p 用户输入含 !同上读取时先关闭延迟展开
路径含 !（少见但合法）路径被截断同上

处理外部文本（文件内容、用户输入、目录名）时，稳妥策略是默认关闭延迟展开，只在需要读取「刚改过的变量」的那一小段临时开启。这比一开头就 enabledelayedexpansion 然后到处补 ^^! 要省心得多。

什么时候必须用 !VAR!

情形用哪个原因
在 for / if 块内读取块内刚赋的值!VAR!%VAR% 在进块前已被冻结
用 & 串在同一行的多条命令间传值!VAR!整行一次性展开
变量值可能含 & | ^ >!VAR!延迟展开发生在语法解析之后，内容不会被二次解析，更安全
变量值含 !%VAR% 并关闭延迟展开! 会被当成定界符吞掉
子串 / 替换的下标来自另一个变量!VAR:~%i%,1!先展开 %i%，再由延迟展开整体求值
独立成行、值在别处早已确定%VAR%没必要，也更兼容
已过时的替代方案

延迟展开是 Windows 2000 才引入的。在那之前，人们用 call echo %%count%% 制造「二次展开」，或者把循环体拆成 call :sub 子程序来绕开。这两种写法在今天的脚本里仍能见到：前者每次都要启动一遍命令解析器，慢且对特殊字符极不友好；后者可读性尚可但啰嗦。除非你要兼容 Windows 9x（那就不必了），一律用 setlocal enabledelayedexpansion。

设计动机与现代提示

为什么微软不干脆把 %VAR% 改成执行时求值？因为兼容性。% 的宏式展开从 DOS 时代就是这样，无数脚本依赖「变量里存命令」这类技巧。改掉它等于让存量脚本集体失效，于是只能新造一套 !VAR! 语法、默认关闭、由脚本自己声明启用。这就是所有长寿系统的宿命——新特性只能加在旧特性旁边。
PowerShell 从零设计，$var 就是执行时求值，根本不存在这个问题。如果你的脚本已经出现三层嵌套加延迟展开，那是它在告诉你：该换语言了。

子串与替换：CMD 的字符串工具箱

CMD 没有字符串函数库，但 %VAR% 的展开语法里内置了两组操作：取子串和查找替换。它们能覆盖日常八成的字符串需求。

取子串 %VAR:~起点,长度%

起点从 0 开始数，负数表示从末尾倒着数。长度为负表示「留下的部分末尾要砍掉这么多字符」。

@echo off
set "s=2026-08-16"
echo %s:~0,4%      rem 2026      从第 0 位取 4 个
echo %s:~5,2%      rem 08        从第 5 位取 2 个
echo %s:~5%        rem 08-16     从第 5 位取到末尾
echo %s:~-2%       rem 16        末尾 2 个字符
echo %s:~0,-3%     rem 2026-08   砍掉末尾 3 个字符
写法含义
%VAR:~n%从第 n 个字符（0 起）取到末尾
%VAR:~n,len%从第 n 个字符起取 len 个
%VAR:~-n%末尾 n 个字符
%VAR:~0,-n%去掉末尾 n 个字符
%VAR:~n,-m%从第 n 个字符起，到倒数第 m 个字符之前

查找替换 %VAR:旧=新%

@echo off
set "s=2026-08-16"
echo %s:-=/%          rem 2026/08/16   把所有 - 换成 /
echo %s:-=%           rem 20260816     把所有 - 删掉

set "u=https://example.com/a/b"
echo %u:*//=%         rem example.com/a/b   删掉开头到第一个 // 为止
写法含义
%VAR:旧=新%把所有「旧」换成「新」，不区分大小写
%VAR:旧=%删除所有「旧」
%VAR:*旧=新%把「从字符串开头到第一个『旧』为止」这整段，替换成「新」
%VAR:*旧=%删除开头到第一个「旧」为止的全部内容

算字符串长度

既然没有 len()，就用「每次砍掉一个字符，数砍了几次」的笨办法。这段代码同时用到了子串、延迟展开和 goto 循环，是本章的一次综合练习：

@echo off
setlocal enabledelayedexpansion
set "s=Hello, CMD"
set /a n=0

:count
if defined s (
    set "s=!s:~1!"
    set /a n+=1
    goto :count
)
echo 长度 = %n%
rem 输出：长度 = 10

三个细节：if defined s 在执行时判断，所以每轮 goto 后重新解析都能看到最新值；!s:~1! 必须用感叹号，因为它读的正是本块内刚改过的变量；示例字符串刻意不含感叹号——延迟展开开着的时候，set "s=Hello!" 里的感叹号会被吃掉，这正是 2.8 说的代价。

现代提示

这些字符串技巧的天花板很低：没有正则、没有大小写敏感替换、不能按字符遍历、对 Unicode 支持取决于代码页。一旦需求超出「切个日期、补个零、换个斜杠」，直接 powershell -NoProfile -Command "..." 会让代码短十倍且不易出错。CMD 字符串操作的正确定位是：能一行解决的就用它，需要三行以上的就换工具。

第 3 章流程控制：if / for / goto

前两章里你写的每一行命令都会被执行，从上到下，一条不落。从这一章开始，脚本才真正变成"程序"：它会挑着执行，会重复执行，会跳来跳去。

CMD 的流程控制关键字只有三个：if、for、goto。没有 while，没有 switch，没有 try/catch，连一个像样的函数定义语法都没有。听上去寒酸，但这三样东西拼装起来几乎能表达任何逻辑——代价是每一个都背着三十多年的历史包袱，而且包袱都藏在语法的暗处。你写出来的第一个 if 十有八九会在带空格的变量上翻车，你写出来的第一个 for 循环十有八九会发现计数器永远是 0。

这一章就是把这些包袱一个个摊开给你看：先讲清楚它为什么会这样，再告诉你怎么绕过去。

关于本章的示例

本章所有代码片段和"实测输出"都在 Windows 11 的 cmd.exe 上真实跑过。cmd 默认开启命令扩展（Command Extensions），本章大量特性（goto :EOF、exit /b、if defined、for /F 的多数选项、%%~ 修饰符）都依赖它。如果你在某台机器上发现这些统统失效，先检查注册表里的 EnableExtensions，或在脚本开头写 setlocal EnableExtensions。

if 的本体：它比较的是字符串

先看一个几乎每个人都踩过的坑。你想判断用户名，写了这么三行：

@echo off
set "NAME=Zhang San"
if %NAME%==Zhang echo 找到了

运行结果不是"没找到"，而是脚本直接崩掉：

San==Zhang was unexpected at this time.

而且更糟的是，脚本到这里就中止了，后面的行一行都不会执行，%errorlevel% 变成 255。如果这是一个部署脚本，它会在半路上悄无声息地停下来。

为什么会这样

关键在于 cmd 处理一行命令的顺序：先做变量展开，再做语法解析。它不是把 %NAME% 当成一个"值"传给 if，而是把这四个字符原样替换成 Zhang San，得到一行新的文本：

if Zhang San==Zhang echo 找到了

然后才交给 if 去解析。if 按空格切参数，拿到第一个参数是 Zhang，接着期待看到 ==，结果看到的是 San==Zhang。语法不成立，报错退出。

打个比方：其它语言的 if 像一台会读值的机器，你递给它两个盒子，它比较盒子里的东西。cmd 的 if 更像一个模板引擎——它先把句子里的占位符换成文字，再从头到尾照字面读一遍。你往变量里塞了一个空格，就等于往句子中间插了一个断句符，整句话的结构就变了。

这不是 bug，是设计上的必然：cmd 的变量展开发生在命令行解析的最早阶段，对所有命令一视同仁，if 并没有被特殊照顾。

解法：两边都加引号

@echo off
set "NAME=Zhang San"

rem 正确写法：引号把带空格的值裹成一个参数
if "%NAME%"=="Zhang San" echo 找到了

rem 判断空值也必须加引号，否则展开成 if ==x，同样报语法错误
if "%NAME%"=="" echo 名字是空的

注意引号是"比较内容的一部分"，不是语法糖。"abc" 和 abc 在 if 眼里是两个不同的字符串，所以两边必须同时加引号，只加一边永远不相等。

写法含义说明
if "%A%"=="%B%"区分大小写的相等比较仍适用 默认就写这个
if /i "%A%"=="%B%"忽略大小写/i 必须紧跟在 if 后面
if not "%A%"=="%B%"不相等—
if /i not "%A%"=="%B%"忽略大小写的不相等唯一正确的顺序
if not /i "%A%"=="%B%"语法错误实测报 "A"=="a" was unexpected at this time. 并中止脚本
if "%A%" == "%B%"合法，等号两侧可以有空格能跑，但可读性差，不推荐
if %A%==%B%值不含空格时可用已过时 只要值可能来自外部输入就不安全
引号套引号的二次陷阱

如果变量的值本身已经带引号（最常见的来源是命令行参数，比如用户拖进来一个路径 "C:\Program Files\App"），你再套一层就变成 ""C:\Program Files\App""==...，比较必然失败。规矩是：从 %1 取值时先用 %~1 剥掉外层引号，再统一由你自己加引号。写成 set "ROOT=%~1"，后面全程用 "%ROOT%"。

现代提示

现代提示 PowerShell 里 -eq 是真正的运算符，两侧先求值再比较，变量里有空格不会改变语法结构：if ($name -eq 'Zhang San') { ... }；而且字符串比较默认忽略大小写（要区分用 -ceq），和 cmd 正好相反，迁移时留意。

数字比较：EQU / NEQ / GTR 家族

再看一个反直觉的例子：

if "10" GTR "9"  (echo 大) else (echo 不大)
rem 实测输出：不大

为什么 10 不大于 9？因为你加了引号。这六个比较运算符的规则是：只有当两侧都能被解析成数字时才做数值比较，否则退化成字符串比较。加了引号，两侧就成了 "10" 和 "9"——包含引号字符，不是数字——于是逐字符比较，" 相同，1 小于 9，判定为"不大于"。

这个"自动挡"是它最危险的地方：你以为在做算术，它可能已经偷偷换到了"比字符串"档，而且不给任何警告。

运算符含义等价数学符号
EQU等于=
NEQ不等于≠
LSS小于<
LEQ小于等于≤
GTR大于>
GEQ大于等于≥

前导零：八进制的幽灵

cmd 解析数字时沿用了 C 语言的字面量规则：0x 开头是十六进制，0 开头是八进制，其余是十进制。这在处理日期时间时会咬人，因为 %DATE% 和 %TIME% 切出来的月份、小时经常带前导零。

if 0x10 EQU 16 echo 相等   rem 成立：0x10 是十六进制 16
if 010  EQU 8  echo 相等   rem 成立：010 是八进制 8
if 08   EQU 8  echo 相等   rem 不成立！08 不是合法八进制

最后一行最阴险：08 里的 8 不是合法八进制数字，解析失败，于是整个比较静默退化成字符串比较——字符串 "08" 当然不等于 "8"。所以"八月"和"九月"会莫名其妙地判错，而一到十月就又对了。

标准解法是加一个 1 再减 100，把前导零挤掉：

set "MM=08"
set /a MM=1%MM% - 100
rem 1%MM% 得到 108（十进制，无前导零），减 100 得 8
if %MM% EQU 8 echo 八月     rem 实测输出：八月

字符串退化时的排序很怪

一旦退化成字符串比较，GTR/LSS 用的排序既不是 ASCII 码点，也不是你直觉里的顺序。实测：

if B GTR a   echo 成立    rem 成立（按 ASCII，B=66 < a=97，本该不成立）
if abc LSS ABC echo 成立  rem 成立：同一个字母，小写排在大写前面

也就是说它用的是一种"字典序 + 同字母小写在前"的排列（a < A < b < B），而 EQU 却是严格区分大小写的精确相等。两套规则不一致，非常容易写出自相矛盾的判断。

结论

已过时用 GTR/LSS 对非数字字符串排序。不直观、不可移植、和 EQU 的大小写规则还打架。要保证走数值比较这条路，先用 set /a 把两边规范成纯十进制整数，并且不要加引号——引号是数值比较的天敌。

rem 稳妥的数值比较模板
set /a LEFT=%~1, RIGHT=%~2
if %LEFT% GEQ %RIGHT% (echo 左边不小) else (echo 右边大)

三个探针：exist、defined、errorlevel

if 除了比较两个值，还内置了三种"探针"，用来问系统三个问题：文件在不在、变量有没有、上一条命令成没成。

if exist：路径存在吗

if exist "C:\logs\app.log"  echo 文件在
if not exist "C:\logs"      echo 目录不在
if exist "C:\logs\*.log"    echo 至少有一个 .log

exist 对文件和目录一视同仁，都算"存在"。想确认"这是一个目录而不是同名文件"，用结尾反斜杠或通配符两种老写法，实测都可靠：

if exist "%ROOT%\"  echo 这是目录
if exist "%ROOT%\*" echo 这也是判断目录的写法

引号规矩和上一节完全一样：路径带空格而不加引号，同样会把脚本炸掉。

if defined：变量存在吗

注意它后面跟的是变量名本身，不带百分号：

if defined PROXY     echo 配了代理：%PROXY%
if not defined LOGDIR set "LOGDIR=%TEMP%\logs"

为什么不直接写 if "%LOGDIR%"==""？因为在括号块里，%LOGDIR% 在块开始执行前就被冻结了（下一节详说），而 defined 后面是个裸名字，不参与展开，它在真正执行到那一行时才去查表。实测：

set "K="
for %%i in (1) do (
    set "K=刚设的值"
    if defined K (echo 看得见) else (echo 看不见)
)
rem 实测输出：看得见   —— 换成 if "%K%"=="" 就会判错

这是 defined 存在的真正理由：它是少数几个能穿透"块内变量冻结"的写法之一。

if errorlevel：它的意思是"大于等于"

这是全章最容易被误读的一句话。if errorlevel 1 不是"返回码等于 1"，而是"返回码 ≥ 1"。实测：

cmd /c exit 5
if errorlevel 3 echo 成立    rem 成立，因为 5 >= 3
if errorlevel 6 echo 成立    rem 不成立

这个设计来自 DOS 时代：那时候程序约定用"越大越严重"的返回码，所以"大于等于"恰好表达"至少出了这么严重的问题"。要判断"恰好等于 N"，老写法是夹逼：

if errorlevel 1 if not errorlevel 2 echo 返回码恰好是 1

更要命的是负数。有些程序（尤其是 .NET 和 PowerShell 脚本）会返回 -1：

cmd /c exit -1
echo %errorlevel%              rem 实测输出：-1
if errorlevel 1 echo 失败了    rem 实测：不成立！-1 < 1

也就是说，用 if errorlevel 1 当作"通用失败判断"，会静默漏掉所有返回负数的失败。

推荐写法

已过时 if errorlevel 1 作为通用的"出错了吗"判断。
仍适用 改用 if %errorlevel% NEQ 0（数值比较，负数照样抓得住），或者 if not "%errorlevel%"=="0"。只有当你确实要表达"严重程度至少是 N"时，if errorlevel N 才是对的工具。

探针语法判定内容要点
文件/目录if exist "路径"路径是否存在目录也算存在；路径\ 或 路径\* 可强制只认目录
变量if defined 名字变量是否已定义不带 %；能穿透括号块的变量冻结
返回码if errorlevel N返回码 ≥ N负数返回码判不出来，优先用 %errorlevel% NEQ 0

if else 与括号：换行在哪里断，是有规矩的

你会很自然地写出这样的代码：

if %N% GTR 0 (
    echo 正数
)
else (
    echo 非正数
)

实测输出是这样的：

正数
'else' is not recognized as an internal or external command,
operable program or batch file.
非正数

请仔细看：两个分支都执行了。这比直接报错还坏——脚本没有崩，返回码是 0，但逻辑已经彻底错了。原因是 cmd 一行一行读：读到第 3 行的 ) 时，if 语句已经完整结束了；第 4 行的 else 被当成一条新命令（找不到这个程序，报错），第 5 到 7 行的 ( echo 非正数 ) 又被当成一个独立的括号块，照跑不误。

规矩很简单：else 必须和上一个块的右括号写在同一行。

if %N% GTR 0 (
    echo 正数
) else (
    echo 非正数
)

rem 单行写法也可以，短逻辑更清楚
if %N% GTR 0 (echo 正数) else (echo 非正数)

括号块里的变量是"冻结"的

这是批处理最著名的坑，没有之一。cmd 在进入括号块之前就把整块文本读进来并做完了一次 % 展开，所以块内对变量的修改，块内的 %变量% 是看不见的：

set N=0
for %%i in (a b c) do (
    set /a N+=1
    echo 块内看到 N=%N%
)
echo 块外看到 N=%N%
块内看到 N=0
块内看到 N=0
块内看到 N=0
块外看到 N=3

计数确实在增加（块外是 3），只是块内的三个 %N% 在开跑前就已经被替换成字面量 0 了。打个比方：括号块不是"代码块"，而是一张一次性打印出来的清单；清单印好之后你再改仓库里的数字，纸上的数字也不会变。

解药是延迟展开：开启后用 !变量! 代替 %变量%，让展开推迟到每条命令真正执行的那一刻。

@echo off
setlocal EnableDelayedExpansion
set M=0
for %%i in (a b c) do (
    set /a M+=1
    echo 块内看到 M=!M!
)
rem 实测输出：1 / 2 / 3

块内的裸括号会提前收尾

块是靠数括号配对来结束的，所以块内任何一个没转义的 ) 都会被当成块的结尾：

if 1==1 (
    echo 步骤 1^) 初始化      rem 必须写 ^) ，实测输出：步骤 1) 初始化
    echo 步骤 2
)

同样的道理，块内的 &、|、>、< 也都保留着原本的含义，要当普通字符输出就得用 ^ 转义。

块内不要用 :: 写注释

:: 其实是一个"永远不会被跳转到的非法标签"，不是真正的注释语法。单独一条通常没事，但连续两条放在括号块里就会出问题，实测：

if 1==1 (
    :: 第一条注释
    :: 第二条注释
    echo 正文
)
The system cannot find the drive specified.
正文
块内注释

禁用 在 ( ) 块内使用 ::。仍适用 老老实实用 rem，它是真正的命令，在任何位置都安全。

for 的本体：一个集合，一个变量，一段命令

所有 for 都是同一个模子：

for %%变量 in (集合) do 命令

第一件要记住的怪事：批处理里写两个百分号 %%i，命令行里写一个 %i。原因还是"先展开再解析"——批处理的每一行都会先过一遍 % 展开，%% 在这一步被折叠成一个 %，正好留给 for 用。命令行没有这一步预处理，所以写一个就够。

循环变量名是单个字符且区分大小写，%%i 和 %%I 是两个不同的变量。它也不是普通环境变量，set 看不到它，循环结束就消失。

集合怎么被切开

集合里的项由 cmd 的通用分词器切分，空格、逗号、分号、等号都算分隔符。实测：

for %%i in (a,b;c=d e) do echo [%%i]
[a]
[b]
[c]
[d]
[e]

如果某一项含通配符，for 会把它当成文件名模式去匹配磁盘；不含通配符就原样当字符串用：

rem 当作文件名模式：展开成当前目录下所有 .txt
for %%F in (*.txt) do echo %%~nxF

rem 当作纯字符串列表
for %%C in (red green blue) do echo 颜色：%%C

%%~ 修饰符速查

循环变量前面可以插入修饰符，把路径拆成零件。这套修饰符对 %1~%9 参数同样有效（写成 %~nx1）。

修饰符取出的内容示例（%%F = C:\logs\app.log）
%%~F去掉外层引号C:\logs\app.log
%%~fF完整绝对路径C:\logs\app.log
%%~dF驱动器号C:
%%~pF路径部分（含末尾反斜杠）\logs\
%%~nF主文件名app
%%~xF扩展名（含点）.log
%%~sF8.3 短路径形式本例各段本来就符合 8.3，所以不变；C:\Program Files 会变成 C:\PROGRA~1
%%~aF文件属性字符串--a------
%%~tF最后修改时间2026/08/16 09:31
%%~zF文件大小（字节）4096
%%~dpF可以组合：盘符 + 路径C:\logs\
%%~nxF组合：文件名 + 扩展名app.log
%%~$PATH:F在 PATH 里搜索该文件名，返回首个完整路径找不到时返回空串

嵌套与"没有 break"

for 可以嵌套，唯一的硬性要求是内外层变量名不能相同：

for %%i in (1 2) do for %%j in (x y) do echo %%i%%j
rem 输出：1x 1y 2x 2y

但 for 没有 break，也没有 continue。想提前结束，只能 goto 跳出去——而且这会连整个循环一起终止，包括外层：

for %%i in (1 2 3) do (
    echo 处理 %%i
    if %%i==2 goto :done
)
:done
echo 跳出来了
rem 实测输出：处理 1 / 处理 2 / 跳出来了

想模拟 continue，常见技巧是把循环体写成一个子过程，用 exit /b 提前返回（见本章最后一节）。

/L、/D、/R：数数、遍历目录、递归下钻

基本形态之外，for 有四个开关，把同一个语法骨架接到四种不同的数据源上。先看简单的三个。

for /L：唯一的计数循环

for /L %%i in (起始,步长,结束) do 命令

区间是闭区间（含两端），步长可以为负：

for /L %%i in (1,2,7) do echo %%i    rem 实测：1 3 5 7
for /L %%i in (3,-1,1) do echo %%i   rem 实测：3 2 1
步长为 0

禁用 for /L %%i in (1,0,10)。步长为 0 时计数器永远不动，这是一个无法用 Ctrl+C 之外的方式停下来的死循环。如果步长来自变量或参数，务必先校验它不为 0。

for /D：只遍历目录

rem 当前目录下的一级子目录（不递归）
for /D %%G in (*) do echo 目录：%%G

rem 配合模式：所有以 20 开头的子目录
for /D %%G in ("D:\backup\20*") do rd /s /q "%%G"

for /R：递归下钻

for /R "根目录" %%F in (模式) do 命令

省略根目录就从当前目录开始。实测的遍历顺序是先根目录本身，再逐个子目录：

for /R "D:\proj" %%F in (*.log) do echo %%~nxF 在 %%~dpF

有一个非常反直觉的行为必须知道：如果集合里的项不含通配符，/R 不会去检查文件是否存在，而是机械地为每一个目录拼出一个路径。实测：

rem d3 目录下只有一个子目录 s1，两个目录里都没有 readme.txt
for /R %%F in (readme.txt) do echo [%%F]
[C:\...\d3\readme.txt]
[C:\...\d3\s1\readme.txt]

这不是 bug，是刻意留的"路径生成器"用法——你可以用它批量造出每个目录下应该有的文件路径，再自己用 if exist 过滤。但如果你以为它在找文件，就会得到一堆幽灵路径。

形态集合的含义典型用途
for字符串列表 / 文件名通配符遍历固定清单、当前目录的文件
for /L(起始,步长,结束) 数值三元组计数、重试、生成序号
for /D目录名通配符只处理子目录
for /R递归遍历，集合是每个目录下的模式全树扫描、批量改名
for /F文件内容 / 字符串 / 命令输出解析文本，见下一节
现代提示

现代提示 for /R 在大目录树上很慢，因为它对每一层都要重新枚举。老派提速办法是 dir /s /b 先一次性列出再用 for /F 逐行读。真要写新脚本，Get-ChildItem -Recurse -Filter *.log 又快又能直接拿到对象属性。

for /F：批处理自带的 awk

你有一个 CSV，要取第 1 列和第 3 列。在别的语言里这是一行代码，在批处理里也是一行——但这一行里塞了五个选项，每个选项都有脾气。

for /F "选项字符串" %%变量 in (数据源) do 命令

先搞清楚数据源的三种写法

for /F 可以从三个地方拿数据，靠括号里用哪种引号区分。而 usebackq 选项会把这三种引号的角色整体换一轮：

数据源默认写法加了 usebackq 之后
读文件in (文件名)in ("文件名")
解析字面字符串in ("字符串")in ('字符串')
执行命令并解析输出in ('命令')in (`命令`)

usebackq 存在的唯一理由是：路径带空格时必须加双引号，但默认模式下双引号已经被"字面字符串"占用了。换一轮之后，双引号腾出来给文件名，反引号接管命令。

rem 路径带空格，只能靠 usebackq
for /F "usebackq tokens=1,2" %%a in ("%TEMP%\my file.txt") do echo [%%a][%%b]

rem 解析命令输出，命令里的管道要用 ^| 转义
for /F "usebackq tokens=2 delims=:" %%a in (`ipconfig ^| find "IPv4"`) do echo IP=%%a
实测到的一个冷门坑

usebackq 模式下的 '字面字符串' 依然要先过 cmd 的通用分词器，所以字符串里的 , ; = 会被统统规范成空格：

for /F "usebackq delims=" %%a in ('a;b=c,d') do echo [%%a] 实测输出 [a b c d]，逗号分号全没了。

而不带 usebackq 的 "a;b=c,d" 写法原样保留。要解析字面字符串，就用不带 usebackq 的双引号形式。

选项速查表

选项作用默认值要点
delims=xy指定分隔符字符集合（逐字符，不是字符串）空格 + Tab必须放在选项字符串的最后，否则后面的空格会被当成分隔符的一部分
delims=（空）不做任何切分，整行给第一个变量—读整行的标准写法，等价于 tokens=* 但不去首部空白
tokens=n,m挑第 n、m 段1支持区间 1-3、通配 *、混写 1,3*
skip=n跳过开头 n 行0跳表头用
eol=c把以字符 c 开头的行当注释跳过;默认就是分号，会悄悄吞掉以分号开头的数据行
usebackq切换三种引号的角色关路径带空格时必开
默认 eol=; 是个暗雷

你没写 eol，不代表没有 eol。任何以分号开头的行都会被 for /F 静默丢掉——INI 文件、某些日志、以及分号开头的 CSV 数据行都中招。要"什么都不跳过"，把 eol 设成一个数据里绝不会出现的字符，例如 eol=|。

tokens 与变量的自动排号

你只指定一个变量名（比如 %%a），tokens 挑出几段，cmd 就按字母顺序自动往后排：第二段给 %%b，第三段给 %%c，依此类推。

* 是个特殊角色：它表示"最后一个编号段之后的全部剩余内容，连分隔符一起原样打包"。这正是处理"前几列固定、最后一列是自由文本"的利器。实测：

for /F "tokens=1,3* delims=," %%a in ("alice,30,Beijing,Engineer,2019") do echo [%%a][%%b][%%c]
[alice][Beijing][Engineer,2019]

一个完整的 CSV 例子

数据文件 users.csv：

name,age,city,title,year
alice,30,Beijing,Engineer,2019
# 这一行是注释
bob,41,Shanghai,Manager,2015
@echo off
for /F "eol=# skip=1 tokens=1,3* delims=," %%a in (users.csv) do (
    echo 姓名=%%a 城市=%%b 其余=%%c
)
姓名=alice 城市=Beijing 其余=Engineer,2019
姓名=bob 城市=Shanghai 其余=Manager,2015

for /F 解析 CSV 的两个硬伤

在你把它当成通用 CSV 解析器之前，先看这两条实测结果：

rem 硬伤一：连续分隔符被当成一个，空字段直接消失
for /F "tokens=1,2 delims=," %%a in ("x,,y") do echo [%%a][%%b]
rem 实测输出：[x][y]   —— 你以为的第 2 列是空，实际拿到的是第 3 列

rem 硬伤二：不认识 CSV 的引号转义
rem q.csv 的内容只有一行：  "Zhang, San",30
for /F "tokens=1,2 delims=," %%a in (q.csv) do echo [%%a][%%b]
rem 实测输出：["Zhang][ San"]  —— 引号里的逗号照样挨了一刀，字段被劈成两半
现代提示

已过时 用 for /F 解析真实世界的 CSV（有空列、有带引号的字段、有换行嵌在字段里）。现代提示 用 Import-Csv / ConvertFrom-Csv，它们按 RFC 4180 处理引号和空列，还能直接按列名取值：Import-Csv users.csv | ForEach-Object { $_.city }。for /F 适合的是格式简单、由你自己控制的文本，比如命令输出和固定格式的日志。

goto 与 :label：最原始也最耐用的跳转

标签就是行首以冒号开头的一行，goto 跳到它：

@echo off
goto :start

:helper
echo 这段只有被跳过来才执行
goto :eof

:start
echo 开始

goto 后面的冒号可以省略（goto start 也合法），但统一带上更好认。标签名不区分大小写，而且标签行上标签名之后的文字会被忽略，所以 :loop 主循环开始 是一种常用的自注释写法。

用 goto 造循环

cmd 没有 while，所有条件循环都是 goto 加 if 手搓出来的。往回跳完全合法：

@echo off
setlocal
set /a N=0

:retry
set /a N+=1
echo 第 %N% 次尝试...
ping -n 2 127.0.0.1 >nul
if %N% LSS 3 goto :retry

echo 试了 %N% 次，放弃
exit /b 1

注意这种"手搓循环"有个 for 没有的优点：循环体不在括号块里，所以 %N% 每一轮都是新鲜的，不需要延迟展开。很多人被 for 的变量冻结折磨够了之后，会退回来用 goto 写循环，这是个正当选择。

goto :EOF

:EOF 是命令扩展提供的一个内置伪标签，意思是"跳到文件末尾"，也就是结束当前批处理或当前子过程。它不需要你在文件里真的写一个 :EOF 标签。

if not exist "%CONFIG%" (
    echo 配置文件缺失
    goto :eof
)

goto 的三个陷阱

陷阱现象怎么办
goto 跳出 for 循环整个循环（包括外层嵌套）立即终止，不是"跳过这一轮"要模拟 continue，把循环体做成子过程用 exit /b 返回
goto 跳进 ( ) 块内部的标签禁用 行为未定义，块的括号配对状态被破坏，通常直接报语法错误标签一律写在所有块外面
找不到标签报 The system cannot find the batch label specified 并中止整个脚本标签名手滑是常见事故；关键跳转前后加日志
为什么 goto 在大脚本里会变慢

批处理是流式解释的：cmd 没有预编译，也没有跳转表。每次 goto 它都要在文件里重新定位——从当前位置往下扫，扫到文件尾还没找到就绕回开头再扫一遍。所以在一个几千行的批处理里高频 goto，开销是实打实的。这也解释了为什么老脚本喜欢把热点子过程放在文件靠前的位置。

call 与 exit /b：把批处理写成有函数的程序

goto 是单程票：跳过去就回不来了。要"跳过去、干完活、回到原地"，需要 call。

call :label —— 批处理的函数

@echo off
setlocal

call :log 开始处理
call :add 3 4
echo 和 = %RESULT%
call :log 结束
exit /b 0

rem ===== 以下是子过程，主流程绝不会顺着走进来 =====

:log
echo [%TIME:~0,8%] %~1
exit /b 0

:add
setlocal
set /a S=%1 + %2
endlocal & set "RESULT=%S%"
exit /b 0

要点有四个：

  • 参数：子过程里 %1~%9 是 call 传进来的参数（不是主脚本的命令行参数），%* 是全部参数原样。%~1 去掉外层引号，%~dp1 等修饰符也可用。超过 9 个参数用 shift 逐个挪。
  • 返回：子过程末尾用 exit /b 或 goto :eof。
  • 哨兵：主流程的最后一句必须是 exit /b（或 goto :eof），否则会一路执行到下面的子过程里去。这是新手最常见的"脚本莫名跑了两遍"的原因。
  • 传值出来：endlocal & set "RESULT=%S%" 这个写法看着诡异，其实很合理——整行在执行前就完成了 %S% 的展开，所以 endlocal 销毁局部环境之后，set 拿到的已经是字面值了。实测可用。

exit /b 与返回码

写法效果
exit /b 0结束当前批处理/子过程，把返回码设为 0
exit /b %errorlevel%把内部命令的失败原样传给调用者，最常用的收尾
exit /b（不带数字）结束并保留当前的 errorlevel（实测：之前是 9，返回后还是 9），不是清零
goto :eof效果与不带数字的 exit /b 基本相同
exit 1（不带 /b）禁用 直接终止整个 cmd.exe 进程。双击运行时窗口瞬间消失，在别的脚本里被 call 时会把调用者一起带走

call 之后 %errorlevel% 就是子过程 exit /b 的值，所以可以直接接 && / ||，实测有效：

call :deploy && echo 部署成功
call :deploy || goto :fail

但是——想在 || 后面把返回码打出来，就又撞上"同一行先展开"的老规矩了。%errorlevel% 在整行被解析时就已经定稿，那时候 call 还没跑：

rem 假设 :fail 子过程 exit /b 42，而调用前 errorlevel 是 0
call :fail || (echo A=%errorlevel%)     rem 实测输出 A=0    ← 拿到的是调用前的旧值

setlocal EnableDelayedExpansion
call :fail || (echo B=!errorlevel!)     rem 实测输出 B=42   ← 正确

rem 不想开延迟展开，就老实拆成两行
call :fail
if %errorlevel% NEQ 0 echo C=%errorlevel%

call 另一个批处理：那个经典的坑

rem 错误：不加 call，控制权一去不返
build.cmd
echo 这一行永远不会执行

rem 正确：加 call，跑完回到下一行
call build.cmd release
echo 构建返回码 %errorlevel%

为什么会有这么反直觉的默认行为？这是 DOS 时代的遗留：那时候内存极其紧张，"链式加载"（一个批处理跑完直接把控制权交给下一个，不保留返回地址）是常规做法，call 才是需要额外开销的特例。今天这个默认值只剩下坑人的作用。

规矩

已过时 在批处理里直接写 other.cmd 调用另一个批处理。仍适用 调用 .bat / .cmd 一律加 call。调用 .exe 不需要（可执行文件本来就会返回）。如果你确实想要"跑完就退出"，也请显式写成 call other.cmd & exit /b %errorlevel%，让意图可见。

方式会回来吗在哪个进程典型用途
goto :label不会当前流程分支、手搓循环
call :label会当前子过程 / 函数
call other.cmd会当前调用另一个批处理并拿返回码
other.cmd不会当前已过时 DOS 链式加载遗留
cmd /c other.cmd会新进程隔离环境变量污染
start other.cmd立刻返回，不等新窗口并行启动；拿不到返回码
call 的第三种用法

已过时 call set "VAR=%%%INNER%%%" —— 利用 call 会把整行再解析一遍的特性做"二次展开"，这是延迟展开出现之前的间接寻址技巧。它慢（每次都要重新解析）、易错（百分号数量全靠数）、还会被值里的特殊字符打断。现代提示 用 setlocal EnableDelayedExpansion 加 !VAR!，或者直接换 PowerShell 的哈希表。

综合演练与陷阱速查

把三样东西拼起来

下面这个脚本把本章所有要点串了一遍：参数校验、if exist、for /R 递归、块内延迟展开、^) 转义、分层返回码。这段代码在 Windows 11 上完整跑通，四个分支的返回码都实测过。

@echo off
setlocal EnableExtensions EnableDelayedExpansion

rem ---- 参数校验：没给目录就打印用法并返回 2 ----
if "%~1"=="" (
    echo 用法: %~nx0 ^<目录^> [扩展名]
    exit /b 2
)

set "ROOT=%~1"
set "EXT=%~2"
if not defined EXT set "EXT=log"

rem ---- 目录不存在返回 3 ----
if not exist "%ROOT%\" (
    echo [错误] 目录不存在: %ROOT%
    exit /b 3
)

rem ---- 递归统计：注意 !COUNT! 用延迟展开，^) 要转义 ----
set /a COUNT=0, BYTES=0
for /R "%ROOT%" %%F in (*.%EXT%) do (
    set /a COUNT+=1, BYTES+=%%~zF
    echo   !COUNT!^) %%~nxF  %%~zF 字节
)

rem ---- 一个都没找到返回 1 ----
if !COUNT! EQU 0 (
    echo 没有找到 *.%EXT%
    exit /b 1
)

echo 共 !COUNT! 个文件，合计 !BYTES! 字节
exit /b 0
> scan.cmd
用法: scan.cmd <目录> [扩展名]        rem 返回码 2

> scan.cmd D:\demo

  2) b.log  9 字节
共 2 个文件，合计 16 字节             rem 返回码 0

> scan.cmd D:\nope
[错误] 目录不存在: D:\nope           rem 返回码 3

> scan.cmd D:\demo zzz
没有找到 *.zzz                       rem 返回码 1
中文脚本的编码坑（顺带一提）

上面这个脚本里有中文提示文字。cmd 是按当前代码页去解释批处理文件字节流的，如果你把它存成 UTF-8 而系统代码页是 GBK，中文字符的字节会被错误地两两配对，多出来或少掉的那个字节可能正好啃掉一个引号或右括号——于是报错信息会指向一个和真正问题毫不相关的位置——本章这个示例脚本第一次跑就是这么翻车的，报的错离真正的问题隔了十几行。稳妥做法：含中文的 .cmd 存成 ANSI(GBK)；坚持用 UTF-8 就在首行写 chcp 65001 >nul。

第 4 章重定向、管道与常用命令

前三章你把「怎么让 cmd 正确读懂你写的一行字」这件事搞定了。这一章换个问题：一行命令跑完，产生的字往哪儿去？怎么把它们截住、拆开、送给下一个命令？

批处理没有函数返回值，也没有对象。它唯一的「数据总线」就是文本流：一个命令吐出文本，你把这股文本导进文件、导进黑洞，或者接到另一个命令的嘴边。理解了这套水管系统，剩下的常用命令不过是接在水管两头的零件——本章后半段就是这些零件的速查表。

三个编号：0、1、2 与它们的默认去向

你在脚本里写了一行看起来很稳妥的：

dir C:\NotExist > log.txt

跑完一看：log.txt 是空的，而错误提示「找不到文件」照样刷在屏幕上。你会本能地怀疑路径写错了、权限不够、或者 dir 有什么坏毛病。都不是——> 从头到尾就没打算管错误信息。

每个进程启动时，操作系统都会给它三根预先接好的管子，用编号标识：

句柄号名称中文默认接到哪里典型内容
0stdin标准输入键盘set /p、more、sort 要读的东西
1stdout标准输出屏幕dir 的清单、echo 的文字、正常结果
2stderr标准错误屏幕「系统找不到指定的文件」「拒绝访问」

关键在于：> 是 1> 的简写。你只接了 1 号管子，2 号管子还老老实实地往屏幕上倒。屏幕上两股水看起来混在一起，是因为它们默认流向同一个地方，不是因为它们本来就是一股。

打个比方：一条命令就是一台车床。它有一个进料口（0 号）和两个出口——一个出成品（1 号），一个出铁屑（2 号）。你在成品口下面放了个桶，铁屑当然还是往地上掉。要接住铁屑，得再搬一个桶（2>），或者干脆让铁屑也倒进成品桶（2>&1）。

为什么当初要分成两根？因为一旦有了管道，输出就不再只是给人看的，而是要喂给下一个程序。如果错误信息混在数据流里，sort 会把「拒绝访问」当成一行数据去排序，findstr 会把它当成候选行去匹配，for /f 会把它当成一条记录去拆分。分流的本质是一句话：1 号给机器，2 号给人。

动手验证一下，一条命令、两个文件：

:: 一次跑一对一错的两个路径，把两根流分别落盘
dir C:\Windows\explorer.exe C:\NotExist 1>ok.txt 2>err.txt

echo ---- 1 号（stdout）----
type ok.txt
echo ---- 2 号（stderr）----
type err.txt
这是约定，不是强制

Windows 自带命令基本都遵守「结果走 1、诊断走 2」。但第三方 exe 不一定：有的把全部日志写进 2 号（于是 >log.txt 抓到空文件），有的把错误写进 1 号（于是 2>nul 屏蔽不掉噪音）。碰到行为诡异的工具，先用上面这个「分两个文件」的实验探一下它的脾气，再决定怎么接管子。

现代提示

PowerShell 把这套东西扩成了六个流：1 Success、2 Error、3 Warning、4 Verbose、5 Debug、6 Information，还有一个 *> 表示「全都要」。理解了 cmd 的 1 和 2，PowerShell 那套只是同一个概念的加长版。

重定向符号一共就这么几个，但组合起来的坑不少。先把表放这儿，随时回来查：

命令 >> 文件stdout 追加文件不存在则创建；写日志的默认选择

1>&2反过来，让正常输出走错误流用来输出「不该被管道吃掉」的提示信息

陷阱一：2>&1 的位置

:: 正确：先把 1 号指向文件，再让 2 号照抄 1 号的地址
mytool.exe >all.log 2>&1

:: 错误：此刻 1 号还指着屏幕，2 号跟着去了屏幕；之后 1 号才改道文件
mytool.exe 2>&1 >all.log

2>&1 不是「把两根管子绑一起」，而是「照抄 1 号此刻的地址」。地址是抄的那一瞬间的快照，后面 1 号搬家，2 号并不会跟着走。记法：先定目的地，再喊跟我走。

陷阱二：> 前面的空格会被写进文件

:: 这行写出的是 "OK " —— 行尾多一个空格，后面比较字符串时就对不上了
echo OK >flag.txt

:: 干净写法：把重定向提到命令前面，一行里一眼看出目标文件
>flag.txt echo OK

陷阱三：紧贴的数字会被当成句柄号

:: 想写出 "1"，实际得到一个空行 —— 因为 1> 被解析成了「1 号重定向」
echo 1>n.txt

:: 两种解法，任选一种
(echo 1)>n.txt
>n.txt echo 1

这个坑对 0～9 这十个数字都成立。凡是 echo 一个纯数字并且紧跟重定向的场合，一律加括号或前置重定向。

陷阱四：重定向失败会让整行命令根本不执行

:: 若目标目录不可写，或文件被别的进程独占，这一行连 echo 都不会跑
echo start >> "C:\Program Files\app\run.log"

cmd 是先建立重定向、再执行命令的。建立失败就直接报错退出，命令本体一次都没运行。写日志前先确认目录存在且可写，或者退一步用 2>nul 把重定向自身的报错也吞掉，再靠后续判断兜底。

NUL 是设备名，不是文件名

NUL（还有 CON、PRN、AUX、COM1～LPT9）在任何目录下都「存在」：D:\anything\nul 也是合法的黑洞。所以别写成 >nul.txt——那会真的生成一个叫 nul.txt 的文件。反过来，你也永远无法在项目里创建名为 nul、con 的文件，Git 仓库跨平台时这是个著名的踩坑点。

管道：把上一个命令的嘴接到下一个的耳朵

type big.log | findstr /i "error" 这种写法你肯定用过，很顺手。但只要你试着在管道里改一个变量，就会撞上一堵墙：

:: 这行跑完，count 是空的
type access.log | find /c "404" | for /f %%a in ('more') do set count=%%a
echo [%count%]

原因不在语法，在于 | 的实现方式：cmd 遇到管道，会给左右两边各开一个新的 cmd.exe 子进程，把左边的 1 号句柄接到一段内存缓冲区的写端，把右边的 0 号句柄接到读端，然后让两个子进程同时跑起来。set 改的是子进程自己的环境块，子进程一退出，环境块就随之消失。

比方：管道是对讲机，不是快递。两个人同时在线，一个说一个听；而不是等左边写完一整封信，再寄给右边。这也解释了为什么 type 10GB.log | findstr x 不会先生成一个 10 GB 的中间文件——数据是边产边耗的。

把「两个子进程」这件事记牢，管道的四大坑就都能自己推导出来：

现象真正原因对策
管道里 set 的变量，出了管道是空的变量属于子进程的环境块用 for /f 把整条管道包住，或走临时文件
管道右边取到的 %var% 是旧值父进程解析整行时就已经展开了setlocal enabledelayedexpansion + !var!
错误信息没被过滤掉只有 1 号进管道，2 号直接上屏写成 命令 2>&1 | findstr ...
管道里 setlocal／cd／pushd 不起作用作用于子进程，退出即还原把它们移到管道外面

把结果接回父进程的标准做法是 for /f——注意单引号里的 | 必须转义成 ^|：

:: 方案 A：临时文件（笨但直白，任何 Windows 版本都稳）
type access.log | find /c "404" > "%TEMP%\c.tmp"
set "count="
set /p count=<"%TEMP%\c.tmp"
del "%TEMP%\c.tmp"
echo 404 出现 %count% 次

:: 方案 B：for /f 直接接住整条管道的输出（推荐）
for /f %%n in ('type access.log ^| find /c "404"') do set "count=%%n"
echo 404 出现 %count% 次

要让错误信息也一并被过滤，必须显式把 2 号并进 1 号，而且 2>&1 要写在 | 之前：

:: 只有加了 2>&1，findstr 才看得见错误行
robocopy src dst /e 2>&1 | findstr /i /c:"ERROR"
echo y | 这类「喂答案」的写法

echo y | del *.tmp、echo A | format 这种做法依赖命令提示语的具体文字，换成英文版系统或换个 Windows 版本就失效，而且一旦提问顺序变了，你喂的 y 可能答到别的问题上。凡是命令自带 /Q、/Y 开关的，一律用开关：del /q、copy /y、xcopy /y、rd /s /q。确实需要多行输入时，用 命令 <answers.txt 而不是管道。

唯一一个必须记住的坑：退出码

robocopy 不遵守「0 成功、非 0 失败」的惯例，它用位标志汇报干了什么。这是无数 CI 流水线被它气疯的原因：明明拷贝成功，构建却报红。

退出码含义算不算失败
0源和目标已一致，什么都没拷成功
1有文件被成功复制成功（最常见的正常返回值）
2目标里有源没有的多余文件/目录成功，但值得留意
4存在不匹配的文件或目录（比如同名一个是文件一个是目录）需要人工看一眼
8有文件或目录复制失败（重试后仍失败）失败
16严重错误，一个文件都没能处理失败
3、5、7…上面各项按位相加，例如 3 = 1+2小于 8 即成功

所以判断规则只有一条：GEQ 8 才是失败。

@echo off
:: 稳妥的同步模板：重试 2 次、每次等 5 秒、8 线程、追加日志
robocopy "D:\src" "\\nas\backup\src" /e /r:2 /w:5 /mt:8 /np /ndl ^
    /log+:"D:\logs\sync.log" /tee

:: 必须紧接着取值，中间插一条命令 ERRORLEVEL 就被覆盖了
set "RC=%ERRORLEVEL%"

if %RC% GEQ 8 (
    echo [FAIL] robocopy 退出码 %RC%，请查看 D:\logs\sync.log
    exit /b 1
)
echo [OK] 同步完成，退出码 %RC% 属正常范围
exit /b 0
/MIR 会删除目标端的文件

/MIR 等价于 /E + /PURGE：目标端凡是源里没有的东西，一律删除。如果源路径写错、源盘临时未挂载但路径仍解析成一个空目录，/MIR 会忠实地把目标端清空。上线前一律先加 /L 跑一遍预演，确认它打算删的东西确实该删。给备份目标做快照或版本控制也是必要的。

现代提示：PowerShell 里也照样调 robocopy

Copy-Item -Recurse 没有重试、没有增量、没有多线程、没有日志。所以在 PowerShell 脚本里直接调用 robocopy.exe 至今仍是业界标准做法，只是判断条件要写成 if ($LASTEXITCODE -ge 8) { throw }。跨机同步量再大一级，就该看 DFS 复制或专门的同步服务了。

xcopy 还能用吗

能。它随系统提供、语法短，临时拷一个小目录树时手敲 xcopy /e /i /y src dst 完全没问题。已过时 指的是：不要再用它写新的、要长期跑的同步脚本。

findstr 与中文编码

start：启动程序、等待与退出码

你写下这一行，期待它打开程序：

start "C:\Program Files\App\app.exe"

结果弹出一个空的命令行窗口，标题栏上写着那串路径，程序压根没启动。

原因是 start 的第一个带引号的参数被当作窗口标题。这是从早期 Windows 就定下的语法，改不了了。所以规则是：只要程序路径带引号，前面就必须先给一个标题占位，哪怕是空标题。

:: 对：先用空字符串占掉标题位
start "" "C:\Program Files\App\app.exe"

:: 带参数、指定工作目录、最小化启动
start "构建任务" /d "D:\proj" /min cmd /c build.cmd
开关作用备注
"标题"新窗口标题位置固定在最前；几乎总是写成 ""
/d 路径指定启动时的工作目录比先 cd 再 start 干净
/b不开新窗口，在当前控制台里跑该进程会忽略 Ctrl+C，只能用 Ctrl+Break 打断
/wait等程序结束再继续拿退出码的前提
/min /max最小化 / 最大化启动无人值守任务常配 /min
/low /belownormal /normal /abovenormal /high /realtime进程优先级/realtime 会抢占系统关键线程，别用
/affinity 掩码绑定 CPU 核心十六进制掩码
/i用 cmd.exe 启动时的原始环境不继承当前脚本里 set 的变量

等待与退出码

默认的 start 是「发射后不管」：它把程序丢给系统就立刻返回，%ERRORLEVEL% 里装的是 start 自己的结果，不是你启动那个程序的结果。要拿真正的退出码，必须加 /wait：

:: 同步执行、不新开窗口、能拿到安装程序的真实退出码
start /wait /b "" installer.exe /silent
echo 安装程序退出码：%ERRORLEVEL%
/wait 也未必等得到

很多 GUI 安装器（尤其是包着 MSI 的 setup.exe）会自己再拉起一个真正干活的进程，然后主进程立刻退出。这时 /wait 等到的只是那个空壳。对策：能用 msiexec /i x.msi /qn /norestart 就直接用它（它是同步的），否则事后用 tasklist 轮询目标进程名，等它从列表里消失。

start 启动批处理会留下窗口

官方文档写得明白：如果 start 的目标是内部命令或批处理文件，它会用 /K 启动命令处理器——意思是命令跑完窗口不关。想让它跑完就消失，自己写清楚：start "" cmd /c mytask.cmd。

四种调用方式的区别

写法是否等待新窗口能拿退出码用在什么场合
app.exe是否是默认选择，绝大多数情况
call other.cmd是否是调用另一个批处理并返回本脚本
other.cmd（漏了 call）是，但一去不回否—几乎总是 bug：控制权转移过去就再也不回来
start "" app.exe否是否并行启动、启动 GUI 程序
start /b "" app.exe否否否后台并行，共用当前控制台
start /wait "" app.exe是是是要独立窗口又要退出码

关联启动：start 最实用的那一面

start 会走 Windows 的文件关联，所以它能「用默认程序打开」任何东西——这是脚本收尾时最方便的一招：

:: 用默认浏览器打开生成的报告
start "" "%~dp0report.html"

:: 在资源管理器里打开输出目录
start "" "D:\out"

:: 打开一个网址
start "" https://example.com

并行与汇合

批处理没有 wait 原语，这是它作为并行工具的硬伤。经典的绕法是「标志文件 + 轮询」：

@echo off
md flags 2>nul
del /q flags\*.done 2>nul

:: 并行起三个任务，各自完成后留下一个标志文件
:: ^& 和 ^> 让这两个符号原样传给新开的 cmd，而不是被当前这行吃掉
for %%J in (a b c) do start "" /b cmd /c work.cmd %%J ^& break^>flags\%%J.done

:: 主流程轮询，等三个标志都出现
:m4wait
timeout /t 2 /nobreak >nul
for %%J in (a b c) do if not exist flags\%%J.done goto m4wait

echo 三个任务全部完成
现代提示

PowerShell 的 Start-Process -Wait -NoNewWindow -PassThru 一次解决窗口、等待、退出码三件事，返回的对象里直接有 ExitCode；并行汇合用 Start-Job + Wait-Job，或 PowerShell 7 的 ForEach-Object -Parallel。如果你的脚本里已经出现「标志文件轮询」这种结构，说明它长到该换语言了。

where、tasklist、taskkill、timeout：探测与节奏

脚本第一行就调用 git，在你机器上跑得好好的，到同事机器上第一句就是「不是内部或外部命令」——而且它还是在删了一堆临时文件之后才炸的。健壮脚本的第一条纪律：先探测，再动手。

where：这个命令到底在不在

:: 依赖自检：找不到就早失败，别跑到一半才出事
where /q git.exe || (
    echo [ERR] 未找到 git，请先安装并加入 PATH
    exit /b 1
)
开关作用
/q只给退出码，不输出——脚本里判断依赖就用这个
/r 目录从指定目录递归找文件（不限于 PATH）
/f结果加双引号，便于直接拼进带空格的路径
/t顺便显示文件大小和修改时间
退出码0 找到 / 1 没找到 / 2 出错

两个要点：where 找的是 PATH 上的文件，所以 where dir 一定失败（dir 是内部命令，不是文件）；它还会自动尝试 PATHEXT 里的扩展名，所以 where git 能找到 git.exe。当同名程序有多份时，它按查找顺序全列出来——排第一个的才是实际会被执行的那个，这对排查「为什么用的是旧版本」特别有用。

tasklist：进程在不在

开关作用
/fi "条件"筛选：imagename eq notepad.exe、pid eq 1234、status eq running、memusage gt 100000、windowtitle eq *报表*
/fo csv|table|list输出格式，脚本里配 csv 最好解析
/nh不打表头
/v详细信息：窗口标题、运行用户、CPU 时间
/svc显示每个进程里承载的服务（查 svchost 时必备）
/m 模块名列出加载了指定 DLL 的进程
/s 机器 /u 用户 /p 密码查远程机器
tasklist 找不到进程时退出码仍是 0

不但如此，它还会往 stdout 打印一句「信息: 没有运行的任务匹配指定标准。」——所以你不能靠退出码，也不能靠「输出是否为空」来判断。正确写法是把结果再过一遍 findstr：

:: 判断某进程是否在运行的可靠写法
tasklist /fi "imagename eq notepad.exe" /nh 2>nul | findstr /i /c:"notepad.exe" >nul
if errorlevel 1 (
    echo notepad 未运行
) else (
    echo notepad 正在运行
)

taskkill：把它关掉

开关作用
/im 映像名按可执行文件名，如 /im notepad.exe
/pid 数字按进程 ID
/f强制终止，不给程序保存和清理的机会
/t连同它启动的所有子进程一起终止
/fi "条件"筛选语法与 tasklist 相同
 
:: 先温和请求退出，等两秒，还在就强制
taskkill /im myapp.exe >nul 2>&1
timeout /t 2 /nobreak >nul
taskkill /f /t /im myapp.exe >nul 2>&1
exit /b 0
别对系统进程动手

taskkill /f /im svchost.exe、lsass.exe、csrss.exe、wininit.exe 之类会直接导致系统崩溃或强制重启，某些进程被终止时 Windows 会主动蓝屏。脚本里只终止你自己启动的、名字明确的进程；不要用通配符匹配映像名；能先试不带 /f 的温和终止就先试。

timeout：让脚本歇一会儿

用法说明
timeout /t 5等 5 秒，期间按任意键提前结束；有效范围 -1 到 99999 秒
timeout /t 5 /nobreak忽略按键，老实等满（Ctrl+C 仍能中断）
timeout /t -1无限等待，直到按键——相当于一个更友好的 pause
timeout /t 5 /nobreak >nul连倒计时的刷屏也一并省掉，脚本里最常用的形式
timeout 在无人值守环境里会直接报错

只要 stdin 被重定向——计划任务、CI 流水线、被别的程序以管道方式调用——timeout 就会打印 ERROR: Input redirection is not supported 然后退出，一秒都不等。因为它的实现依赖读控制台按键。这类场景改用 ping 当秒表：

:: 交互式场景
timeout /t 5 /nobreak >nul

:: 无人值守 / 输入被重定向的场景：ping 自己 n 次，间隔 1 秒，实际等 n-1 秒
ping -n 6 127.0.0.1 >nul
sleep.exe

老脚本里常见的 sleep 5 来自 Windows 2000/2003 资源工具包，早已不随系统提供。现在的选择只有上面两个，或者 PowerShell 的 Start-Sleep -Seconds 5。

组合起来：实战模板与现代替代对照

把这一章的零件拼起来，一个「归档日志」的完整脚本长这样。它串起了依赖自检、路径校验、两流合并的日志、robocopy 退出码判断、findstr 复查：

@echo off
setlocal enableextensions

set "SRC=D:\app\logs"
set "DST=E:\archive\logs"
set "LOG=%~dp0archive.log"

if not exist "%SRC%\." (echo [ERR] 源目录不存在：%SRC% & exit /b 1)

:: 2) 只归档 7 天内的 .log，两根流一起进日志文件
robocopy "%SRC%" "%DST%" *.log /e /maxage:7 /r:2 /w:5 /np /ndl ^
    /log+:"%LOG%" 2>&1
set "RC=%ERRORLEVEL%"

if %RC% GEQ 8 (
    echo [FAIL] robocopy 退出码 %RC%
    exit /b 1
)

:: 3) 复查日志里有没有权限类问题（robocopy 会重试后跳过，退出码未必反映）
findstr /i /c:"ERROR 5 " /c:"Access is denied" "%LOG%" >nul 2>&1
if not errorlevel 1 (
    echo [WARN] 日志中存在权限问题，请人工复核 %LOG%
    exit /b 2
)

echo [OK] 归档完成，robocopy 退出码 %RC%
exit /b 0

下一章我们把注意力转回控制流：for 的五种形态、if 的比较陷阱，以及怎么用 call 和标签把长脚本拆成能读懂的结构。而这一章的重定向和管道，会是那一章里几乎每个例子的底座——因为 for /f 读的，正是你在这里学会怎么产生的那股文本流。

第 5 章转义、引号与实战陷阱

为什么同一个脚本换台机器就崩

你写了一个部署脚本，在自己机器上跑得好好的。发给同事，第一行就报错；装到服务器上，日志里全是问号；某天有人把项目挪到 D:\我的 项目\build 下，脚本直接把半个目录删了——因为路径里的空格把一个参数劈成了两个。

这些故障看上去毫无关联，其实全都出自同一个根源：cmd.exe 不是在「解释一门语言」，它是在「对一行文本做几遍替换，然后把替换结果当命令执行」。

这一点非常重要，值得再说一遍：变量的值会被塞回命令行文本里，然后重新参与语法解析。所以一个值里如果含有 &、|、>、空格，它就不再只是数据，它会变成语法。看这个真实例子（本章所有示例的输出均在 Windows 11 的 cmd.exe 上实测）。

@echo off
set "V1=x&y"
echo T2: [%V1%]

rem 实际输出：
rem   T2: [x
rem   'y]' 不是内部或外部命令，也不是可运行的程序

set "V1=x&y" 这一句是完全正确的，变量里确实存着 x&y。崩在下一句：%V1% 被替换成 x&y 之后，cmd 才开始找命令分隔符，于是它看到了一个 &，把这一行劈成了 echo T2: [x 和 y] 两条命令。

打个比方：cmd 像一间老式排版车间。工人先拿模板稿，把稿子上的 %V1% 之类占位符手工贴上实际文字，贴完再把整张稿子交给排版机。如果你贴上去的文字里正好有排版机的控制符号，排版机分不出那是「你贴的内容」还是「原稿的指令」——它只看最终这张纸上有什么。

这个设计不是失误，是省内存

cmd 的语法继承自 COMMAND.COM，那是要在 64KB 内存里跑完的东西。「逐行做文本替换再执行」是当年最省内存的方案：不需要建语法树，不需要保存中间结构，扫一遍字符串就行。后来为了兼容三十年的存量脚本，这套规则被彻底冻结——包括它的全部怪癖。

工序做了什么你能用什么手段影响它
① 读行取一行；行首 @ 抑制本行回显@
② 百分号展开%VAR%→值；%%→%；%1→参数%%；改用 !VAR!
③ 转义与引号^X→X（^ 消失）；记录引号内/外状态^、"
④ 切分按 & && || | ( ) 拆成多条命令^ 转义、引号、括号分组
⑤ 延迟展开!VAR!→值（此时不再重新切分）setlocal enabledelayedexpansion
⑥ 执行调内部命令或启动外部程序，设置 ERRORLEVEL—
现代提示

PowerShell 走的是完全相反的路线：先把整段脚本解析成抽象语法树，参数以对象形式传递，变量的值永远不会被重新当作语法解析。$v = 'x&y'; Write-Output $v 一定输出 x&y，没有任何转义顾虑。你在本章看到的每一个坑，基本都能在 PowerShell 的设计文档里找到对应的「我们为什么这么改」。

脱字符 ^：把语法降级成字符

^（脱字符 / caret，键盘 Shift+6）是 cmd 唯一的转义字符。它的语义只有一句：紧跟在我后面的那个字符，只是普通字符，不是语法；说完这句话，^ 自己就从命令行里消失了。

@echo off
rem 错误：& 被当成命令分隔符
echo Tom & Jerry
rem 输出 Tom，然后报 'Jerry' 不是内部或外部命令

rem 写法一：用 ^ 转义
echo Tom ^& Jerry
rem 输出：Tom & Jerry

rem 写法二：整段加引号（引号本身也会被 echo 出来）
echo "Tom & Jerry"
rem 输出："Tom & Jerry"

echo 3 ^> 2
rem 输出：3 > 2   （不转义的话会创建一个名为 2 的文件）
字符不转义时的含义转义写法
&命令分隔符^&
|管道^|
> >>输出重定向^> ^>^>
<输入重定向^<
( )命令分组^( ^)
^转义符本身^^
!延迟展开开启后为变量定界符^!（仅在延迟展开开启时需要）
"引号，切换「字面区」^"（用于打破引号配对）
%变量定界符无法用 ^ 转义，见下一节

三条容易踩空的附加规则

规则一：引号内部，^ 不再是转义符。进入双引号后，特殊字符已经被字面化了，^ 就只是一个普通的脱字符。echo "a^b" 原样输出 "a^b"，而不是 "ab"。

规则二：行尾的 ^ 是续行符——因为它转义的是那个看不见的换行符。这既是功能也是陷阱：^ 后面绝对不能有空格，否则它转义的是空格，换行照样生效。

@echo off
robocopy "%SRC%" "%DST%" ^
  /MIR /R:2 /W:3 ^
  /LOG:"%~dp0sync.log"
rem 三行合成一条命令；每个 ^ 后面必须立刻换行，不能有尾随空格

规则三：一行要被解析两次时，转义也要写两遍。这是最难自查的一类 bug。当一条命令会经过第二个 cmd 解析器（cmd /c、管道的两端、for /f 里带引号的命令），第一遍解析会把 ^ 吃掉，第二遍解析就看到了裸的 &。

场景解析次数要输出一个字面 & 该怎么写
直接在脚本里执行1echo a ^& b
cmd /c "..." 内部2cmd /c "echo a ^^& b"
管道右侧的命令2echo x | findstr "a^^&b"
for /f %%L in ('命令') 内部2管道写 ^|，重定向写 ^>
start "" cmd /c "..."2~3能加引号就加引号，别硬堆 ^
 
@echo off
rem for /f 的括号里是「要执行的命令」，会被再解析一次
rem 所以管道必须写成 ^| ，否则 for 语句本身就被劈断了
for /f "tokens=*" %%L in ('echo pipe-test ^| find "pipe"') do echo 命中: %%L
rem 输出：命中: pipe-test
经验法则

数一数你的命令会被几个 cmd 读到，转义符就写几个 ^。写到需要 ^^^& 的时候，停下来——那说明这段逻辑该换实现方式了（提取成独立脚本、或者用 PowerShell）。

百分号的两副面孔：%% 与延迟展开

新手最早撞上的一堵墙通常是这个：教程里写 for %%i in (*.txt) do ...，你复制到命令行窗口一跑，报 %%i was unexpected at this time；改成 %i 又能跑了。回到脚本里，%i 反而不行。

原因是：批处理文件和交互式命令行，对 % 的处理规则根本不是同一套。批处理文件里有 %0～%9 参数，所以 cmd 必须提供一个「写出字面百分号」的写法，那就是 %%；命令行没有参数概念，也就不做这个折叠。

你写的在 .bat 文件里的结果在命令行窗口里的结果
echo 100%%100%100%%
echo 100%100（末尾孤立的 % 被吞掉）100%
echo a%baba%b
%未定义变量%展开成空串原样保留 %未定义变量%
for 循环变量必须写 %%i必须写 %i

所以在脚本里想显示一个百分号，唯一可靠的写法是 %%。禁用 用 ^% 转义百分号——它不但没用，还会引发一个极其隐蔽的连锁反应：

@echo off
echo P1:^%
echo P2:50%%

rem 你期望两行输出。实际只有一行：
rem   P1:echo P2:50%
rem 因为 % 在第②道工序就被吞掉了，剩下的 ^ 落到了行尾，
rem 于是它转义了换行符 —— 下一行被拼了上来。

记住工序顺序就能理解：百分号展开（②）发生在 ^ 处理（③）之前。等 ^ 上岗时，% 早已不在现场了。

%VAR% 与 !VAR!：烫金 vs 查表

第二副面孔是展开时机。%VAR% 在工序②被替换，也就是整条语句（含整个括号块）被读进来的那一刻；而开启延迟展开后的 !VAR!，是在工序⑤——这条命令真正要执行的前一刻——才去查值。

@echo off
set C=0
for %%f in (a b c) do (
  set /a C+=1
  echo NORMAL C=%C%
)
rem 输出：NORMAL C=0 / NORMAL C=0 / NORMAL C=0

setlocal enabledelayedexpansion
set C=0
for %%f in (a b c) do (
  set /a C+=1
  echo DELAYED C=!C!
)
endlocal
rem 输出：DELAYED C=1 / DELAYED C=2 / DELAYED C=3

比方：%VAR% 像印刷时就把内容烫在纸上——纸一进印刷机内容就定死了，后面再改变量也没用；!VAR! 像现场查表念出来——每次执行都重新查一次。

延迟展开还能顺手解决上一节那个 & 的问题，因为工序⑤展开出来的值不会再被切分：

@echo off
setlocal enabledelayedexpansion
set "V=x&y"
echo F1: "%V%"      rem 输出 F1: "x&y"  —— 靠引号保护
echo F2: !V!         rem 输出 F2: x&y    —— 靠延迟展开保护
需求写法
脚本内开启延迟展开setlocal enabledelayedexpansion（配 endlocal）
整个 cmd 会话开启cmd /v:on（调试时很好用）
单次调用开启cmd /v:on /c "..."
延迟展开下输出字面 !^!（引号内也要转义）
循环里累加、拼接字符串一律用 !VAR!
for 的循环变量 %%i不受影响，每轮迭代自动更新
现代提示

PowerShell 没有「展开时机」这个概念：$c 在任何位置都是同一个变量的当前值，循环里直接 $c++ 即可。延迟展开这个开关的存在本身，就是「文本替换式解释器」的补丁。

引号该加在哪：带空格路径的正确写法

C:\Program Files 这个带空格的目录名，制造的 bug 大概比任何单个 Windows 特性都多。规则本身很简单：cmd 用空格分割参数；要让含空格的一串字符算作一个参数，就用双引号把它整个包起来。

rem 错：被拆成三个参数
copy C:\Program Files\app\a.txt D:\backup

rem 对：引号从盘符一直包到文件名
copy "C:\Program Files\app\a.txt" "D:\backup"

rem 也错：只包了中间一段，引号不是「保护空格」而是「界定参数」
copy C:\"Program Files"\app\a.txt D:\backup

第三种写法在很多情况下碰巧能跑，但它把参数拆成了 C:\ + Program Files + \app\... 三段再拼回去，遇到 for、%~ 修饰符、外部程序自己的参数解析器时就会翻车。引号要从头包到尾。

已过时的绕法

已过时 用 8.3 短文件名规避空格（C:\PROGRA~1\...）。短名生成规则依赖创建顺序，同一路径在不同机器上可能是 PROGRA~1 也可能是 PROGRA~2；NTFS 卷还可以整卷关闭 8.3 名生成（fsutil 8dot3name），届时这类路径全部失效。老脚本里见到就该替换成带引号的长路径。

set 的标准写法：引号包住整个赋值

这是全章最值得你立刻改掉的习惯。set "VAR=value"——引号包的是 VAR=value 整体，不是 包 value。

rem 坑一：行尾看不见的空格进了变量值
set LOG=D:\logs      rem 若这行末尾多一个空格，值就是 "D:\logs "
rem 之后 "%LOG%\a.txt" 变成 "D:\logs \a.txt"，路径不存在

rem 坑二：值里的 & 立刻生效，把 set 这行都劈断
set V2=x&y            rem 实际执行 set V2=x 和 命令 y

rem 标准写法：两个问题一次解决
set "LOG=D:\logs"
set "V2=x&y"
rem 注意：引号不会进入变量值本身

rem 而这个写法会把引号一起存进去，通常不是你想要的
set BAD="D:\logs"      rem %BAD% 的值是 "D:\logs"（含引号）
rem 于是 "%BAD%\a.txt" 变成 ""D:\logs"\a.txt"

if 语句里的引号：不加会直接崩

@echo off
set "EMPTY="
if %EMPTY%==abc (echo never) else (echo F3-else)
echo F4: done

rem 实际输出：( 后面的语法不正确  —— 而且脚本就此中止，F4 永远打不出来
rem 因为 %EMPTY% 展开成空，那行变成  if ==abc (...)

正确写法是给两边都加引号，让空值退化成一对空引号：if "%EMPTY%"=="abc"。要判断变量是否存在，更稳的是专用语法 if defined VAR（它不做百分号展开，天然免疫这个问题）。

场合推荐写法说明
赋值set "K=V"吃掉尾随空格，屏蔽 & | >
字符串比较if "%A%"=="%B%"两边都加，缺一边照样崩
不区分大小写比较if /i "%A%"=="%B%"—
判断变量是否已定义if defined A不加 %，最安全
判断文件存在if exist "%F%"路径必须加引号
调用外部程序"%~dp0tools\x.exe" "%ARG%"程序名和每个参数各自加引号
新开窗口start "" "C:\Program Files\a.exe"第一个 "" 是窗口标题占位，见下
for /f 读带空格路径的文件for /f "usebackq" %%L in ("%F%")没有 usebackq 时，引号内容被当成字符串本身
取消参数外层引号%~1见下表
start 的第一个引号参数是窗口标题

start "C:\Program Files\a.exe" 不会启动程序——start 把第一个带引号的参数当成新窗口的标题，然后发现没有要运行的命令。永远写成 start "" "路径"，那个空引号就是标题占位符。这个坑几乎人人踩过一次。

%~ 修饰符速查

参数（%1～%9）和 for 变量都支持 ~ 修饰符，它们是处理路径时唯一正确的工具——别用字符串截取去凑。

写法含义示例（%1 = "D:\proj\a b\x.txt"）
%~1去掉外层引号D:\proj\a b\x.txt
%~f1完整绝对路径D:\proj\a b\x.txt
%~d1盘符D:
%~p1路径（带尾部反斜杠）\proj\a b\
%~n1主文件名x
%~x1扩展名（带点）.txt
%~dp1盘符+路径，可组合D:\proj\a b\
%~nx1文件名+扩展名x.txt
%~z1 %~t1 %~a1大小 / 时间戳 / 属性2048 / 2026-03-01 10:22 / --a------
%~s18.3 短路径 已过时不可靠，别依赖
%~dp0脚本自身所在目录（末尾已含 \）最常用，见下
 
@echo off
rem 定位脚本同级资源的标准句式：%~dp0 末尾已经有反斜杠，别再加一个
set "TOOL=%~dp0tools\ffmpeg.exe"
if not exist "%TOOL%" (
  echo [ERROR] 找不到 %TOOL%
  exit /b 1
)
"%TOOL%" -i "%~f1" -c copy "%~dp1%~n1_out%~x1"

& && || 与管道：连接符和退出码

把几条命令写在一行，是批处理最常见的紧凑写法，也是最容易把「成功」和「失败」搞混的地方。

连接符语义典型用途
A & B先 A 后 B，无论 A 成败一行里塞多条无关命令
A && BA 的 ERRORLEVEL 为 0 才执行 B「成功则继续」链
A || BA 的 ERRORLEVEL 非 0 才执行 B「失败则报错退出」
A | BA 的标准输出接到 B 的标准输入过滤、统计
( A & B )分组，整组共享重定向 / 作为一个条件分支( cmd1 & cmd2 ) > log.txt
 
@echo off
rem 从左到右求值，没有优先级；下面这句读作 ((build && test) || 报错)
call build.bat && call test.bat || (echo [FAIL] 构建或测试失败 & exit /b 1)

rem 分组重定向：两条命令的输出一起进日志
( echo ==== %date% %time% ==== & call deploy.bat ) >> "%~dp0deploy.log" 2>&1

ERRORLEVEL 的两种判断，语义不一样

if errorlevel N 是「大于等于 N」，不是「等于 N」。这是从 DOS 继承的老语义，因为当年的比较只有单向。

@echo off
cmd /c exit 3
echo P6:%errorlevel%          rem 输出 P6:3
if errorlevel 2 echo P7:ge2   rem 会打印（3 >= 2）
if errorlevel 5 echo P8:ge5   rem 不打印（3 < 5）
写法含义注意
if errorlevel 1退出码 ≥ 1「是否失败」的经典判断
if not errorlevel 1退出码 < 1，即 0「是否成功」
if %errorlevel%==3精确等于 3受工序②影响，块内会被提前展开
if !errorlevel!==3精确等于 3块内正确写法，需延迟展开
exit /b N返回 N 给调用者，不关窗口脚本对外的标准返回方式
exit N关闭整个 cmd 进程慎用 双击运行时会直接关窗口
不是所有命令都好好设置退出码

&& 和 || 完全依赖 ERRORLEVEL，但内部命令的表现参差不齐：echo、set（无 /a 时）基本不改动它；for 循环体内部的失败不会冒泡到 for 本身。所以 for ... || echo 失败 这种写法通常抓不到任何东西。判断关键步骤时，宁可显式检查产物：if not exist "%OUT%" ( ... )。

管道的隐藏代价：两个子进程

A | B 并不是在当前 cmd 里跑的——cmd 会为两边各启动一个子 cmd 进程。后果是：管道里对变量的修改，管道结束后全部丢失。

@echo off
set "N="
rem 想统计行数存进变量 —— 这么写永远拿不到值
type data.txt | find /c /v "" > nul & set N=?

rem 正确做法：用 for /f 捕获命令输出
for /f %%N in ('type data.txt ^| find /c /v ""') do set "N=%%N"
echo 行数=%N%
现代提示

PowerShell 的管道传的是对象且在同一进程内，$n = (Get-Content data.txt).Count 一句话搞定；错误处理有 try/catch 和 $ErrorActionPreference，不必去猜某个命令到底设不设置退出码。

括号块：整块解析引出的连环坑

if 和 for 的括号块，是「整块文本一次性读入并做百分号展开」的重灾区。上一节那个计数器恒为 0 的例子，只是它最出名的表现。

块内其余五条规矩

一、连续两行 :: 注释会报错。:: 本质是一个「不可能被跳转到的标签」，不是真正的注释命令。单独一行放在块里，现代 cmd 还能容忍；连着写两行就会炸：

@echo off
if 1==1 (
  echo L3
  :: c1
  :: c2
)
echo END

rem 实际输出：
rem   L3
rem   系统找不到指定的驱动器。   ← 莫名其妙的报错就来自这两行 ::
rem   END

结论很简单：括号块里一律用 rem，不要用 ::。块外两者随意，:: 稍快且更醒目。

二、块里的 ) 必须转义或加引号，否则它会提前关闭整个块：

( echo 进度 ^) 完成 )        rem 输出：进度 ) 完成
( echo "进度 ) 完成" )      rem 引号内的 ) 不算语法

三、else 必须和前一个 ) 同一行。写成 ) else (，中间换行会报「命令语法不正确」。

四、块内的变量赋值，块外才看得见（用 %…% 读时）。因为块结束后才有下一次百分号展开。

五、rem 行以 ^ 结尾会吞掉下一行。注释里带路径时特别容易中招——路径末尾常常正好是反斜杠加脱字符之类的组合，或者你手滑打了个 ^。

@echo off
setlocal enabledelayedexpansion
set "FAILED="
for %%F in (*.log) do (
  rem 块内注释只用 rem；判断和拼接一律用 !…!
  findstr /i /c:"ERROR" "%%F" >nul
  if not errorlevel 1 (
    set "FAILED=!FAILED! %%~nxF"
  )
)
if defined FAILED (
  echo 含错误的日志:!FAILED!
) else (
  echo 全部日志正常
)
endlocal

「命令语法不正确」) 未转义 / else 换了行^)；写成 ) else (

中文与代码页：chcp 65001 到底改了什么

「脚本里的中文提示在别人机器上变成一堆问号」——这是中文环境下最高频的报障。要根治，你得知道一条中文从字节变成屏幕上的字，中间要过几关。

下面这段是实测：把一个 GBK 编码的脚本放到代码页 65001 的控制台里跑，输出的字节直接变成了一串 EF BF BD（Unicode 替换字符 U+FFFD），原文已经不可恢复。

rem 文件以 GBK 保存，控制台当前为 65001
@echo off
chcp
echo 中文测试

rem 输出文件的十六进制：
rem   Active code page: 65001
rem   EF BF BD EF BF BD ... ← 全是替换字符，不是「显示问题」，是数据已经烂了
代码页名称说明
437OEM 美国英文系统的老默认值
936GBK / GB2312简体中文 Windows 的传统默认值 仍适用
950Big5繁体中文
65001UTF-8现代首选 现代提示
1200UTF-16LEcmd 控制台不支持，别设

可落地的两条路线

路线 A（保守）：脚本存 GBK，不动代码页。在纯中文 Windows 内网环境里最省事，中文照常显示。代价是脚本文件进 Git 后 diff 不友好，跨语言系统必炸。

路线 B（推荐）：脚本存 UTF-8 无 BOM，开头切到 65001，结束前还原。还原这一步很多人省略，但 chcp 改的是整个控制台窗口的状态，不是脚本私有的——如果用户是在已有窗口里手动运行你的脚本，你把人家的代码页永久改掉了。下面这段是可直接复用的实测代码：

@echo off
setlocal
rem 保存当前代码页（chcp 的输出形如 "Active code page: 936" / "活动代码页: 936"）
for /f "tokens=2 delims=:" %%c in ('chcp') do set "OLDCP=%%c"
set "OLDCP=%OLDCP: =%"
chcp 65001 >nul

echo 正在处理中文目录…
rem …你的主逻辑…

chcp %OLDCP% >nul
endlocal
rem 实测：SAVED=[65001] → 切 437 → 还原 65001，往返正确

chcp 65001 的历史包袱

已过时的认知 「65001 会导致程序崩溃、for /f 读不到内容」——这些是 Windows 7/8 时代 conhost 的老 bug，在 Windows 10 之后的版本上已基本消失，本章的全部实测都在 65001 下完成。但仍有两个残留风险：一是某些老旧的第三方 exe 自己按 ANSI 代码页解释参数，收到 UTF-8 字节会认不出；二是 chcp 只改控制台，不改 Windows 的 ANSI 代码页（ACP），程序内部的文件名转换仍走 ACP。

现代提示

Windows 10 1903 起，设置里有「Beta：使用 Unicode UTF-8 提供全球语言支持」，可把系统 ACP 直接设为 65001，从根上解决问题——但它会让部分老软件出现乱码，企业环境要先小范围验证。PowerShell 7 更彻底：脚本默认按 UTF-8 读取，Out-File 默认写 UTF-8 无 BOM，整条链路不再需要你手动对齐。

CRLF 与 BOM：看不见的字节

还有一类故障，你把脚本打开逐字看都找不出问题——因为出问题的字符压根不显示。

BOM：文件开头的三个隐形字节

UTF-8 BOM 是 EF BB BF，很多编辑器（尤其是记事本的老版本、以及默认设置下的部分 IDE）保存 UTF-8 时会自动加上。它排在你的第一行代码之前。

好消息：现代 Windows 11 的 cmd.exe 已经能跳过它，带 BOM 的 .bat 直接执行没有报错（实测通过）。坏消息：for /f 读数据文件时不会跳过，BOM 会粘在第一个 token 上：

rem data.txt 存成 UTF-8 带 BOM，内容：alpha,1 / beta,2
@echo off
for /f "tokens=1,2 delims=," %%a in (data.txt) do echo [%%a]-[%%b]

rem 输出：
rem   [﻿alpha]-[1]   ← 方括号和 alpha 之间夹着看不见的 BOM
rem   [beta]-[2]
rem 于是 if "%%a"=="alpha" 永远为假，而你怎么看都觉得它们一模一样

同一份数据存成无 BOM，输出立刻变成 [alpha]-[1]。批处理脚本和它读取的数据文件，一律存 UTF-8 无 BOM。

CRLF：行尾的一个还是两个字节

Windows 行尾是 CR LF（0D 0A），Linux/macOS 是 LF（0A）。批处理传统上要求 CRLF。实测下来，现代 cmd 对纯 LF 文件的容忍度比江湖传说高得多——goto :label、call :sub、括号块在 Windows 11 上都能正常工作。但你不该依赖这份宽容：

  • WinPE、Windows Server 老版本、部分嵌入式镜像里的 cmd 版本行为不一致；
  • 混合行尾（一部分 CRLF、一部分 LF）的文件行为最难预测；
  • 更常见的是间接伤害：脚本从 Git 检出时若被转换，最后一行可能丢掉换行符，导致最后一条命令或最后一个标签不被识别。

所以规矩照旧：.bat/.cmd 用 CRLF，文件末尾留一个空行。在团队里把它固化下来，比每次靠自觉可靠：

rem 仓库根目录的 .gitattributes —— 一次配置，全员生效
* text=auto
*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf
*.sh  text eol=lf

VS Code 里对应两处：右下角状态栏可切换 CRLF/LF 与编码；工作区设置写 "files.eol": "\r\n" 和 "files.encoding": "utf8"（注意不是 utf8bom）。

症状可能的隐形字节怎么确认
第一行报「不是内部或外部命令」文件开头有 BOM（老版本 cmd）看前三字节是否 EF BB BF
字符串比较明明相同却不等token 上粘了 BOM 或 CRecho [%%a] 看方括号间距
最后一条命令不执行文件末尾缺换行符末尾补一个空行
set 的值末尾多东西行尾多余空格 / CR改用 set "K=V"
Git 上每行都显示改动行尾被批量转换配 .gitattributes
 
rem 一行命令查看文件真实字节（前 32 字节），BOM 和行尾一目了然
powershell -NoProfile -Command "Format-Hex -Path '.\build.bat' -Count 32"

调试三件套：回显、暂停、日志

批处理没有断点、没有单步、没有变量监视窗口。你能用的就三样东西：让它把执行过程说出来、让它在关键处停下来、把一切写进文件事后翻。用好了，效率并不比调试器差多少。

一、回显：让 cmd 把展开后的命令念出来

回显打开时，cmd 会在执行前打印经过全部六道工序之后的命令行——这正是你最需要看到的东西：变量到底被替换成了什么，引号有没有配对，行有没有被劈断。

@echo off
rem 只给可疑的一段开回显，其余保持安静
echo on
robocopy "%SRC%" "%DST%" /MIR
echo off

rem 单行前缀 @ 表示「这一行不回显」，与全局开关无关
@set "SECRET_PATH=%TEMP%\stage"
调试第一步永远是注释掉 @echo off

把首行改成 rem @echo off，重跑一遍。80% 的转义 / 引号 bug 会在展开后的回显里当场现形——你会亲眼看到 echo hi Tom 后面跟着一句孤零零的 Jerry。

二、暂停：不让窗口一闪而过

手段用途
pause停住等按键，最常用的「断点」
timeout /t 5停 5 秒后自动继续（可按键跳过）
timeout /t 5 /nobreak停 5 秒，不许跳过
cmd /k "脚本路径"脚本跑完窗口不关，可继续手敲命令查现场
set /p X=按回车继续等回车；顺便可以现场输入测试值

三、日志：把过程和错误都收进文件

重定向本身也有个经典陷阱：2>&1 的位置有讲究。它的意思是「让 2 号句柄指向 1 号句柄当前指向的地方」，所以必须写在 >file 之后。

写法效果
cmd > log.txt覆盖写入标准输出；错误仍打在屏幕上
cmd >> log.txt追加写入
cmd 2> err.txt只收错误
cmd > log.txt 2>&1正确 输出和错误都进 log.txt
cmd 2>&1 > log.txt无效 顺序错了：错误仍去屏幕
cmd >nul 2>&1彻底静音
echo msg > con强制输出到控制台，即使整体已被重定向
( a & b ) > log.txt 2>&1整组共享同一个日志句柄（比每行加 >> 快得多）
 
@echo off
setlocal enabledelayedexpansion
set "LOG=%~dp0build.log"
set "DEBUG=%1"

rem 可开关的调试输出：跑脚本时加个参数 1 就打开
if "%DEBUG%"=="1" echo on

echo ===== %date% %time% 开始 ===== >> "%LOG%"
call :step "编译" msbuild.exe /nologo app.sln
call :step "测试" ctest.exe --output-on-failure
echo ===== 结束，退出码 !ERRORLEVEL! ===== >> "%LOG%"
endlocal & exit /b 0

:step
rem %~1 是步骤名（去引号），%~2 及之后是真正要跑的命令
echo [STEP] %~1 >> "%LOG%"
shift
%1 %2 %3 %4 %5 >> "%LOG%" 2>&1
if errorlevel 1 (
  echo [FAIL] 见日志 "%LOG%"
  exit /b 1
)
goto :eof
日志里的 %errorlevel% 常常是假的

在 if/for 块里写 echo 退出码=%errorlevel%，打出来的是进块之前的值——又是工序②。要么用 !errorlevel!，要么改用 if errorlevel N 这种不做百分号展开的判断。

现代提示

批处理没有 tee，想「既上屏又落盘」得绕一大圈。PowerShell 一句 … | Tee-Object -FilePath build.log 即可；它还有真正的调试器：Set-PSBreakpoint、VS Code 里 F5 单步、$PSDebugContext、Write-Debug／-Verbose 分级输出。如果一个脚本你已经需要靠加日志来定位问题，那它多半已经超出批处理的合理规模了。

为什么这些坑正是 PowerShell 存在的理由

回头看这十个坑，你会发现它们不是十个独立的 bug，而是同一个设计决定的十种表现：cmd 把「数据」和「代码」放在同一个字符串里反复替换。三十年前这是内存约束下的最优解；今天它意味着——你的变量值可以变成命令，你的路径可以变成两个参数，你的注释可以吃掉下一行。

PowerShell 在 2006 年发布时，设计文档里几乎逐条回应了这些问题：

批处理的痛点PowerShell 的做法
值被重新解析成语法参数以对象传递，值永远不参与语法解析
空格路径要靠引号硬扛$path 就是一个字符串对象，含不含空格无所谓
%% / !! 两套展开规则只有 $var 一种，任何位置语义一致
括号块提前展开foreach 是真正的语法结构，作用域清晰
退出码语义靠猜try/catch、$?、$LASTEXITCODE、终止型 / 非终止型错误分级
编码要手动对齐三处PowerShell 7 全链路默认 UTF-8
只能靠 echo 调试真正的断点、单步、变量监视
该在什么时候切换

批处理仍然有它无可替代的位置：仍适用 开机自启、安装程序的钩子、CI 里的一两行胶水、任何「保证在裸装 Windows 上能跑、无需执行策略」的场合。但只要你的脚本里出现了以下任意一条，就该考虑换成 PowerShell：需要循环里累加变量、需要解析结构化输出（JSON/CSV/XML）、需要可靠的错误处理、需要处理不确定编码的文本、或者超过 100 行。判断标准很朴素：当你开始为了对付 cmd 本身而写代码，而不是为了完成任务而写代码时，工具就选错了。
